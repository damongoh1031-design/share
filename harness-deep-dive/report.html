〇什么是 Harness

公式
Agent = Model + Harness
LangChain 提出
提出时间
2026-02-05
Mitchell Hashimoto（HashiCorp 联合创始人）
核心哲学
人类掌舵，智能体执行
通过构建系统环境提升效果
定义

Harness 是模型之外的一切代码、配置与执行逻辑。

「Harness」本意是马具。在 AI 语境中，它指连接「模型（马匹）」和「人类需求（骑手）」的控制框架：它不参与任务执行本身，但决定任务的方向、节奏与停止时机。

三层关系（是包含关系，不是并列）

层解决什么类比
Prompt Engineering怎么对模型说指令
Context Engineering让模型在这一轮看到什么喂给模型的工作台
Harness Engineering整套系统怎么运行、怎么持久化、怎么验证、怎么兜底操作系统

一个很好用的类比

引自 Beren Millidge（2023），被 Akshay 的《The Anatomy of an Agent Harness》引用

裸的 LLM 是一颗没有 RAM、没有磁盘、没有 I/O 的 CPU。

  • 上下文窗口充当内存
  • 外部数据库充当磁盘
  • 工具集充当设备驱动

让这台机器持续跑起来的，是外面这套调度、执行、校验和保护机制。

Harness 回答的是一个工程问题：怎样把一个无状态、会推理的模型，变成一个能持续交付结果的系统。

学术界的定位

中国人民大学高瓴人工智能学院等机构 2026-07 发布全景综述《Towards Long-Horizon Agents: A Survey》：

智能体的长程能力源于「外部脚手架工程（Harness Engineering）」与「内部模型优化（Model Optimization）」的协同演化。Harness 作为运行时控制层，负责组织上下文、维护状态、调度工具、编排流程并进行验证与恢复。

Prompt Engineering → Context Engineering → Runtime Harness（2025 至今）

长程智能体面临的四个挑战：单步错误积累、目标漂移、上下文腐化、稀疏奖励。

一为什么 2026 年突然都在讲 Harness

证据 1：只换 Harness，不换权重，名次可以跳一个量级

LangChain 只换外围基础设施，就把名次从 TerminalBench 2.0 的前 30 名之外拉到第 5。

还有研究项目把「优化 Harness 本身」变成了搜索对象，最终拿到 76.4% 的通过率。

⚠️ 边界

榜单结果不能直接等同于真实产品体验，单个实验也不能替所有场景下结论。但它至少说明——Agent 的表现并不只由模型上限决定，还强烈依赖它跑在什么样的系统里。

证据 2：长任务的误差会快速累积

一个 10 步流程，如果每一步成功率都是 99%，最终全链路成功率也只有大约 90%。

任务再拉长，误差就会开始明显堆积。这就是为什么长任务需要 checkpoint、验证、恢复——而不是靠模型自觉。

证据 3：减法比加法更有效

案例结果
Vercel 在 v0 上删掉了 80% 的工具表现反而更好
Claude Code 靠懒加载实现 95% 的上下文缩减
Manus 半年内重建 Harness 五次每次都在做减法

一个投资人的概括

Aakash Gupta（SaaS 投资人）：「2025 年是 Agent 之年，2026 年是 Harness 之年。模型是商品，Harness 才是护城河。」

一句话总结这一章

把系统拉垮的，越来越是这些更工程的问题：上下文会不会逐轮变脏、工具失败后有没有显式反馈、状态能不能跨会话延续、高风险动作有没有权限边界、结果到底由谁验收。

模型智力在线之后，大家开始重新面对软件工程。

二Harness 的六个承重层

引用 Akshay 的生产级 Harness 拆解（12 个组件压缩为 6 个核心结构）：

1

主循环 —— Harness 的心脏

组装输入 → 调用模型 → 解析输出 → 执行工具 → 塞回结果 → 再来一轮

但难点在循环里每一步到底由谁控制、何时终止、出错后怎么回来。

常见失败：无限转圈 / 提前收尾 / 误把中间结果当最终结果

很多人第一次做 Agent，会把注意力放在「模型有没有想明白」。上线以后，最先暴露的反而是循环失控。

2

工具系统 —— Agent 的手

不只是「给几个函数名」。至少还要管四件事：

  1. 工具如何注册
  2. 参数如何校验
  3. 执行环境是否隔离
  4. 结果如何回写成 Observation
工具分类
Claude Code六类：文件操作、搜索、执行、Web 访问、代码智能、子 Agent 派生
OpenAI Agents SDK三类：函数工具、托管工具、MCP 工具

模型知道可以调用什么工具，只是起点。它能不能在合适的时候调用、带着正确参数调用、在失败后继续恢复，才是 Harness 的事情。

3

上下文与记忆 —— 该记什么、什么时候记、什么时候删

Claude Code 的三层记忆设计（值得直接抄）：

层内容加载方式
① 轻量索引每条约 150 字符始终加载
② 详细主题文件具体主题的展开按需拉取
③ 原始会话记录完整历史只通过搜索访问

关键原则：成熟系统不会把记忆当真相，而是把它当线索。 先靠记忆提示方向，再回到真实文件、真实环境和真实状态里确认。

记忆如果不能被验证，就很容易从「帮助检索」滑向「帮助幻觉」。

4

状态与检查点 —— 让长任务可以继续

系统需要知道：当前做到哪一步、失败后从哪恢复、哪些中间产物值得保留、哪些只是临时噪音。

两种实现路径：

  • 结构化状态对象做 checkpoint
  • 把 git commit + 进度文件 + 任务日志一起当作恢复点

实现可以不同，但目的只有一个：让长任务可以继续，而不是每次都从头赌一遍。

5

权限、错误与安全护栏 —— 最被低估的一层

一个看起来很能干的 Agent，如果没有权限控制，本质上只是一个事故放大器。

核心设计原则：把「模型想做什么」和「系统允许做什么」拆开。

角色职责
模型负责提出动作
工具系统负责决定这个动作能不能做、要不要用户确认、失败后是重试、回传错误、还是直接终止
企业级结论

权限与治理必须在基础设施层通过沙箱、权限策略等机制强制执行，而非依赖提示词。

6

验证与纠偏 —— Demo 和生产的分水岭

工具给了模型行动能力。验证才给了模型纠错能力。

外部反馈回路的构成：测试、lint、类型检查、页面截图、端到端操作，甚至另一个专门负责挑刺的评估器。

一条硬数据

Claude Code 创始人 Boris Cherny 提到，给模型一种能验证自己工作的方式，质量提升 2 到 3 倍。

没有验证，Harness 很容易变成「更快地产出错结果」。

三一次完整循环的七步

1
组装输入
system prompt + 工具定义 + 记忆 + 会话状态 + 当前任务 → 这一轮实际给模型看的上下文
2
模型推理
模型决定这轮是直接回答，还是先调工具
3
分类输出
只有文本没有 tool call → 这轮可能就该结束；有工具调用 → 进入执行阶段
4
执行工具
先参数校验 → 再权限检查 → 再决定并发读 / 串行改 / 直接拒绝
5
回写结果
工具输出重新包装成 Observation；失败也不能静默吞掉，要回成一个明确错误
6
更新状态
会话历史、检查点、工作记忆、压缩触发条件
7
决定是否继续
回到下一轮，或因任务完成 / 预算用尽 / 达最大轮数 / 用户中断 / 安全护栏触发而终止

循环本身往往很朴素。复杂的是每一步背后的工程取舍。

很多人第一次做 Agent 时会困惑：循环有了，怎么还是不稳？多数时候，有循环不等于有 Harness。

4.3 沙箱基础设施层（Harness 的「Hands」）

2026-04-15 是一个分水岭

OpenAI Agents SDK 发布，沙箱成为原生一等公民原语。它同时做了四件事：

  1. 原生沙箱执行
  2. Codex 风格的 agent harness
  3. snapshot / rehydrate 生命周期
  4. 七个内置 provider：Blaxel、Cloudflare、Daytona、E2B、Modal、Runloop、Vercel（+ bring-your-own）

关键的抽象是 workspace Manifest——mount 本地文件、定义输出目录、从 S3/GCS/Azure Blob/Cloudflare 拉数据，而这份工作区描述跨 provider 可移植。provider="e2b" 换成 provider="modal"，agent 的代码执行就换了云。

威胁模型（三个让 Docker 容器不够用的原因）

  1. 通过检索网页内容的间接 prompt injection
  2. 通过攻击者发布的 Python 包、针对 agent 运行的供应链攻击
  3. 监管对 agent 能触及客户数据的关注

agent 被视为对抗性的。它代码能触及的一切都是爆炸半径的一部分。沙箱的职责是让半径小、有时间界、可审计。

一个常被忽略的边界

沙箱是按设计以 session 为界的，而 deployment 恰恰是 session 所不是的一切。 沙箱不做部署——这是它和「交付一个跑在稳定 URL 后面的应用」之间的鸿沟。

五深度案例一：Claude Managed Agents

这是目前公开资料最完整的 Harness 设计。 它把问题从「怎么写一个更聪明的循环」推进到了「怎么设计一个能进生产的运行时」。

5.1 四阶段演进史

阶段抓手局限
① 长上下文100K / 200K context window「长上下文只是工作区变大了，不等于系统有了可靠记忆」
② workflow vs autonomous loop《Building Effective AI Agents》区分两者稳定业务流程用 workflow 更便宜、更稳、更易调试
③ 工具 / 上下文 / 安全think tool、multi-agent research、context engineering、Agent Skills、Claude Code sandboxing、MCP主题分散，但都指向同一个问题
④ Runtime 层Managed Agents—
 
思路主线：长上下文 → 工具循环 → 上下文工程 → 安全执行 → 可恢复运行时
第③阶段的共同指向

Agent 一旦开始做真实工作，问题会从「模型会不会回答」转向「系统怎么承载模型行动」。

  • 工具太多，上下文会爆
  • 任务太长，聊天记录不够用
  • 执行太自由，安全边界会失控
  • 多 Agent 太积极，成本和协调复杂度会压上来
  • 模型升级太快，旧 harness 假设会过期

5.2 核心逻辑：不要把会变化的东西绑死在一起

Harnesses encode assumptions that go stale as models improve.（Harness 会编码当前模型的弱点。）

Anthropic 举的具体例子：

Claude Sonnet 4.5 在接近上下文窗口上限时容易提前结束任务，所以 harness 加了 context reset。到了 Claude Opus 4.5，这个行为消失了，原来的 reset 逻辑就开始显得多余。

不要把今天模型的缺陷，写成明天系统的架构。

5.3 沉淀出的八个核心接口

Session：任务发生过什么
Harness：下一步怎么调度
Sandbox：动作在哪里执行
Tool interface：动作如何被调用
Credential boundary：动作是否被授权
Context builder：这次模型该看什么
Trace / Eval：过程和结果如何被复盘

这套设计不追求某一个固定 Agent loop 的优雅。它追求的是当模型、工具、执行环境变化时，系统还能继续演进。

5.4 关键点一：Brain / Hands 解耦

概念组成
BrainClaude + harness
Handssandbox、MCP server、外部工具、设备、浏览器、代码执行环境

早期做法的典型问题：把 brain 放进 hands 里面（一个容器里跑 harness、存 session、执行工具、放文件系统、有时还放凭证）→ 容器变成 pet server（不能轻易丢、不能轻易重启、挂了要救、调试要进去看）。

Anthropic 的做法：让 harness 离开 sandbox
  • Harness 成为相对无状态的控制面
  • Sandbox 变成可调用、可重建的执行资源
  • 二者通过一个极简接口连接：execute(name, input) -> string

三个直接收益：① Sandbox 挂了，不等于任务死了 ② Brain 可以先工作，sandbox 后加载 ③ 一个 brain 可以调多个 hands

5.5 关键点二：Session 的设计

Session is not Claude's context window.

这个区分是全篇最重要的判断。 很多 Agent 系统把 session、聊天记录、memory、上下文窗口混在一起——短任务还能撑，长任务很容易乱。

一个靠谱的 session 至少应该记录：

user_input / model_response / tool_call / tool_result
file_change / error / retry / approval / checkpoint
分工

Prompt 是工作区，Session 是账本。

  • 工作区可以整理、压缩、裁剪、重组
  • 账本要尽量完整、可查、可恢复
原始事件长期保存
      ↓
Context Builder 动态选择
      ↓
当前模型调用看到一个高信号上下文

Context engineering 负责「这次模型该看什么」。Session event log 负责「系统到底发生过什么」。

为什么这层不能省：长任务 Agent 如果没有这一层，后面做 resume、trace、eval、debug 都会很难。

5.6 关键点三：Sandbox 的三个要求

  1. 要隔离文件系统和网络 —— 模型生成代码必须按不可信代码处理。否则 prompt injection 可以诱导 Agent 读不该读的文件、访问不该访问的服务，把结果带出去
  2. 不该直接持有长期凭证 —— 只要 sandbox 里有 GitHub token、数据库 key、云服务密钥，Agent 就有机会被诱导读取它们
  3. 要能重建和恢复 —— 长任务一定会遇到失败；如果 sandbox 和 session 绑定太死，失败就会拖垮任务

5.7 完整架构图（文字版）

模块责任边界
Harness控制面 —— 负责调度模型、上下文、工具、策略
Session event log持久状态 —— 不跟某个容器绑定
Context Builder从 session、memory、skills、工具结果里组装高信号上下文
Tool Router把动作分发给 MCP、代码执行环境、sandbox 或其他 hand
Sandbox执行动作 —— 可以失败，可以重建
Credential Proxy / Vault管住凭证 —— 不让不可信执行环境直接拿 token
Trace / Eval贯穿整个 run —— 让系统能复盘、回归、对比 harness 改动

6.2 核心公式的展开

Model + Harness = Agent

模型负责预测下一个 token；Harness 决定模型能看到哪些上下文、调用哪些工具、记录什么会话事件、管理哪些文件与子进程。

把这些「决策权」做成可插拔的插件，就是 dsh 的核心价值。

6.3 一切皆插件

所有 Agent 能力都是插件，模型、工具、会话、沙箱、UI 都能在配置层自由替换：

插件类型决定什么
模型插件模型适配器（V4-Flash / V4-Pro / OpenAI / Claude / 本地）
工具插件注册可调用工具（读文件 / 跑命令 / 调 API）
会话插件多轮对话 + 上下文窗口
沙箱插件隔离文件系统 + 网络 + 进程
UI 插件Web UI / CLI / Headless 三种使用方式

启动时通过有序插件树组合这些能力，并叠加 profile / bundle / patch——无需改源码，即可在配置层定制自己的 Agent。

6.4 四种运行模式

模式适用
Standard通用对话 / 问答（默认）
PTC（Programmatic Tool Calling）让模型用 TypeScript 组合多步工具调用，适合复杂工作流、跨工具编排
Minimal极简、纯模型对话（关闭大部分插件）
Creator自定义 Agent（给开发者最大自由度）

6.5 三个关键转变（dsh 最有价值的部分）

从到机制
「框架能力」「可治理运行时」自改写运行时 + 沙箱 + fail-closed 设计，使治理成为动态、可观测的决策引擎
「日志」「事件-可重放-可审计」事件溯源技术把 Agent 行为转化为可完整回放和审计的证据链
依赖「调参 / 自评」「工程纪律与自动化守门」代码覆盖率、自动化快照回归测试、死代码检测等机器强制门禁

它要解决的是 Agent 从「能跑」到「敢交付」的治理缺口。

6.6 可观测性

  • 每次运行写入仅追加会话日志
  • Trajectory 视图可查看：系统提示词 / 思维链 / 工具调用 / 子 Agent 调度

7.2 设计理念（与 Anthropic 形成鲜明对比）

避免创建独立的 AI 应用外壳，而将 Agent 能力直接嵌入现有业务软件。

组件作用

Codex SDK提供编程式接口

7.4 它为什么被称为「生产级 Agent 的底层架构」

Codex 通过 CLI 在本地执行可靠的代码改动，拥有完整的 Agent 循环编排能力，支持数百轮工具调用和自动上下文管理。

7.5 行业判断

OpenAI 开源 Codex Harness 标志着：Agent 竞赛的重心，正从模型层下移至执行层。

这与 Anthropic 的判断一致：两家在半年内都把 Harness 作为独立资产开源/公测，说明「模型是商品，Harness 才是护城河」已经从观点变成了动作。

八研究型 vs 生产型 Harness

这是判断一个 Harness 是否「成熟」的核心标准

很多 Agent demo 看起来很强，进入生产之后变得笨重、昂贵、难调。原因是研究型 harness 和生产型 harness 的目标不同。

维度研究型 Harness生产型 Harness
目标拉高任务成功率上限在成本、延迟、安全约束下稳定交付
状态transcript、本地文件、临时 progress file外部 session log、checkpoint、event history
上下文尽量多给模型更小、更高信号的上下文集合
工具能接多少接多少动态发现、按需加载、权限收敛
多 Agent优先尝试并行和角色分工只在高价值、可并行任务中启用
安全人工确认、简单隔离sandbox、proxy、vault、scoped credential
失败恢复重跑或人工接管resume、replay、checkpoint、trace
评估看最终 demo 是否完成outcome eval、trace analysis、regression suite
迭代方式加模块、加策略、加 Agent做 ablation，删掉过时策略

一条关键概念：Harness 策略会被模型升级「重新定价」

今天 planner 有用，明天可能拖慢系统；今天 evaluator 能救错，明天可能只是在增加成本；今天 context reset 是必要补丁，明天可能成了无用复杂度。

所以生产型 harness 不能只会加东西，也要能删东西。 每次模型升级，都应该重新测：

  • memory 是否有收益
  • critic 是否有收益
  • tool search 是否有收益
  • multi-agent fanout 是否值得
  • context reset 是否还需要

Agent 工程里，能删掉过时复杂度，是一种很实际的能力。

九Harness 设计的五组取舍

没有标准答案，只有取舍。

9.1 单 Agent 还是多 Agent

一个常见误区，是一上来就上多 Agent。但多 Agent 从来不是白拿的收益——它会带来额外路由开销、上下文损失、角色边界设计和更多失败点。

更稳的顺序通常是：先把单 Agent 做通，再把明显超载的职责拆出去。

9.2 ReAct 还是 Plan-and-Execute

优点类比
ReAct灵活，边想边做即兴驾驶
Plan-and-Execute稳定，先摊开路线再逐段执行先画施工图再开工

任务越长、代价越高、回滚越麻烦，越值得把计划层显式拿出来。

9.3 上下文到底怎么管

很多团队的默认思路是「窗口大一点就好了」。但窗口变大，不代表中间位置的信息就更容易被利用。

成熟系统关心的是信号密度：哪些信息必须常驻、哪些只在需要时检索、哪些旧 Observation 应该折叠、哪些总结必须进入长期记忆。

9.4 验证交给谁

让生成器自己验自己，速度很快。问题是它通常也最容易放过自己。

所以只要任务一旦碰到代码、页面、部署、数据写入这些「能真测」的地方，外部验证几乎都是值得补上的。

9.5 Harness 到底要多厚（最难的一组）

Harness 太薄，很多稳定性问题只能靠模型自觉。

Harness 太厚，系统会变得笨重、昂贵，而且和当前模型强绑定，模型一升级，很多脚手架可能反而成了负担。

好的 Harness 要一边补承重结构，一边等待模型进步后再把不再承重的部分删掉。

9.6 一条量化经验

当工具数超过 10 个且职责重叠时，模型的调用质量会明显下降。

如果不是明确必要，更稳的做法是只暴露当前步骤会用到的最小工具集。

十AGENTS.md / Spec / Skills 也是 Harness

这一节连接了本会话前几轮的所有发现

很多人以为 Harness 只是 Runtime，其实不是。Harness 真正吃力的地方，往往是那些把团队经验外移成工件的层。

这三层解决的是同一个问题：尽量缩小「必须靠模型临场发挥」的面积。

层回答什么类比
AGENTS.md这个仓库怎么读 / 哪些规则先于当前任务 / 哪些入口才是标准入口 / 改哪些东西必须联动哪些检查仓库地图
Spec这次到底要交付什么 / 哪些边界不能越 / 什么叫「做完了」 / 哪些验收条件必须先对齐本轮任务契约
Skills这类问题以后通常怎么做 / 哪些步骤高频而稳定 / 哪些检查和脚手架值得复用团队程序性记忆

它们合起来在做同一件事：

  • 把知识从聊天记录里搬出来
  • 把规则从 review 口头提醒里搬出来
  • 把经验从某个资深工程师脑子里搬出来
  • 把验证从「我觉得差不多」搬到系统动作里
这条线接回前几轮的发现

上一轮社区调研的最高分诉求是 AGENTS.md 跨工具标准（Claude Code #6235，4,060 👍）——现在可以理解它为什么是「最强的单一诉求」：它不是配置文件偏好问题，它是 Harness 的一层。

第七轮发现的 Agent Skills 生态（102 家官方厂商、数千个官方 skill） 同理——Skills 是 Harness 的程序性记忆层。

门槛在于：软件工程能不能被改造成对 Agent 可见、可验证、可执行的系统。

两个新衍生概念

概念定义
Coordination Engineering（协调工程）Harness Engineering 延伸出面向团队协作的范式：在 Harness SDK Agent 个体能力之上增加协调层，解决团队编排、任务调度、通信协议等系统工程问题
Runtime Harness 阶段综述把大模型系统演进概括为 Prompt Engineering → Context Engineering → Runtime Harness（2025 至今）
工业场景的一条特殊洞察

工业实践强调双模双轨协同：大模型负责语义理解、任务拆解和决策调度，而小模型与工业机理模型承担高确定性执行——以应对工业场景对确定性、安全性、实时性和可追溯性的严苛要求。

这条对任何高可靠性场景都有借鉴意义：不是所有环节都该交给概率模型。
