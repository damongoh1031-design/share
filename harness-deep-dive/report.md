## 〇 什么是 Harness

### 0.1 公式与定义

**LangChain 提出的公式**：

```
Agent = Model + Harness
```

> **Harness 是模型之外的一切代码、配置与执行逻辑。**

**「驾驭工程」（Harness Engineering）** 由 HashiCorp 联合创始人 **Mitchell Hashimoto 于 2026-02-05 首次提出**，核心哲学是「**人类掌舵，智能体执行**」——旨在通过构建系统环境来提升大模型的使用效果，而非单纯追求模型性能。

「Harness」本意是马具。在 AI 语境中，它指连接「模型（马匹）」和「人类需求（骑手）」的控制框架：**它不参与任务执行本身，但决定任务的方向、节奏与停止时机。**

### 0.2 三层关系（是包含关系，不是并列）

| 层 | 解决什么 | 类比 |
|---|---|---|
| **Prompt Engineering** | 怎么对模型说 | 指令 |
| **Context Engineering** | 让模型在**这一轮**看到什么 | 喂给模型的工作台 |
| **Harness Engineering** | **整套系统怎么运行、怎么持久化、怎么验证、怎么兜底** | **操作系统** |

### 0.3 一个很好用的类比

引用自 Beren Millidge（2023），被 Akshay 的 *The Anatomy of an Agent Harness* 引用：

> **裸的 LLM 是一颗没有 RAM、没有磁盘、没有 I/O 的 CPU。**
> - 上下文窗口充当**内存**
> - 外部数据库充当**磁盘**
> - 工具集充当**设备驱动**
>
> **让这台机器持续跑起来的，是外面这套调度、执行、校验和保护机制。**

**Harness 回答的是一个工程问题：怎样把一个无状态、会推理的模型，变成一个能持续交付结果的系统。**

### 0.4 学术界的定位

**中国人民大学高瓴人工智能学院**等机构于 2026-07 发布全景综述《**Towards Long-Horizon Agents: A Survey**》，提出：

> 智能体的长程能力源于「**外部脚手架工程（Harness Engineering）**」与「**内部模型优化（Model Optimization）**」的**协同演化**。Harness 作为运行时控制层，负责组织上下文、维护状态、调度工具、编排流程并进行验证与恢复。

**该综述把大模型系统演进概括为三个阶段**：

```
Prompt Engineering → Context Engineering → Runtime Harness（2025 至今）
```

**在 Runtime Harness 阶段，控制面扩展到了智能体运行脚手架**——不仅组织上下文，还管理工具、记忆、工作流、权限、验证、恢复和多智能体协作。

**长程智能体面临的四个挑战**：单步错误积累、目标漂移、上下文腐化、稀疏奖励。

## 一 为什么 2026 年突然都在讲 Harness

**三个硬证据。**

### 证据 1：只换 Harness，不换权重，名次可以跳一个量级

> **LangChain 只换外围基础设施，就把名次从 TerminalBench 2.0 的前 30 名之外拉到第 5。**

还有研究项目把「**优化 Harness 本身**」变成了搜索对象，最终拿到 **76.4% 的通过率**。

> ⚠️ **边界**：榜单结果不能直接等同于真实产品体验，单个实验也不能替所有场景下结论。但它至少说明——**Agent 的表现并不只由模型上限决定，还强烈依赖它跑在什么样的系统里。**

### 证据 2：长任务的误差会快速累积

**一个简单的算术**：

> 一个 10 步流程，如果**每一步**成功率都是 **99%**，最终全链路成功率也只有大约 **90%**。

任务再拉长，误差就会开始明显堆积。**这就是为什么长任务需要 checkpoint、验证、恢复——而不是靠模型自觉。**

### 证据 3：减法比加法更有效

| 案例 | 结果 |
|---|---|
| **Vercel 在 v0 上删掉了 80% 的工具** | **表现反而更好** |
| **Claude Code 靠懒加载** | **实现 95% 的上下文缩减** |
| **Manus 半年内重建 Harness 五次** | **每次都在做减法** |

### 一个投资人的概括

> **Aakash Gupta（SaaS 投资人）**：「**2025 年是 Agent 之年，2026 年是 Harness 之年。模型是商品，Harness 才是护城河。**」

**行业佐证**：Manus 重写 Harness 五次历时六个月，LangChain 一年迭代四次架构，OpenAI 甚至用 Agent 构建了完整的生产系统。

### 一句话总结这一章

> **把系统拉垮的，越来越是这些更工程的问题**：上下文会不会逐轮变脏、工具失败后有没有显式反馈、状态能不能跨会话延续、高风险动作有没有权限边界、结果到底由谁验收。
>
> **模型智力在线之后，大家开始重新面对软件工程。**

## 二 Harness 的六个承重层

引用 Akshay 的生产级 Harness 拆解（12 个组件压缩为 6 个核心结构）：

### 2.1 主循环 —— Harness 的心脏

表面上经常只是一个 `while` loop：

```
组装输入 → 调用模型 → 解析输出 → 执行工具 → 塞回结果 → 再来一轮
```

**但难点在循环里每一步到底由谁控制、何时终止、出错后怎么回来。**

> 很多人第一次做 Agent，会把注意力放在「模型有没有想明白」。上线以后，**最先暴露的反而是循环失控：无限转圈、提前收尾、误把中间结果当最终结果。**

### 2.2 工具系统 —— Agent 的手

不只是「给几个函数名」。至少还要管四件事：

1. 工具如何**注册**
2. 参数如何**校验**
3. 执行环境是否**隔离**
4. 结果如何**回写成模型能继续理解的 Observation**

**两家厂商的分类对照**：

| | 工具分类 |
|---|---|
| **Claude Code** | **六类**：文件操作、搜索、执行、Web 访问、代码智能、子 Agent 派生 |
| **OpenAI Agents SDK** | **三类**：函数工具、托管工具、MCP 工具 |

> 分类方法不同，但要解决的问题一样。**同样都支持 tool calling，跑出来的体验也会差很多。**
>
> **模型知道可以调用什么工具，只是起点。它能不能在合适的时候调用、带着正确参数调用、在失败后继续恢复，才是 Harness 的事情。**

### 2.3 上下文与记忆 —— 该记什么、什么时候记、什么时候删

**Claude Code 的三层记忆设计**（值得直接抄）：

| 层 | 内容 | 加载方式 |
|---|---|---|
| **① 轻量索引** | 每条约 **150 字符** | **始终加载** |
| **② 详细主题文件** | 具体主题的展开 | **按需拉取** |
| **③ 原始会话记录** | 完整历史 | **只通过搜索访问** |

> **关键原则**：**成熟系统不会把记忆当真相，而是把它当线索。** 先靠记忆提示方向，再回到真实文件、真实环境和真实状态里确认。
>
> **记忆如果不能被验证，就很容易从「帮助检索」滑向「帮助幻觉」。**

### 2.4 状态与检查点 —— 让长任务可以继续

系统需要知道：当前做到哪一步、失败后从哪恢复、哪些中间产物值得保留、哪些只是临时噪音。

**两种实现路径**：
- 结构化状态对象做 checkpoint
- 把 git commit + 进度文件 + 任务日志一起当作恢复点

> 实现可以不同，但目的只有一个：**让长任务可以继续，而不是每次都从头赌一遍。**

### 2.5 权限、错误与安全护栏 —— 最被低估的一层

> **一个看起来很能干的 Agent，如果没有权限控制，本质上只是一个事故放大器。**

**核心设计原则：把「模型想做什么」和「系统允许做什么」拆开。**

| 角色 | 职责 |
|---|---|
| **模型** | 负责**提出**动作 |
| **工具系统** | 负责**决定**这个动作能不能做、要不要用户确认、失败后是重试、回传错误、还是直接终止 |

**这一层的企业级结论**（来自综述解读）：

> **权限与治理必须在基础设施层通过沙箱、权限策略等机制强制执行，而非依赖提示词。**

### 2.6 验证与纠偏 —— Demo 和生产的分水岭

> **工具给了模型行动能力。验证才给了模型纠错能力。**

**外部反馈回路的构成**：测试、lint、类型检查、页面截图、端到端操作，甚至**另一个专门负责挑刺的评估器**。

**一条硬数据**：

> **Claude Code 创始人 Boris Cherny 提到，给模型一种能验证自己工作的方式，质量提升 2 到 3 倍。**

**反面**：

> **没有验证，Harness 很容易变成「更快地产出错结果」。**

## 三 一次完整循环的七步

只讲组件容易停在名词层。顺着一轮真实执行看：

| # | 步骤 | 关键细节 |
|---|---|---|
| **1** | **组装输入** | system prompt + 工具定义 + 记忆 + 会话状态 + 当前任务 → 这一轮实际给模型看的上下文 |
| **2** | **模型推理** | 模型决定这轮是直接回答，还是先调工具 |
| **3** | **分类输出** | 只有文本没有 tool call → 这轮可能就该结束；有工具调用 → 进入执行阶段 |
| **4** | **执行工具** | **先参数校验 → 再权限检查 → 再决定并发读 / 串行改 / 直接拒绝** |
| **5** | **回写结果** | 工具输出重新包装成 Observation；**失败也不能静默吞掉，要回成一个明确错误** |
| **6** | **更新状态** | 会话历史、检查点、工作记忆、**压缩触发条件** |
| **7** | **决定是否继续** | 回到下一轮，或因任务完成 / 预算用尽 / 达最大轮数 / 用户中断 / 安全护栏触发而终止 |

> **循环本身往往很朴素。复杂的是每一步背后的工程取舍。**
>
> **很多人第一次做 Agent 时会困惑：循环有了，怎么还是不稳？多数时候，有循环不等于有 Harness。**

## 四 成熟 Harness 全景

**按层次分五类。** 这是本报告最实用的一章。

### 4.1 厂商官方 Harness（三家，均已开源或公测）

| Harness | 厂商 | 时间 | 许可 | 核心设计 |
|---|---|---|---|---|
| **Claude Managed Agents** | **Anthropic** | 2026-04 公测 | — | **Session / Harness / Sandbox 三分解构**；Brain-Hands 解耦 |
| **Codex Harness** | **OpenAI** | **2026-08-19 开源** | **Apache-2.0** | **把 Agent 能力嵌入现有业务软件**；`app-server` + JSON-RPC |
| **DeepSeek Harness (dsh)** | **DeepSeek** | **2026-08-13 v0.1** | **MIT** | **一切皆插件**（Cordis）；「Model + Harness = Agent」 |

**三家的定位差异很清晰**：
- **Anthropic** 走「**托管运行时**」路线——把 Harness 做成云服务
- **OpenAI** 走「**嵌入现有软件**」路线——明确「避免创建独立的 AI 应用外壳」
- **DeepSeek** 走「**微内核 + 插件**」路线——官方定位是「**Agent 微内核操作系统**」

### 4.2 开源成品 Agent（Harness 运行底座类）

**特点**：自带完整 Agent 运行环境，不是单一用途 Agent；可以在底座上组装多个不同能力 Agent，支持子 Agent 互相调用、原生 MCP、会话统一管理。

| 项目 | 星数（本会话前几轮核验） | 特点 |
|---|---|---|
| **OpenHands** | 90,850★ | 前身 OpenDevin；生产级自主选项；**1880 万美元 A 轮**；AMD / Apple / Google / Amazon / Netflix 在用 |
| **OpenCode** | — | MIT；相对完整的开发体验；多模型接入、文件操作、会话与工作区体验 |
| **Pi** | — | 可扩展、多 provider 支持 |
| **Goose** | 55,269★ | **AAIF 创始项目**；MCP 即扩展模型，70+ 内置扩展 |
| **Hermes Agent** | 253,604★ | 持久记忆 + `bot_relay` + `cron` |
| **SWE-agent** | — | 学术路线；SWE-bench 原始实现 |

**一个关键判断**（知乎，2026-09-01）：

> 截至 2026 年 9 月，OpenCode、Pi 等开源 Coding Agent **已经具备替代 Codex CLI 日常开发能力的实力，但还不能完整替代 Codex 的整套产品体系**。真正的差异已经不只是「谁更会写代码」，而是**模型、Agent 框架、执行环境、上下文管理、云端基础设施和安全机制的综合竞争**。

### 4.3 沙箱基础设施层（Harness 的「Hands」）

**2026-04-15 是一个分水岭**：OpenAI Agents SDK 发布，**沙箱成为原生一等公民原语**。

**它同时做了四件事**：
1. **原生沙箱执行**
2. **Codex 风格的 agent harness**
3. **snapshot / rehydrate 生命周期**
4. **七个内置 provider**：Blaxel、Cloudflare、Daytona、E2B、Modal、Runloop、Vercel（+ bring-your-own）

**关键的抽象是 workspace Manifest**——mount 本地文件、定义输出目录、从 S3/GCS/Azure Blob/Cloudflare 拉数据，而这份工作区描述**跨 provider 可移植**。`provider="e2b"` 换成 `provider="modal"`，agent 的代码执行就换了云。

**三大沙箱对比**（2026-10-08 核价）：

| 维度 | **E2B** | **Daytona** | **Modal** |
|---|---|---|---|
| **隔离** | **Firecracker microVM**（每沙箱独立内核） | 默认容器；有 Linux VM / Windows VM 类 | 默认 gVisor；**VM runtime 2026-10-01 GA** |
| **冷启动** | ~150ms（从快照） | **~71-90ms**（热池/快照） | 亚秒到 2-4s |
| **Pause with memory** | ✅ **resume ~1s，计费停止** | 仅 VM 沙箱 | 文件系统快照；内存快照实验性且 7 天过期 |
| **Fork** | ✅ **一次调用最多 20 份，带内存** | VM 沙箱，带内存 | 快照后创建 |
| **连续运行上限** | 1h Hobby / 24h Pro | 默认 15 分钟空闲后自动停止 | 默认 5 分钟 / 最大 24h |
| **GPU** | ❌ 不提供 | ✅ **最多 8 GPU** | ✅ 仅 gVisor runtime |
| **许可 / 自托管** | **Apache-2.0，可自托管** | 曾 AGPL-3.0；**2026-06 核心转私有**（社区 fork：Nightona） | **闭源云，无自托管** |
| **vCPU 费率** | $0.0504/vCPU-hr | $0.0504/vCPU-hr | $0.071/vCPU-hr（**40% 溢价**） |
| **内存费率** | $0.0162/GiB-hr | 与 E2B 持平 | $0.024/GiB-hr |
| **企业背书** | **88% 的 Fortune 100 已签约**；$21M A 轮 | SOC 2/HIPAA/GDPR；$24M A 轮 | SOC 2 + HIPAA；**$355M C 轮 @ $4.65B** |

**其他严肃选手**：Fly.io Sprites、Docker Sandboxes、Deno Sandbox、**Cloudflare Sandbox SDK**（1.0 于 2026-09-30 发布，Durable Object 类通过 `this.ctx.container` 管理沙箱容器）。

**威胁模型（三个让 Docker 容器不够用的原因）**：
1. 通过检索网页内容的**间接 prompt injection**
2. 通过攻击者发布的 Python 包、针对 agent 运行的**供应链攻击**
3. 监管对 agent 能触及客户数据的关注

> **agent 被视为对抗性的。它代码能触及的一切都是爆炸半径的一部分。沙箱的职责是让半径小、有时间界、可审计。**

**一个常被忽略的边界**：**沙箱是按设计以 session 为界的，而 deployment 恰恰是 session 所不是的一切。** 沙箱不做部署——这是它和「交付一个跑在稳定 URL 后面的应用」之间的鸿沟。

## 五 深度案例一：Claude Managed Agents（Anthropic）

**这是目前公开资料最完整的 Harness 设计。** 它把问题从「怎么写一个更聪明的循环」推进到了「**怎么设计一个能进生产的运行时**」。

### 5.1 四阶段演进史

| 阶段 | 抓手 | 局限 |
|---|---|---|
| **① 长上下文** | 100K / 200K context window | **「长上下文只是工作区变大了，不等于系统有了可靠记忆」** |
| **② workflow vs autonomous loop** | 《Building Effective AI Agents》区分两者 | 稳定业务流程用 workflow 更便宜、更稳、更易调试 |
| **③ 工具 / 上下文 / 安全** | think tool、multi-agent research、context engineering、Agent Skills、Claude Code sandboxing、MCP | 主题分散，但都指向同一个问题 |
| **④ Runtime 层** | **Managed Agents** | — |

**思路主线**：

```
长上下文 → 工具循环 → 上下文工程 → 安全执行 → 可恢复运行时
```

**第③阶段的共同指向**：

> **Agent 一旦开始做真实工作，问题会从「模型会不会回答」转向「系统怎么承载模型行动」。**
> - 工具太多，上下文会爆
> - 任务太长，聊天记录不够用
> - 执行太自由，安全边界会失控
> - 多 Agent 太积极，成本和协调复杂度会压上来
> - **模型升级太快，旧 harness 假设会过期**

### 5.2 核心逻辑：不要把会变化的东西绑死在一起

> **Harnesses encode assumptions that go stale as models improve.**
> （Harness 会编码当前模型的弱点。）

**Anthropic 举的具体例子**：

> **Claude Sonnet 4.5 在接近上下文窗口上限时容易提前结束任务**，所以 harness 加了 **context reset**。到了 **Claude Opus 4.5，这个行为消失了**，原来的 reset 逻辑就开始显得多余。

> **不要把今天模型的缺陷，写成明天系统的架构。**

### 5.3 沉淀出的八个核心接口

```
Session：任务发生过什么
Harness：下一步怎么调度
Sandbox：动作在哪里执行
Tool interface：动作如何被调用
Credential boundary：动作是否被授权
Context builder：这次模型该看什么
Trace / Eval：过程和结果如何被复盘
```

**这套设计不追求某一个固定 Agent loop 的优雅。它追求的是当模型、工具、执行环境变化时，系统还能继续演进。**

### 5.4 关键点一：Brain / Hands 解耦

| 概念 | 组成 |
|---|---|
| **Brain** | Claude + harness |
| **Hands** | sandbox、MCP server、外部工具、设备、浏览器、代码执行环境 |

**早期做法的典型问题**：把 brain 放进 hands 里面（一个容器里跑 harness、存 session、执行工具、放文件系统、有时还放凭证）→ 容器变成 **pet server**（不能轻易丢、不能轻易重启、挂了要救、调试要进去看）。

**Anthropic 的做法**：**让 harness 离开 sandbox。**
- Harness 成为相对**无状态的控制面**
- Sandbox 变成**可调用、可重建的执行资源**
- 二者通过一个极简接口连接：**`execute(name, input) -> string`**

**三个直接收益**：
1. **Sandbox 挂了，不等于任务死了**
2. **Brain 可以先工作，sandbox 后加载**
3. **一个 brain 可以调多个 hands**

### 5.5 关键点二：Session 的设计

> **Session is not Claude's context window.**

**这个区分是全篇最重要的判断。** 很多 Agent 系统把 session、聊天记录、memory、上下文窗口混在一起——短任务还能撑，长任务很容易乱。

**一个靠谱的 session 至少应该记录**：

```
user_input / model_response / tool_call / tool_result
file_change / error / retry / approval / checkpoint
```

**分工**：

> **Prompt 是工作区，Session 是账本。**
> - 工作区可以整理、压缩、裁剪、重组
> - 账本要尽量完整、可查、可恢复

**结构**：

```
原始事件长期保存
      ↓
Context Builder 动态选择
      ↓
当前模型调用看到一个高信号上下文
```

> **Context engineering 负责「这次模型该看什么」。Session event log 负责「系统到底发生过什么」。**

**为什么这层不能省**：长任务 Agent 如果没有这一层，后面做 **resume、trace、eval、debug 都会很难**。

### 5.6 关键点三：Sandbox 的三个要求

1. **要隔离文件系统和网络** —— **模型生成代码必须按不可信代码处理**。否则 prompt injection 可以诱导 Agent 读不该读的文件、访问不该访问的服务，把结果带出去
2. **不该直接持有长期凭证** —— 只要 sandbox 里有 GitHub token、数据库 key、云服务密钥，Agent 就有机会被诱导读取它们
3. **要能重建和恢复** —— 长任务一定会遇到失败；如果 sandbox 和 session 绑定太死，失败就会拖垮任务

### 5.7 完整架构图（文字版）

| 模块 | 责任边界 |
|---|---|
| **Harness** | **控制面** —— 负责调度模型、上下文、工具、策略 |
| **Session event log** | **持久状态** —— 不跟某个容器绑定 |
| **Context Builder** | 从 session、memory、skills、工具结果里**组装高信号上下文** |
| **Tool Router** | 把动作**分发**给 MCP、代码执行环境、sandbox 或其他 hand |
| **Sandbox** | **执行动作** —— 可以失败，可以重建 |
| **Credential Proxy / Vault** | **管住凭证** —— 不让不可信执行环境直接拿 token |
| **Trace / Eval** | 贯穿整个 run —— 让系统能复盘、回归、对比 harness 改动 |

## 六 深度案例二：DeepSeek Harness（dsh）

### 6.1 基本信息

| 项 | 值 |
|---|---|
| 开源时间 | **2026-08-13（v0.1 开发者预览）** |
| 许可 | **MIT** |
| 定位 | **Agent 微内核操作系统** |
| 官方定义 | **Model + Harness = Agent** |
| 核心设计 | **一切皆插件（Everything is a Plugin）** |
| 底层框架 | **Cordis 插件系统**（论文 *A Programming Paradigm for Spatiotemporal Composability*） |
| 对标 | **OpenAI Codex** 与 **Anthropic Claude Cowork** |
| 立项时间 | 2026 年 5 月 → 6 月 10 日第一条提交 → 8 月 13 日 v0.1 |

### 6.2 核心公式的展开

> **Model + Harness = Agent**
>
> 模型负责**预测下一个 token**；**Harness** 决定模型能看到哪些上下文、调用哪些工具、记录什么会话事件、管理哪些文件与子进程。

**把这些「决策权」做成可插拔的插件，就是 dsh 的核心价值。**

### 6.3 一切皆插件

所有 Agent 能力都是插件，**模型、工具、会话、沙箱、UI 都能在配置层自由替换**：

| 插件类型 | 决定什么 |
|---|---|
| **模型插件** | 模型适配器（V4-Flash / V4-Pro / OpenAI / Claude / 本地） |
| **工具插件** | 注册可调用工具（读文件 / 跑命令 / 调 API） |
| **会话插件** | 多轮对话 + 上下文窗口 |
| **沙箱插件** | 隔离文件系统 + 网络 + 进程 |
| **UI 插件** | Web UI / CLI / Headless 三种使用方式 |

**启动时通过有序插件树组合这些能力，并叠加 profile / bundle / patch——无需改源码，即可在配置层定制自己的 Agent。**

### 6.4 四种运行模式

| 模式 | 适用 |
|---|---|
| **Standard** | 通用对话 / 问答（默认） |
| **PTC（Programmatic Tool Calling）** | 让模型用 **TypeScript 组合多步工具调用**，适合复杂工作流、跨工具编排 |
| **Minimal** | 极简、纯模型对话（关闭大部分插件） |
| **Creator** | 自定义 Agent（给开发者最大自由度） |

### 6.5 三个关键转变（这是 dsh 最有价值的部分）

综合百度百科对 DeepSeek Harness 的分析，它标志着三个转变：

| 从 | 到 | 机制 |
|---|---|---|
| 「框架能力」 | **「可治理运行时」** | **自改写运行时 + 沙箱 + fail-closed 设计**，使治理成为动态、可观测的决策引擎 |
| 「日志」 | **「事件-可重放-可审计」** | **事件溯源技术**把 Agent 行为转化为**可完整回放和审计的证据链** |
| 依赖「调参 / 自评」 | **「工程纪律与自动化守门」** | **代码覆盖率、自动化快照回归测试、死代码检测**等机器强制门禁 |

**它要解决的是 Agent 从「能跑」到「敢交付」的治理缺口。**

### 6.6 可观测性

- 每次运行写入**仅追加会话日志**
- **Trajectory 视图**可查看：系统提示词 / 思维链 / 工具调用 / 子 Agent 调度

### 6.7 明确的局限（官方自述）

| 局限 | 说明 |
|---|---|
| **生产环境关键业务** | 官方明确标注「开发者预览阶段，**未来会有破坏性更新**」 |
| **沙箱强度** | 官方文档明确：「**filesystem sandbox 不覆盖网络访问和进程可见性**」，需自建加固层 |
| **非 DeepSeek 模型** | 虽支持 OpenAI 兼容路由，但工具调用格式 / 推理行为 / 上下文限制**需针对每条路由自测** |

## 八 研究型 vs 生产型 Harness

**这是判断一个 Harness 是否「成熟」的核心标准。**

很多 Agent demo 看起来很强，进入生产之后变得笨重、昂贵、难调。**原因是研究型 harness 和生产型 harness 的目标不同。**

| 维度 | **研究型 Harness** | **生产型 Harness** |
|---|---|---|
| **目标** | 拉高任务成功率上限 | **在成本、延迟、安全约束下稳定交付** |
| **状态** | transcript、本地文件、临时 progress file | **外部 session log、checkpoint、event history** |
| **上下文** | 尽量多给模型 | **更小、更高信号的上下文集合** |
| **工具** | 能接多少接多少 | **动态发现、按需加载、权限收敛** |
| **多 Agent** | 优先尝试并行和角色分工 | **只在高价值、可并行任务中启用** |
| **安全** | 人工确认、简单隔离 | **sandbox、proxy、vault、scoped credential** |
| **失败恢复** | 重跑或人工接管 | **resume、replay、checkpoint、trace** |
| **评估** | 看最终 demo 是否完成 | **outcome eval、trace analysis、regression suite** |
| **迭代方式** | 加模块、加策略、加 Agent | **做 ablation，删掉过时策略** |

### 一条关键概念：Harness 策略会被模型升级「重新定价」

> 今天 planner 有用，明天可能拖慢系统；今天 evaluator 能救错，明天可能只是在增加成本；今天 context reset 是必要补丁，明天可能成了无用复杂度。

**所以生产型 harness 不能只会加东西，也要能删东西。** 每次模型升级，都应该重新测：

- memory 是否有收益
- critic 是否有收益
- tool search 是否有收益
- multi-agent fanout 是否值得
- context reset 是否还需要

> **Agent 工程里，能删掉过时复杂度，是一种很实际的能力。**

## 九 Harness 设计的五组取舍

**没有标准答案，只有取舍。**

### 9.1 单 Agent 还是多 Agent

> 一个常见误区，是**一上来就上多 Agent**。但多 Agent 从来不是白拿的收益——它会带来**额外路由开销、上下文损失、角色边界设计和更多失败点**。
>
> **更稳的顺序通常是：先把单 Agent 做通，再把明显超载的职责拆出去。**

### 9.2 ReAct 还是 Plan-and-Execute

| | 优点 | 类比 |
|---|---|---|
| **ReAct** | 灵活，边想边做 | 即兴驾驶 |
| **Plan-and-Execute** | 稳定，先摊开路线再逐段执行 | 先画施工图再开工 |

> **任务越长、代价越高、回滚越麻烦，越值得把计划层显式拿出来。**

### 9.3 上下文到底怎么管

> 很多团队的默认思路是「窗口大一点就好了」。**但窗口变大，不代表中间位置的信息就更容易被利用。**
>
> 成熟系统关心的是**信号密度**：哪些信息必须常驻、哪些只在需要时检索、哪些旧 Observation 应该折叠、哪些总结必须进入长期记忆。

### 9.4 验证交给谁

> 让生成器自己验自己，速度很快。**问题是它通常也最容易放过自己。**
>
> 所以只要任务一旦碰到代码、页面、部署、数据写入这些「能真测」的地方，**外部验证几乎都是值得补上的**。

### 9.5 Harness 到底要多厚（最难的一组）

> Harness 太薄，很多稳定性问题只能靠模型自觉。
> Harness 太厚，系统会变得笨重、昂贵，而且**和当前模型强绑定，模型一升级，很多脚手架可能反而成了负担**。
>
> **好的 Harness 要一边补承重结构，一边等待模型进步后再把不再承重的部分删掉。**

### 9.6 一条量化经验

> **当工具数超过 10 个且职责重叠时，模型的调用质量会明显下降。**
>
> 如果不是明确必要，更稳的做法是**只暴露当前步骤会用到的最小工具集**。

## 十 AGENTS.md / Spec / Skills 也是 Harness

**这一节连接了本会话前几轮的所有发现。**

> **很多人以为 Harness 只是 Runtime，其实不是。Harness 真正吃力的地方，往往是那些把团队经验外移成工件的层。**

这三层解决的是同一个问题：**尽量缩小「必须靠模型临场发挥」的面积。**

| 层 | 回答什么 | 类比 |
|---|---|---|
| **`AGENTS.md`** | 这个仓库怎么读 / 哪些规则先于当前任务 / 哪些入口才是标准入口 / 改哪些东西必须联动哪些检查 | **仓库地图** |
| **Spec** | 这次到底要交付什么 / 哪些边界不能越 / 什么叫「做完了」 / 哪些验收条件必须先对齐 | **本轮任务契约** |
| **Skills** | 这类问题以后通常怎么做 / 哪些步骤高频而稳定 / 哪些检查和脚手架值得复用 | **团队程序性记忆** |

**它们合起来在做同一件事**：

- 把知识从**聊天记录**里搬出来
- 把规则从 **review 口头提醒**里搬出来
- 把经验从**某个资深工程师脑子里**搬出来
- 把验证从「我觉得差不多」搬到**系统动作**里

### 这条线接回前几轮的发现

**上一轮社区调研的最高分诉求是 `AGENTS.md` 跨工具标准（Claude Code #6235，4,060 👍）**——现在可以理解它为什么是「最强的单一诉求」：**它不是配置文件偏好问题，它是 Harness 的一层。**

**第七轮发现的 Agent Skills 生态（102 家官方厂商、数千个官方 skill）** 同理——**Skills 是 Harness 的程序性记忆层。**

> **门槛在于：软件工程能不能被改造成对 Agent 可见、可验证、可执行的系统。**

### 两个新衍生概念

| 概念 | 定义 |
|---|---|
| **Coordination Engineering（协调工程）** | Harness Engineering 延伸出面向团队协作的范式：在 Harness SDK Agent 个体能力之上**增加协调层**，解决团队编排、任务调度、通信协议等系统工程问题 |
| **Runtime Harness 阶段** | 综述把大模型系统演进概括为 Prompt Engineering → Context Engineering → **Runtime Harness**（2025 至今） |

### 工业场景的一条特殊洞察

> 工业实践强调**双模双轨协同**：**大模型负责语义理解、任务拆解和决策调度**，而**小模型与工业机理模型承担高确定性执行**——以应对工业场景对确定性、安全性、实时性和可追溯性的严苛要求。

**这条对任何高可靠性场景都有借鉴意义**：不是所有环节都该交给概率模型。
