## 二、硬件账本（为什么是这几个数）

- **RX 9060 XT 16GB（Navi 44 / RDNA4，gfx1200-1201）**：128-bit GDDR6，带宽约 320 GB/s。Vulkan 下 Windows 实际可分配显存约 15.0–15.5 GB。
- 显存要分三份：**权重 + KV cache + 计算缓冲（约 0.6–1.0 GB）**。
  - 稠密 27B 开 16k 上下文，KV 约 2.5–4 GB → 权重必须 ≤ 12 GB 才安全。所以 27B 只能 IQ3_S/Q3_K 档，`Q4_K 16.81GB` 和 `UD-Q4_K_XL 17.38GB` 会溢出，稠密模型一溢出就掉到 3–5 tok/s，**不要碰**。
  - Gemma-4-12B 是滑窗注意力，长上下文 KV 增长慢，Q8_0（12.67GB）还能留 2GB 开 32k。
- **32GB DDR4 的意义**：只对 **MoE** 有用。35B-A3B 每 token 只读约 3B 激活参数，把一部分专家层放内存（约 50 GB/s），损失远小于稠密模型同样操作。这就是 C 档能成立的原因。
- **5800X3D**：96MB 3D V-Cache 对 llama.cpp 的 prompt processing（prefill）帮助明显，长 prompt 首字延迟会比你预期好；生成阶段仍受显存带宽限制。

## 0. 先做决策：Vulkan vs ROCm

| | **Vulkan (Mesa RADV)** | **ROCm (HIP)** |
|---|---|---|
| 安装成本 | 装个驱动包就行 | 装 ROCm 运行时（几 GB）+ 编译 |
| RDNA4 (gfx1200) 支持 | 2026 年的 Mesa 已成熟 | 需 ROCm 7.x / TheRock，版本对不上就 fallback |
| 生态兼容 | llama.cpp / KoboldCpp / LM Studio 全支持 | 主要是 llama.cpp / vLLM |
| 性能 | 大模型 decode 接近 ROCm | prefill 略强，长 prompt 有优势 |
| 崩了怎么查 | `vulkaninfo` + dmesg，好查 | HSA 报错信息晦涩 |

**建议：先用 Vulkan 跑通并留下基准数字，再决定要不要为那 10% prefill 去装 ROCm。** 下面两条路径都给。

### 1.2 关键一步：放大 GTT（跑 MoE 混合卸载必须）

Linux 上“专家层放内存”走的是 **GTT（共享显存）**，默认只有内存的一半左右，35B-A3B 那种 21.7GB 权重会直接报显存不足。改内核参数：

```bash
sudo nano /etc/default/grub
# 在 GRUB_CMDLINE_LINUX_DEFAULT 里追加（示例：GTT 上限 24GB）
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash amdgpu.gttsize=24576 ttm.pages_limit=6291456"
```

> `amdgpu.gttsize` 单位 MB；`ttm.pages_limit` 单位 4KiB 页（6291456 页 = 24GB）。两个要一起改，且**别超过物理内存的 70%**，否则容易 OOM。

```bash
sudo update-grub && sudo reboot
# 验证
cat /sys/module/amdgpu/parameters/gttsize   # 应显示 24576
```

### 1.3 BIOS

开 **Re-Size BAR / Smart Access Memory**。RDNA4 上这直接决定大模型能不能整块映射进显存。

## 3. 路径 B：ROCm（可选，想要更强 prefill 再上）

Ubuntu 26.04 刚发布时，AMD 官方 `amdgpu-install` 的支持矩阵往往还滞后。按优先级选：

**结论先说：不会，前提是你别装错“那两样东西”。** ROCm 是计算栈，不碰图形栈；但 AMD 的安装脚本默认会顺手把图形栈也换掉——这才是游戏挂掉的真实原因。

---

## 一、为什么 ROCm 本身不影响游戏

一张卡上跑着两套互不干扰的东西：

```
内核 amdgpu 驱动
├── DRM render node (/dev/dri/renderD128) ── Mesa RADV (Vulkan) / RadeonSI (OpenGL)  ← 游戏走这里
└── KFD 计算队列 (/dev/kfd)               ── ROCm HIP runtime / rocBLAS / MIOpen     ← LLM 走这里
```

- **Mesa 仍然是唯一的图形驱动**。Steam/Proton、原生 Vulkan 游戏、桌面合成器全都还在用 `radeon_icd.x86_64.json`（RADV）。
- ROCm 用户态只通过 `/dev/kfd` 提交计算任务，**不接管显示、不接管 Vulkan**。
- `HSA_OVERRIDE_GFX_VERSION` 这类变量只在你的 shell 里生效，出了终端就没了。

所以：**ROCm userspace ≠ 替换显卡驱动**。真正危险的是下面两个东西。

---

## 二、四个真实的踩坑点（按危险程度排序）

### ⚠️ 1. `amdgpu-dkms` —— 唯一能让机器黑屏的东西

`amdgpu-install` 不带参数时默认 `--usecase=all`，会装上 **out-of-tree 的 amdgpu-dkms 内核模块**，把 Ubuntu 26.04 自带的内核 amdgpu 顶掉。26.04 内核很新，DKMS 编译失败是高频事件，失败后驱动不加载 → 直接黑屏或掉到 llvmpipe。

**规避**：永远带 `--no-dkms`，且只装 rocm：
```bash
sudo amdgpu-install --usecase=rocm --no-dkms
```
装完立刻确认没被塞进来：
```bash
dpkg -l | grep -i amdgpu-dkms      # 必须为空
lsmod | grep amdgpu                # 应该是内核自带模块
```

### ⚠️ 2. `--usecase=graphics` / `all` —— 会装第二个 Vulkan ICD

这条路会装 AMD 的专有 Vulkan（amdvlk / amdgpu-pro 的 `vulkan-amdgpu-pro`）。一旦 `/usr/share/vulkan/icd.d/` 里出现两个 ICD，游戏可能挑中错的那个 → 卡顿、闪退、着色器缓存反复重建。

**规避 + 检查**：
```bash
ls /usr/share/vulkan/icd.d/
# 期望只有: radeon_icd.x86_64.json
# 若出现 amdvlk_icd / amd_pro_icd → 卸载：
sudo apt remove --purge amdvlk vulkan-amdgpu-pro
```

### ⚠️ 3. ROCm 的 apt 源会把 `libdrm-amdgpu1` / `llvm` 降级

ROCm 仓库里带的 `libdrm` 常常比 Ubuntu 26.04 的新版旧。加源后一次 `apt upgrade` 就可能把 Mesa 依赖的 libdrm 降级，症状是**桌面能进但游戏全崩、`vulkaninfo` 报 ICD 加载失败**。

**规避**：加 apt pinning，把 Mesa/libdrm 钉死在 Ubuntu 源：
```bash
sudo tee /etc/apt/preferences.d/99-keep-mesa <<'EOF'
Package: libdrm* mesa-* libgl1-mesa* libvulkan*
Pin: release o=Ubuntu
Pin-Priority: 1001
EOF
```

### ⚠️ 4. 显存争抢（不是驱动冲突，但体感最明显）

16GB 显存，llama-server 常驻吃着 10–13GB，再开 3A 游戏 → 游戏爆显存、贴图糊、掉帧。这跟 ROCm 无关，跟“服务没停”有关。

**规避**：玩游戏前 `systemctl stop llama-*`；或用 llama-swap 的 idle 超时自动卸载模型（`ttl` 设 300 秒，闲置 5 分钟自动释放显存）。

## 三、三种方案，按“对游戏的安全度”排

| 方案 | 游戏风险 | 装法 | 适合 |
|---|---|---|---|
| **A. 宿主机最小 ROCm** | 低（守好上面 4 条） | `--usecase=rocm --no-dkms` + apt pinning | 想长期用 ROCm 跑 LLM，也常玩游戏 |
| **B. 容器化 ROCm** | **零** | 宿主只装 Mesa，ROCm 全在 `rocm/` 镜像里 | 最推荐。宿主环境一根手指都不动 |
| **C. 不装 ROCm，继续 Vulkan** | **零** | 什么都不用做 | 只要 decode 速度，不追 prefill |

**我的建议：先选 B 或 C。** 你这台是“游戏机 + 本地 LLM”双用途，宿主机越干净越好。RDNA4 上 Vulkan 的 decode 速度已经接近 ROCm，ROCm 的优势主要在长 prompt 的 prefill——为这个去动系统驱动栈，性价比不高。

方案 B 示意（宿主完全不动）：
```bash
# 宿主只放行设备，不装任何 ROCm 包
docker run --rm -it \
  --device=/dev/kfd --device=/dev/dri \
  --group-add video --group-add render \
  --security-opt seccomp=unconfined \
  -v /srv/models:/models \
  rocm/llama.cpp:latest \
  -m /models/gemma-4-12b-heretic-Q6_K.gguf -ngl 999 -c 32768
```

## 四、装完必做的 5 条验证（确认游戏栈没被动）

```bash
# 1. Vulkan 还是 RADV？
vulkaninfo --summary | grep -i driverName        # 期望: radv

# 2. ICD 只有一个？
ls /usr/share/vulkan/icd.d/                       # 期望: radeon_icd.x86_64.json

# 3. OpenGL 还是 Mesa？
glxinfo | grep "OpenGL renderer"                  # 期望: AMD Radeon RX 9060 XT (radeonsi, ...)

# 4. 内核模块还是原生的？
modinfo amdgpu | grep -E "^(filename|version)"    # filename 应在 /lib/modules/$(uname -r)/kernel/

# 5. ROCm 只多了一个设备节点？
ls -l /dev/kfd /dev/dri/renderD128                # 两个都在，且 kfd 属于 render 组
```

**5 条全过 = 游戏栈完好。** 任何一条不对，立刻回滚（见下）。

## 五、回滚（30 秒恢复）

```bash
sudo apt purge -y 'rocm*' 'hip*' 'hsa*' amdgpu-dkms
sudo apt autoremove --purge -y
sudo rm -f /etc/apt/sources.list.d/rocm*.list /etc/apt/preferences.d/99-keep-mesa
sudo update-initramfs -u
sudo reboot
```

装之前**先做快照**（Timeshift 或 btrfs snapshot），比任何回滚命令都可靠——万一黑屏进不去系统，能 1 分钟退回。
