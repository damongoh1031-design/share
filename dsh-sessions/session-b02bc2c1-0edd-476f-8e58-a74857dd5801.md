## 一、先拆成三个目标，它们共用一条采集管道

| 目标 | 时间维度 | 产出 | 难度 |

多数人只做第一件就放弃了，因为**按时间线性摘要读起来像流水账**。真正有用的是第二、三件，而它们都建立在“消息已经入库”这个前提上。

## 二、平台能不能读到消息：动手前必须先确认

这是最容易出问题的地方，先看这张表：

| | Telegram | Discord |
|---|---|---|
| 读全量消息 | 默认**读不到**。需要 BotFather `/setprivacy` → Disable，**或**把 bot 设为管理员 | 需要在开发者后台开启 **Message Content** 特权 intent |
| 门槛 | 无 | 2026-06-10 起阈值从“100 个服务器”改为“**1 万独立用户**”，低于此可自助开启，无需审核（[官方说明](https://support-dev.discord.com/hc/en-us/articles/40281523410967-Changes-to-Private-Intent-Access-for-Discord-Apps)） |
| 能读入群前的历史吗 | **不能**。Bot API 无此能力 | **能**。有 Read Message History 权限即可翻历史 |
| 因此采集架构 | 必须**常驻进程**接收，或用 userbot 拉历史 | 可以**纯定时任务**，每天拉一次，不常驻 |

Telegram 的两个细节必须知道：

1. **隐私模式是“入群那一刻”的快照**。改完设置必须把 bot 踢出群再重新拉进来，否则不生效。
2. **历史回填有两条路**：① 用 Telethon 登录一个**小号**当 userbot 拉历史（有封号风险，别用主号）；② 让管理员用官方导出（Settings → Advanced → Export chat history，选 JSON）——**冷启动建经验库时这条路最稳、零风险**，一次性把几年的聊天记录喂给模型。

另外两个容易被忽略的问题：Telegram 论坛群的 `message_thread_id`、Discord 的**线程和论坛频道**。如果不单独枚举，它们会漏掉 30%~50% 的有效内容。

## 五、决定摘要“能不能看”的六个细节

1. **先聚类，再摘要**。按 reply 链 + 时间窗 + embedding（bge-m3 / text-embedding-3-small）+ HDBSCAN 聚成话题，每个话题给模型单独写。日消息 < 800 条时，可以偷懒：把「时间+作者+前 80 字」直接丢给模型让它分组，一次调用搞定。
2. **采样而不是全量**。长贴只取「首条 + 高互动消息 + 结尾」，控制在 200 字/条。这一步能把 token 降 60%，且摘要质量不降。
3. **结构化输出**：`{title, summary, decisions, open_questions, resources, heat, msg_ids}`。有了 `decisions` 和 `open_questions`，日报才从“聊天记录”变成“值班交接”。
4. **两段式模型**：便宜模型做分类/抽取/去重，强模型只写最终 8 个话题。成本能压到 1/5。
5. **防幻觉硬约束**：提示词里写死“只允许陈述给定消息中的事实；不确定写‘未确认’；禁止编造链接和人名”，并校验输出 JSON 里的 `msg_ids` 必须存在于输入。
6. **三种粒度**：日报（24h）、周报（7 天 rollup，只写“本周新增结论/变化”）、经验库（增量更新）。日报看热闹，周报看趋势，经验库才是资产。

---

## 六、社区经验库怎么做（这是真正稀缺的部分）

不要试图“总结所有聊天”，而是**抽取可复用的单元**：

- **Q&A 对**：有人问、有人答且被认可（表情/后续确认）→ 一条 FAQ
- **结论**：`decisions` 里出现过的 → 一条“已定事项”
- **资源**：链接 + 一句话说明 + 谁推荐的
- **坑/反例**：“别用 X，因为 Y” → 一条警告

写入时用 RAG 检索已有条目（embedding top-k），让模型三选一：**新建 / 合并进已有条目 / 标记为“存在分歧”**。每条都带：来源消息链接、首次出现时间、最后确认时间。**超过 6 个月未再被验证的条目标“待复核”**——社区经验会过期，这是多数知识库烂掉的原因。

冷启动就用第二节说的官方导出，离线跑一次，直接产出初始 100~300 条，比从今天开始攒快得多。

Discord 还有个现成补充：**Answer Overflow** 可以把 help 频道索引成公开可搜索的网页，等于半个经验库，可以先接上再自建。

## 一、小群为什么反而更好办

| 大群的麻烦 | 小群（几十人、日活几十条） |
|---|---|
| 一天几千条，必须分片 / map-reduce | 一天几十条，一次 LLM 调用就装完 |
| 需要 Postgres/Redis 撑住 | SQLite 单文件就够，甚至可以不用数据库 |
| 要常驻进程实时收 | 定时任务每天跑一次即可 |
| 长消息要预压缩 | 基本没有超长消息 |

所以你之前看到的那套 `group-digest/`（并查集串回复链、超预算 map-reduce、热度排序）**对小群是过度设计**。它现在能跑，但你可以先走下面更懒的路，跑不顺再回来。

唯一在小群**更有价值**的是"跨天趋势"：人少的时候，一个话题往往拖 3–5 天（今天提问 → 明天有人回 → 后天给结论），"延续「X」第三天"这种标记比大群更有用。

## 二、三条从简到繁的路线

### 路线 A：零代码 —— 官方导出 + 丢给 AI（最懒，推荐先试一周）

Telegram Desktop / 手机端都有 **Export chat history**，支持**选定时间范围**、**只导出文本**，产出 `result.json`（每条消息带 `id`）和 HTML。

关键是：**导出 JSON 里保留了 `message_id`，可以自己拼回原消息链接**：

```
https://t.me/c/<chat_id 去掉 -100 前缀>/<message_id>
```

（私有群用 `t.me/c/`，公开频道用 `t.me/<username>/`。这个拼法就是 `tg-digest-userbot` 项目里 `link_base` 的实现。）

所以流程是：

1. 每天导出昨天的记录（勾掉媒体，只要文本）
2. 把 JSON 丢给任意聊天模型，附一句：「按话题分组，每条结论后面附上 `https://t.me/c/xxx/<id>` 链接」
3. 完事

**成本：每天 2 分钟手工 + 一次 AI 对话。零部署、零 token 之外的开销。**

**代价**：手工、无跨天记忆（每天你得自己记得昨天聊了啥，或者把昨天的摘要一起贴进去）、拼链接要靠模型老实抄数字。

---

### 路线 B：半自动 —— 只导出、不调 AI

就是 [`pavnxet/tg-digest-userbot`](https://github.com/pavnxet/tg-digest-userbot) 那套思路：Telethon **只读**拉消息 → 写成结构化 JSON → **内嵌 `ai_instructions`**，它自己一个 token 都不花，你拿去粘给任意模型。

带一个 owner-only 控制 bot：`/run today|yesterday|6h|since-last`、`/find` 本地检索、定时调度。

适合你想要路线 A 的手感、但不想每天点导出按钮。同类的还有 `mooreslaws/tg-digest`（输出能直接适配 Notion / Obsidian / Logseq，你笔记在哪它就往哪写）。

---

### 路线 C：开箱即用 —— 现成 bot

- **`nekomeowww/insights-bot`**（288★，Go）—— 最接近成品。`/recap` 手动回顾、`/subscribe_recap` 每天私聊推送你群里的摘要，输出自带 `话题 → 参与人 → 讨论点 + 原消息链接 → 结论`。**代价：要 Postgres + Redis + OpenAI key。**
- **`belaytzev/Telebrief`**（Python，活跃维护）—— Telethon 采集 + 自己的 bot 投递，AI 可用 **Ollama 本地模型（零成本）**，SQLite 存储，还内置 MCP server。**代价：输出语言只有 en/ru/es/de/fr，没有中文。**
- **`asukaminato0721/telegram-summary-bot`**（201★）—— Cloudflare Worker + D1 + **Gemini 2.5-flash，作者称成本 0**，支持 CJK。需自部署。

注意这三家**都不做"趋势"**：没有跨天议题匹配、没有延续/新增标记、没有热度排序。它们只是"今天这段消息的话题摘要"。

## 三、诚实对比：「转发给 AI」丢了什么

| | 多选转发给 AI | 导出 JSON 给 AI | 现成 bot | 自研 group-digest |
|---|---|---|---|---|
| 原消息链接 | ❌ **断了**（转发后是新消息，原 id 丢失） | ✅ 可拼 | ✅ | ✅ |
| 跨天趋势（延续/🆕） | ❌ | ❌ 要手工贴昨天摘要 | ❌ | ✅ |
| 每日自动 | ❌ | ❌ | ✅ | ✅ |
| 部署成本 | 0 | 0 | 中（PG+Redis） | 低 |

**最容易被忽略的就是第一行**：Telegram 里多选消息转发，收件方看到的是一堆新消息，`message_id` 全变了，你再也点不回原文。所以如果"附上链接"是你的硬需求，**至少要走导出 JSON，别走转发**。

## 先说一个判断：你的 RSS 阅读器已经做了 80% 的事

「每天更新后离线保存」——FreshRSS / Inoreader / NetNewsWire / Reeder 基本都在做，只是各家保留期不同（FreshRSS 本地无限，Inoreader 免费版有限）。

所以你真正缺的**不是归档，是这两件**：
1. **永久归档**：文章下线/改版/404 了还在你手上（阅读器不保证这个）
2. **语义检索**：按意思搜，而不是按关键词

这两层要分开选工具。

---

## 第一层：离线归档（保原文，防链接腐烂）

### ArchiveBox（28843★，Python，更新 2026-10-22）

唯一真正做「网页级永久保存」的开源方案。官网明确支持 RSS：

```bash
# 每天拉一次 feed
archivebox schedule --every=day --parser=rss --tag='news' 'https://news.example.com/feed.xml'

# 查看任务
archivebox schedule --show
```

每个 URL 存成 **HTML + PDF + PNG 截图 + TXT + JSON + WARC + SQLite**（视频源还会存 MP4）。是文件，不是数据库 blob，可以直接用文件系统工具翻。

搜索后端三选一（`SEARCH_BACKEND_ENGINE`）：
- `sonic`（默认）— Rust 写的轻量索引，10 万+ 快照仍是微秒级，支持 Unicode 和模糊匹配
- `sqlite` — FTS5，无额外进程，中等规模够用
- `ripgrep` — 纯文件扫描，永远准确但大集合慢

```bash
archivebox config --set SEARCH_BACKEND_ENGINE=sqlite
archivebox update --index-only
archivebox search '某个词'
```

**但 ArchiveBox 没有 embedding**，它的搜索全是关键词/子串。所以语义检索得自己加一层。

## 第二层：嵌入检索（按意思搜）

### 模型选型（中文场景，2026 现状）

| 模型 | 体积 | 维度 | 上下文 | 许可 | 适合你吗 |
|---|---|---|---|---|---|
| **bge-m3** | 568M / 1.2GB | 1024 | 8192 | **MIT** | ✅ **首选**。一个模型同时出 dense + sparse（类 BM25）+ ColBERT 多路召回。100+ 语言。 |
| **Qwen3-Embedding-0.6B** | 1.5GB（Q4_K_M 约 800MB） | 1024（可压到 32） | 32K | Apache-2.0 | ✅ CPU/小显存首选，MTEB-eng-v2 **70.7**，Ollama 一把梭 |
| Qwen3-Embedding-4B | 9GB | 2560 | 32K | Apache-2.0 | 有 3060/4060 级别显卡时上，74.6 |
| Qwen3-Embedding-8B | 17GB | 4096 | 32K | Apache-2.0 | MMTEB **70.58 开源第一**，17GB 显存才考虑 |
| gte-Qwen2-7B-instruct | 15GB | 3584 | 32K | Apache-2.0 | 老牌中英双语，C-MTEB **72.05** |

**结论：8GB 显存以下 → bge-m3（要混合检索）或 Qwen3-0.6B（要省事）。**

⚠️ **两个坑**：
- `jina-embeddings-v3` 和 `NV-Embed-v2` 分数很高，但都是 **CC-BY-NC-4.0，禁止商用**。个人自用无所谓，别拿去做产品。
- **换模型 = 全库重算**。所以一开始就定死，别来回换。Qwen3 系列迭代快，这也是个隐性成本。

### 向量库

**sqlite-vec**（8204★）就够了——单文件、零服务进程、SQLite 扩展。

别一上来就 Qdrant/LanceDB/Chroma：你这个是「几千到几万篇文章」的量级，sqlite-vec 加一层 FTS5 做混合检索完全够，而且**备份就是复制一个文件**。

## 中文特有的三个坑（没人提但会咬你）

1. **分词**：SQLite FTS5 默认 `unicode61` 分词器对中文几乎无效。要中文关键词检索，得用 `trigram` 分词器（`CREATE VIRTUAL TABLE ... USING fts5(..., tokenize='trigram')`）——LM Studio 的 rss-rag-cache 插件就是这么干的，专门建两个 FTS 索引（trigram 给 CJK，porter unicode61 给英文）。**embedding 天然不受这个问题影响**，这也是语义检索在中文场景更值钱的原因。
2. **RSS 只有摘要**：大量 feed 只给前两百字。必须做全文抽取（`trafilatura` 是现在的默认选择，Readability 老一点）。或者用 RSSHub（400+ 源）补全。
3. **重复内容**：同一篇被多个源转载，语义搜索会返回一堆一样的。需要 SimHash 去重（64 位 SimHash over 3-gram）。
