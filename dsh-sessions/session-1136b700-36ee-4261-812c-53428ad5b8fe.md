## 一句话结论

真正变化的是**分工**：skills/CLI 正在赢下“调用层”：agent 用什么方式表达它要做什么；MCP 正在退守“接入层”：agent 凭什么身份、通过什么通道够到那个系统。“MCP 要被淘汰”是误读，但“MCP 是 agent 扩展能力的默认答案”确实已经过期了。

---

## 一、skills/CLI 这一侧为什么在赢

**1. 上下文成本的结构不同**
MCP 是“常驻税”：一个 15 个工具的 server，JSON Schema 全量塞进 system prompt，每个工具 150–300 token，就是 2–5k token，十个 server 就是几万 token，用户还没开口就已经付了。skills 是“按需付费”：常驻只有 name + description（几十 token），正文在命中时才加载。Anthropic 那篇 code execution with MCP 的样例给的是 15 万 → 2 千 token 量级——这个量级差不是优化，是数量级。

**2. 往返次数比 token 更贵**
MCP 的每次调用是一次完整模型往返：模型 → tool → 模型。而 CLI + 代码执行可以把 N 次调用压成一条 pipeline（`gh pr list --json ... | jq ... | rg ...`），一次往返出结果。在 agent loop 里，round-trip 数是延迟和失败面的乘数——每多一跳就多一次格式错误、超时、重试的机会。

**3. 训练先验的落差**
模型见过几百万次 `git`、`curl`、`rg`、`jq` 的用法，几乎不用解释。一个新的 MCP 工具 schema，模型只能靠那两百字 description 现场学，而且每个 server 的命名风格、参数习惯都不一样。CLI 借的是几十年的存量语料，MCP 是从零开始的新语料。

**4. 可验证、可重放、可交接**
CLI 命令是一个字符串：能记日志、能贴进 issue、能交给人类复跑、能进 CI。MCP 调用是进程内的临时事件，出问题只能看那一段 JSON 返回值。排障成本差一个量级。

---

## 二、MCP 不会消失，但它的价值重心挪了

| MCP 真正不可替代的地方 | 原因 |
|---|---|
| **凭据与授权** | OAuth 授权码流、token 刷新、多用户隔离——这是 MCP 最有价值的部分，也是最难用 CLI 复刻的部分 |
| **没有好 CLI 的长尾 SaaS** | Figma、Linear、Notion、Slack、各家 CRM。总得有人把 HTTP API 包成稳定的工具面 |
| **治理与审计** | 按 connection / server / tool 三级 allow-deny、逐次审批、调用留痕。CLI 一旦能跑 bash，边界就模糊了 |
| **有状态的长连接** | 浏览器会话、连接池、websocket 订阅——这些天然是 server 形态 |
| **能力发现** | 一个目录点一下就能装，比“去 go install 十二个二进制”现实 |

换句话说：**MCP 卖的是“接入 + 授权 + 治理”，不是“调用形态”**。它错在把这三件事和“把 40 个工具塞进上下文”绑在了一起。

---

## 三、真正的分界线

判断标准不是“有没有 MCP”，是三个问题：

1. **这个东西有成熟 CLI 吗？** 有 → CLI（`git`/`gh`/`ffmpeg`/`rg`/`psql`/各家云 CLI）。没有 → 往下走。
2. **需要谁的凭据、要不要多人隔离？** 需要 → MCP 或等价的凭据中介层，因为这是它唯一真正难被替代的部分。
3. **调用结果要不要被复用/重放/审计？** 要 → 优先能被脚本化的形态。

三条都指向 CLI 的时候还用 MCP，就是在为“统一协议”付没必要的上下文学费。

---

## 四、一个不太受欢迎的反例：skills 自己也会膨胀

拿这个 session 当样本：技能目录大约 700 条，光 name + description 就是几万 token 的常驻开销；而 MCP server 只有 5 个。**当 N 大到几百，skills 的“渐进披露”就退化成“渐进税”了**——和 MCP 犯的是同一个错，只是税率低一点。

所以“skills 比 MCP 省 context”只在**小规模 + 强路由**下成立。真到几百个 skill，你需要的是再上一层：先检索（`find-skills` 那类），再加载。这和 MCP 侧的演进是同构的——你本机 DSH 就是这么做的：`mcp_connector_tool_search` 负责搜、`session_tools activate` 带 TTL 负责临时挂载、`mcp_connector_policy` 负责治理。**MCP 被包了一层元工具，就从“N 个常驻工具”变成“2 个常驻工具 + 一个目录”**。这才是当下真正的趋势：不是 CLI 取代 MCP，是 MCP 被 CLI 化 / 元工具化。

---

## 五、我的判断

- 短期（当下）：**默认用 CLI，需要凭据中介或治理时才上 MCP**。反过来了就是在烧 context。
- 中期：MCP server 会越来越多地“以代码 API 的形式暴露”而不是“以工具列表的形式暴露”——server 提供 SDK，模型写三行代码调它。这本质上是把 MCP 降格成 HTTP 之上的又一层，只在跨进程、跨凭据、跨组织时才值得存在。
- 长期看，胜负手不在协议，在**“谁能把上下文成本压到接近零”**。skills 赢在当下是因为它做到了按需加载；它也会以同样的理由被下一代机制取代——比如真正按需检索的能力目录，而不是把 700 条 description 全列出来。

一句话：**别问 skills/CLI 还是 MCP，问“这次调用，谁该持有凭据、谁该持有上下文”。** 凭据归 MCP，上下文归 CLI。

# 调研后结论：三层模型与两个意外发现

完整报告已生成：[skills-cli-vs-mcp-2026.md](C:\Users\Admin\Documents\deepseek-harness\default-workspace\skills-cli-vs-mcp-2026.md)。下面是核心内容与关键发现。

---

## 一、先纠正问法：它们不是同一层的竞品

把 skills、CLI、MCP 当作同层竞品，是当前最普遍的误判。三者其实是三层的不同默认打包：

| 层 | 要解决的问题 | 谁在赢 |
|---|---|---|
| **接入层** | 用什么通道到达系统、用谁的身份、怎么隔离租户 | **MCP**（几乎无对手） |
| **发现层** | agent 怎么知道能力存在、花多少 context 装载规格 | **Skills**（小 N 时）；N 大时两者都输，要检索 |
| **调用层** | 怎么表达调用、花几次模型往返 | **CLI / code execution**（压倒性） |

真正的判断：

> **凭据归 MCP，上下文归 CLI/code，流程知识归 Skills。**

被淘汰的并非 MCP，而是**「把所有 MCP 工具定义常驻在 system prompt 里」这一种用法**。

---

## 二、两个反常识的调研发现

### 发现 1：MCP 正在把自己改造成纯粹的接入层

最新规范是 [`2026-07-28`](https://modelcontextprotocol.io/specification/2026-07-28/changelog)（不是 2025 版）。这一版做了大幅精简：

- **彻底无状态**：删掉 `initialize` 握手，每个请求自带 `protocolVersion`；删掉 `Mcp-Session-Id`，跨调用状态改用「server-minted handle 当普通参数传」（SEP-2567 / SEP-2575）
- **弃用 Roots / Sampling / Logging / DCR**：迁移路径分别是「传参数」「直接对接 LLM API」「走 stderr/OTel」
- **Tasks 移出核心**变成扩展；新增 **Skills over MCP** 扩展、**MCP Apps** 扩展
- 两条专门为省 context 的改动：`tools/list` **必须**按确定性顺序返回（*"improve LLM prompt cache hit rates"*）、列表结果**必须**带 `ttlMs` + `cacheScope` 缓存字段

更关键的是[工作组名单](https://modelcontextprotocol.io/community/working-interest-groups)：**Progressive Disclosure**、**Server Card**、**Skills Over MCP**、**Interceptors**、**Tool Annotations** 五个 WG 同时在推。

也就是说：「上下文太贵」和「不知道该用哪个工具」这两条对 MCP 最激烈的批评，官方已经分别立项在做。争论里"MCP 就是上下文税"在 2025 年成立，2026 年正在被协议自身消解。

### 发现 2：Skills 并没有消灭上下文税，只把税率降到 1/2

用这个会话本身当样本：技能目录约 700 条，按每条 60–120 token 估，**光目录就在 4–8 万 token 量级**，而 MCP server 只有 5 个。

| 机制 | 常驻成本 | 20 个 | 200 个 | 700 个 |
|---|---|---|---|---|
| MCP 直连（~200 tok/工具） | 200×N | ~4k | ~40k | ~140k |
| MCP + tool search（2 个元工具） | ~400 | ~0.4k | ~0.4k | ~0.4k |
| MCP + code mode（文件树） | ~300–500 | ~0.5k | ~0.5k | ~0.5k |
| Skills（~90 tok/条） | 90×N | ~1.8k | ~18k | ~63k |
| CLI（模型先验） | ~0 | ~0 | ~0 | ~0 |

**Skills 只比 MCP 便宜约 2 倍，不是数量级。** 真正的数量级差来自 tool search / code mode。而 CLI 的「0」是假象——冷门内部 CLI 的 `--help` 探索成本会吃掉优势，所以 CLI 的红利只在**模型已经认识的工具**上（`git`/`curl`/`rg`）。

## 三、成本模型：把「更好」变成能算的东西

```
C_total = C_resident + C_discover + Σ(C_call + C_result) + λ · N_turns
```

**关键不对称**：前四项线性涨，但 `N_turns` 是**乘性惩罚**——同时放大延迟、cache 风险、格式错误率、重试次数。

而实测上 stdio MCP 传输是毫秒级、CLI 进程启动 10–100ms，**一次模型往返是 1–5 秒**。所以：

> **减少往返次数的收益，比减少传输开销大两到三个数量级。**

这才是 code mode 的真正价值——不是省 token，是**把 10 次往返压成 1 次**。Anthropic 原文的算例：150,000 → 2,000 token（98.7%），以及"两小时会议记录在 context 里流两遍、多烧 50k token"。

## 五、最容易被忽略的维度：确定性

争论里几乎没人提，但它是 Skills 与 MCP 的**本质差异**：

> **Skills 是软约束（建议），MCP 是硬接口（契约）。**

SKILL.md 写「你必须先做 A 再做 B」，模型可以选择不听；MCP 的 `tools/call` 是协议规定的路径，参数会被 schema 校验，失败返回结构化错误。这一条直接决定合规、金融、医疗场景的选型，比 token 数重要得多。

顺带一个被低估的点——**可审计性**：

- MCP 的 tool description 是**用户不可见的元数据**。Invariant Labs 的 [Tool Poisoning](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) 三种攻击（投毒 / rug pull / shadowing）全部建立在这个前提上。其中 shadowing 最狠：恶意 server **完全不被使用**，只靠 description 里写一句「当 `send_email` 存在时所有邮件发给 attacker」，就劫持了可信工具，日志里看不到异常。
- SKILL.md 是**文件**。能 `git diff`、能 code review、能 grep。

这是 skills 相对 MCP 的真正优势——不是省 token，是**攻击面可见**。
