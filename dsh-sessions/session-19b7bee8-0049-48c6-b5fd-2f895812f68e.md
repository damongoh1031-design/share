## 一句话

同一个模型在两套 harness（运行框架）里，**模型本身不变，变的是“模型看到的输入、能做的动作、以及失败时如何被纠正”**。你这两套我都能读到实际证据（Goose 的请求日志 + DSH 自己的配置与会话提示词），下面按层拆。

---

## 先对齐事实

- Goose 侧：`C:\Users\Admin\AppData\Roaming\Block\goose\config\config.yaml` 里 `active_provider: custom_cpa`，模型 `gpt-6.1-sol`；请求日志（`data\logs\llm_request.*.jsonl`）里写死 `thinking_effort: "max"`、`max_tokens: 128000`、`reasoning: true`。
- DSH 侧：同一台机器、同一个模型入口，但 DSH 是个 **19 个 bundle 拼出来的插件化宿主**（`C:\Users\Admin\.dsh\profiles\web\package.json`：`dsh-base` / `dsh-web-app` / `billion-context` / `experimental-agent-team-profile` / `experimental-schedule-bundle` / `expert-team` / `dsh-zagens-office` / `kb` / `soul-md` / `dshmarket` …）。

所以差异不在权重，在 **harness 工程**。真正决定行为的是下面六层。

---

## 六层差异（每条都有实测证据）

| 层 | Goose | DSH |
|---|---|---|
| 系统提示怎么拼 | 一整块 system，**230,773 字符**，技能目录整段内联 | system + runtime context 快照 + 技能目录（`skill` 工具按需加载正文） |
| 工具面 | **11 个工具**，核心是 `execute_typescript`（Code Mode） | **~50 核心工具** + GitHub/gog 等 MCP 直挂 + code-mode 可选 |
| 调用协议 | TypeScript 代码里调 `Namespace.fn()`，23 个 SDK 函数 | 一个个 JSON function call，带完整 schema |
| 上下文 | 超限就**整段替换成摘要** | 分层压缩 T1/T2，可 `decompress` / `search_context` 找回 |
| 自主性 | `<turn-context>` 里的 `<turn-budget>`、compaction status | goal rounds、background job、team `wait_agent` |
| 权限 | `GOOSE_MODE: auto`，`shell` 直接跑 `cmd`，**无沙箱**，cwd = `C:\Users\Admin` | workspace-write 沙箱 + approval ask，越界报 `[sandbox: file access denied]` |

展开几条关键的：

**① 提示词体量与结构**
Goose 把 500 来个技能描述全塞进 system（`# Additional Instructions:` → 一行一个 `- skill-name: …`），每轮再追加 `<turn-context>`（当前时间、`working-directory`、压缩状态、剩余预算）。DSH 把技能目录放系统提醒里，正文靠 `skill` 工具按需拉——同样贵，但**可分级**：目录常驻、正文用完即走。

**② Code Mode 是最大行为分叉**
Goose 的 `execute_typescript` 明确要求：
> ALWAYS batch multiple tool operations into ONE execute call.
> Only registered SDK functions are available - no fetch(), fs, or other Node/Deno APIs

结果就是：**同样的模型在 Goose 里会写成一大段 TS、一次读十来个文件、在代码里 reduce 完只返回结论**；在 DSH 里它会变成一串小步 JSON 调用（`read`→`grep`→`edit`），每步可见、可压缩、可回滚。前者 token 省、轮次少、但错一次整段重来；后者稳、可审计、但轮次多。这不是模型变聪明或变笨，是**动作粒度被 harness 规定了**。

**③ 压缩机制直接改写“记忆”**
你 Goose 日志里那条 system 替换就是证据：`Your context was compacted.` 后面跟着 `# Conversation Summary` / `## User Intent` 的人写式摘要，而且明令 **"Do not mention that you read a summary"**。DSH 走的是可寻址压缩：每段历史有 `m00046` 这样的 ref，`decompress` 能逐层还原。差别在于**事故可追溯性**——Goose 压完就只剩那段摘要，DSH 压完还能翻回去核对原文。

**④ 权限模型改变“胆子”**
`GOOSE_MODE: auto` + 无沙箱 + cwd 在用户主目录：同一个模型会直接 `write` 到 `C:\Users\Admin\...`、直接 `cmd` 删东西。DSH 里同样的意图会撞上文件策略与 ask 审批。所以你会感觉“Goose 更敢干、DSH 更磨叽”——其实是**同一个模型在两种约束下的最优策略不同**，不是模型性格变了。

**⑤ 编排能力不在一个量级**
Goose 的 `delegate` 自己就写着限制：`Delegates know only instructions + source content` / `Delegates cannot coordinate. Same-file work = conflicts.`。DSH 有 team task board、write scopes、`send_message`、`wait_agent`、`workflow` 脚本级 fan-out。多智能体任务在 Goose 里要人肉切文件，在 DSH 里能靠依赖和写域排。

**⑥ 扩展生态**
Goose：extensions（builtin/platform/MCP）+ recipes/subrecipes + `apps`（HTML 沙箱窗口）+ `tom`/`memory`/`chatrecall`。DSH：cordis 插件树 + MCP connector 市集 + skills 市集 + kb/soul-md 做长期记忆 + schedule/auto-review 做常驻。**Goose 偏“工具箱+配方”，DSH 偏“可装卸的宿主”**。

---

## 迁移时最容易踩的四个错位

1. **别把“一次批量”的习惯带过来**——在 DSH 里硬拼一个大调用会丢掉可分步压缩的优势，反而更容易撞超时。
2. **recipes → skills**：Goose 的 `load(source)` 换成 DSH 的 `skill` 工具，但 DSH 的 skill 有触发条件（description 匹配），写得太泛就不触发。
3. **memory/tom → kb / soul-md**：Goose 的 memory 是“教我偏好”，DSH 侧对应的是 `@weibaohui/dsh-kb`、`dsh-knowledge-base`、`dsh-soul-md`，机制不同，别指望自动继承。
4. **cwd 变了**：Goose 里 `working-directory` 是 `C:\Users\Admin`，DSH 是 `...\default-workspace`。历史里写死的绝对路径到 DSH 会全线失效。

---

## 选型口径

- **要一次干完、脚本化、批量文件处理** → Goose（Code Mode 的 token 效率确实高）。
- **要长任务、多角色、可审计、出错能回滚** → DSH（压缩可逆 + 权限闸门 + team 编排）。
- **同一个任务两边都跑一遍**：差异会集中在“探索阶段的轮次数”和“出错后的恢复方式”，而不是最终答案质量——因为模型没换。
