一句话回答

DSH 的内核（Agent 循环 + 多模型 + 插件市场 + 会话日志）已经具备工作台的地基，但要达到 Goose / OpenWork / Open WebUI / WorkBuddy 那种「完整工作台」体验，需要补 10 个维度的插件。其中最小可用组合只需 7 个插件就能覆盖 80% 的日常场景。

但要注意：有 5 项能力是插件也补不了的——DSH 是「单人本地工具」架构，而 Open WebUI 是「多用户服务平台」架构，这是设计定位差异，不是插件能填的坑。

Goose 三栏布局 · OpenWork 面向非技术用户的界面

dsh plugin --profile web add dock-base

dsh plugin --profile web add dsh-ui-auth dsh plugin --profile web add @mrweicodes/dsh-permgate dsh plugin --profile web add "github:a23842/dsh-notifier"

顺序很重要：先有认证门禁，再开远程访问。

六、装完之后怎么验证

# 1) 确认已装（应能看到新插件）
dsh plugin --profile web list

# 2) 重启服务让插件生效
dsh web

# 3) 浏览器刷新页面 → 左下角「设置」→ 应出现新插件的配置项

# 4) 出问题先查锁文件（上次异常退出残留会导致插件启动失败）
#    Windows: 删除 %USERPROFILE%\.dsh\**\*.lock 后重启

插件版本兼容性检查

很多插件对 dsh 版本有硬性要求，例如 DSH-better-sidebar 要求 ^0.2.0-rc.2、dsh-wallpaper-engine 要求 0.1.5-rc.1+。装之前先确认：

dsh --version

不满足版本要求的插件装上去会启动失败，甚至导致 dsh web 起不来。建议装一个验证一个，别一次性全装。

七、插件也补不了的 5 项 —— 架构性差距

这是本报告最重要的部分。DSH 与 Open WebUI / OpenWork 的差距不只是「缺插件」，有些是设计定位差异：

能力为什么补不了
真正的多用户 + 多租户Open WebUI 是多用户平台，用户/角色/权限是数据模型层的概念。DSH 是单人本地工具，.credentials.yaml、sessions/、profiles/ 都是单用户结构。插件只能做「认证门禁 + 权限守卫」，做不到租户级数据隔离。
模型并行对比Open WebUI 的 side-by-side 多模型同时回答，需要平台层同时维护多条推理流。DSH 的会话绑定单一模型，插件层未见对应实现。
完全离线 Docker 一键部署Open WebUI 可打包成单个容器完全离线跑。DSH 依赖 Node 运行时 + pnpm 依赖树 + 各插件的外部服务，架构上不是「一个镜像」。
Google Workspace 等 SaaS 原生深度集成OpenWork 把 Google Workspace 做成内置能力来源。DSH 侧需要自己配 MCP server，且 OAuth 流程要逐个接。
服务端 / 客户端分离架构OpenWork 是「server API + 多客户端」，能力天然可共享。DSH 是本地单体，跨机共享只能靠导出配置再导入（即 dsh-config-manager 做的事），不是原生能力。

结论

DSH 可以做到「单人全能工作台」，但做不到「多人协作平台」。如果你的目标是给团队/公司搭一个可管权限、可多租户的 AI 门户，DSH 不是合适的选择，应该用 Open WebUI 那类平台。如果目标是给自己造一个功能齐备的本地工作台，那按上面的清单装插件就够了，而且 DSH 在「上下文压缩」和「本地 Agent 能力」上反而强于这些平台。
