结论先行

  • 优化项真实、可核查——全部代码与配置在 GitHub 公开，参数可逐条查证。
  • "优化了什么数值"可以精确回答——BORE 10 个参数、tick 1000Hz、sysctl、IO 调度器分配、NVIDIA 模块参数等。
  • 但"效果证据"最弱的一环恰恰是游戏专项——最强证据是 Phoronix 综合基准，而它存在明显混杂变量（confounder）。

一、游戏优化清单：到底做了什么

CachyOS 的"游戏优化"不是单一开关，而是四层叠加。

A. 编译层 让 CPU 少空转

优化项做法
全仓库重编译整个仓库按 x86-64-v3 / x86-64-v4 / znver4 指令集重建，而非使用 Arch 通用二进制
LTOClang ThinLTO，默认在主包 linux-cachyos 启用；支持分布式 ThinLTO
PGO核心包启用 PGO；内核用 AutoFDO（类 PGO 的采样优化）
BOLT核心包额外做 BOLT 后链接优化
GCC 高级 flag-fivopts、-fmodulo-sched
目的：现代指令集 + 跨函数优化 → 更紧凑、分支预测更准的代码 → 减少 CPU 空转，收益落在吃 CPU 的场景（1080p/2K、竞技网游、模拟类）。

B. 内核层 降低调度延迟与抖动

优化项做法 / 数值
调度器可选EEVDF（默认，含自有 tunables）/ BORE / BMQ（Project C）/ RT-BORE（实时）
sched-ext (SCX)用户态可插拔调度器（BPF），scx_loader 管理，可运行时切换；与 BMQ 变体不兼容
Tick rate默认 1000Hz；可选 100 / 250 / 300 / 500 / 600 / 750 / 1000 Hz
抢占模型PREEMPT_DYNAMIC（full / lazy / voluntary / none 运行时可选）
POC Selector类 scx_cake 的 Piece-Of-Cake 快速空闲 CPU 选择器，降低唤醒延迟
sched/wait LIFO accept()socket accept() 按 LIFO 处理，改善缓存效率
MGLRU + "Cachy Sauce" MMLRU-gen 工作集保护、compaction / watermark 调整、hugepage 回收
I/O 调度器增强 BFQ 与 mq-deadline；集成 ADIOS v3.2.0 多队列 I/O 调度器
VRAM cgroup (DMEM)DRM 设备内存控制器，可按 cgroup 限制显存占用
补丁集Linux 7.1 基线合并 15 个 topic 分支：amd-isp4 bbr3 cachy cgroup-vram drm-fair hdmi lenovo-wmi mglru preempt-ipi sched-cluster snd-codecs t2 vesa-dsc-bpp 等
游戏硬件适配Steam Deck 补丁（Audio / HW Quirks / HID）、ROG Ally、MSI Claw HID（deckify）
显示相关HDR 启用、AMDGPU amdgpu_ignore_min_pcap、AMD 上 HDMI VRR、ALLM 与被动 VRR connector 属性
目的：把"游戏卡顿"的来源——调度延迟、唤醒延迟、内存回收抖动、I/O 排队——逐项压掉。

C. 系统层 具体数值 —— "优化什么数值"的核心

以下数值来自官方 CachyOS-Settings 仓库。

sysctl 内核运行时参数

  • vm.swappiness = 100（启动时）；ZRAM 初始化时提升到 150，并关闭 Zswap
  • vm.vfs_cache_pressure、vm.dirty_bytes、vm.dirty_background_bytes、vm.dirty_writeback_centisecs
  • 禁用 vm.page-cluster；禁用 kernel.nmi_watchdog
  • 启用 kernel.unprivileged_userns_clone；限制 kernel.kptr_restrict
  • kernel.printk 隐藏控制台消息；提高 net.core.netdev_max_backlog；设置 fs.file-max

udev / 设备级

  • I/O 调度器按设备类型分配：HDD → bfq；SATA SSD / eMMC → mq-deadline；NVMe → kyber
  • SATA host link power management → max_performance
  • HDD 应用 hdparm -B 254 -S 0
  • 音频：snd-hda-intel 省电策略随供电切换（AC 时关闭，避免爆音）
  • 设备权限：rtc0 / hpet 归入 audio 组；开放 cpu_dma_latency

systemd / 资源

  • ZRAM：zstd 压缩、swap-priority=100
  • DefaultLimitNOFILE：system 2048:2097152，user 1024:1048576
  • 服务超时：DefaultTimeoutStartSec=15s、DefaultTimeoutStopSec=10s；journald 上限 50MB
  • 用户服务资源委托（CPU / cpuset / IO / memory / pids）
  • 开机加载 ntsync 内核模块（Windows 同步原语，替代 esync/fsync 的新方案）

THP（透明大页）

  • transparent_hugepage/defrag → defer+madvise
  • khugepaged/max_ptes_none（6.12+）

NVIDIA 专有模块参数（modprobe）

  • NVreg_InitializeSystemMemoryAllocations=0（跳过 GPU 分配内存清零）
  • NVreg_DynamicPowerManagement=0x02（移动 GPU 省电）
  • NVreg_EnableS0ixPowerManagement=1（S0ix 空闲省电）

延迟 / 优先级

  • 音频：@audio 组 rtprio 99
  • pci-latency 脚本：声卡 PCI latency timer 设为 80 cycles
  • game-performance 脚本：启动应用时用 powerprofilesctl 切到 performance 电源档，并默认抑制屏保
目的：把电源档、I/O 队列、内存回收、GPU 内存分配、同步原语这些"游戏外"的干扰项调到低延迟状态。

二、BORE 调度器：优化了什么数值（完整参数表）

这是"优化什么数值"最硬的答案。BORE（Burst-Oriented Response Enhancer）由 firelzrd 开发，CachyOS 深度参与测试。

核心思路：跟踪任务自上次 yield / sleep / IO-wait 以来消耗的 CPU 时间（burst time）→ 取 bit count → 用 offset 与 coefficient 调整 → 得到 0–39 的 burst score（类似 niceness）。分数每降低 1，可消耗的时间片约变为 1.25 倍。越"不贪 CPU"的任务获得越长时间片与越激进的唤醒抢占。

参数范围默认值作用
sched_bore0 – 11启用 / 关闭 BORE 机制
sched_burst_cache_lifetime0 – 429496729560000000 ns（60ms）fork 时计算的平均 burst time 缓存时长
sched_burst_fork_atavistic0 – 32祖先进程 burst time 继承（拓扑 hub/stub 树）；对大量 fork 场景（如内核编译）提升响应性
sched_burst_penalty_offset0 – 6422计算 burst score 时从 bit count 中减去的位数；越大则短突发任务越不被"过强"
sched_burst_penalty_scale0 – 40951280（1.25x）按 burst time 比例区分任务的强度
sched_burst_smoothness_long0 – 11长时平滑（抑制突发尖峰）
sched_burst_smoothness_short0 – 10短时平滑（0 = 不平滑）
sched_burst_exclude_kthreads0 – 111 = 仅对非内核任务生效
sched_burst_parity_thresholdu82runqueue 任务数超过该值时自适应关闭 RUN_TO_PARITY
sched_deadline_boost_masku32ENQUEUE_INITIAL | ENQUEUE_WAKEUP以此标志入队时 deadline 减半
目的：在"吞吐"与"响应性"之间偏向后者——保证前台 / 交互任务（游戏、输入）优先获得 CPU，代价是批处理任务权重下降。

三、优化的目的是什么

目标对应手段
减少 CPU 空转、提高 IPC全仓库 v3/v4/znver4 重编译、LTO/PGO/BOLT、AutoFDO
降低调度延迟与抖动BORE / EEVDF 调参 / sched-ext、1000Hz tick、PREEMPT_DYNAMIC、POC Selector
让游戏 / 前台优先BORE burstiness、ananicy-cpp 规则、game-performance 切 performance 档、nice 值
降低输入延迟AMD Anti-Lag 2、NVIDIA Reflex（vkd3d-low-latency）、NTSync
减少 I/O 与内存抖动IO 调度器按设备分配、MGLRU、zram zstd、dirty 参数、THP 调优
提升兼容性（"能跑"）Proton-CachyOS、deckify 内核、Steam Deck / ROG Ally / MSI Claw 补丁、反作弊修复
提升画质 / 帧率（低配）FSR4 自动升级、OptiScaler、GameScope + FSR 缩放、DLSS 预设强制
一句话：目标是把"尾部表现"（卡顿瞬间、输入延迟）拉平，而不是提高平均帧上限——这也解释了为什么收益主要体现在 1% low 而非平均帧。

4.3 弱证据 / 存疑

  • "相比 Nobara / Garuda 有 10–15% FPS 提升，并已在 ProtonDB 统计中验证"（来源为 CSDN 转载笔记）→ 该说法不成立：ProtonDB 是玩家兼容性上报平台，不提供对照基准测试，无法"验证"帧率提升幅度。
  • 官方 AutoFDO 内核优化：有专门博客说明方法，但主要给的是"优化方法"而非独立可复现的对照数字。
  • 反证：Phoronix 在同一台 Razer Blade 18 上的本地 AI 推理测试中，Windows 11 大幅领先——优化并非"全面碾压"，而是场景特定。

4.4 证据链的结构性问题

  1. 游戏专项测试几乎都来自个人 UP 主（单样本、单机型、多为高端 N 卡）。
  2. 平均帧提升有限，宣传的是 1% low；两者混用容易造成误解。
  3. 收益与场景强相关：CPU 受限（1080p/2K、竞技网游、模拟类）收益大；4K 下 GPU 成为瓶颈，优势明显收窄。
  4. 归因困难：Linux 游戏收益大头来自 Proton / 驱动 / 上游内核，任何发行版都能吃到；CachyOS 独有的只是"编译优化 + 调度器调校"那一层。

5.2 评测条件是否公平、全面？

公平的部分 ✅

  • 同一台硬件、同一时段、同一测试套件（Phoronix Test Suite），控制住硬件变量。
  • 公开原始数据（OpenBenchmarking.org），可复核。
  • 内核变体横评隔离了调度器变量（BORE vs EEVDF vs hardened）——方法学上最干净的一组。

不够公平 / 不够全面 ❌

  • 单一机型：仅 Razer Blade 18（高端 Intel + NVIDIA），无法外推到 AMD / 中低端 / 掌机。
  • 版本混杂（关键 confounder）：CachyOS 用更新的内核 + Mesa/驱动，Ubuntu 26.04 是 LTS 快照——差异不完全来自"发行版优化"。
  • 负载偏科：99 项含编译、渲染、模拟、AI，纯游戏项占比低。
  • 统计口径：51/99 是胜项数；geomean 差 0.07 属噪声级。
  • 缺少帧时间分析：多数项目是吞吐/耗时型，不是 1% low / 帧生成时间。
  • 单次运行：未披露重复次数与置信区间。
  • 未做归因拆解：编译优化 / 调度器 / 内核版本 / 驱动版本各自贡献度未分离。
  • 未覆盖 4K：而该场景恰恰是 CachyOS 优势消失的地方。
5.3 评价：Phoronix 的评测在"跨系统整体性能"这一命题上方法严谨、可复核，是当前最可靠的第三方证据；但它不能作为"游戏优化有效"的直接证据——既没有游戏帧率 / 帧时间专项，也存在"新版内核 + 新驱动"对"LTS 快照"的混杂变量。

结论：想验证"CachyOS 游戏优化值多少帧"，目前没有高质量、多机型、控制变量的公开评测。最靠谱的做法是自己在目标机型上用同一游戏、同一画质，记录 1% low 与帧时间做 A/B 对照。

六、总结

问题回答
做了什么优化？四层叠加：编译层（v3/v4/znver4 + LTO/PGO/BOLT）、内核层（BORE/EEVDF/SCX、1000Hz、PREEMPT_DYNAMIC、MGLRU、ADIOS）、系统层（sysctl/IO 调度器/ZRAM/THP/NVIDIA 模块参数）、运行时层（Proton-CachyOS、FSR4、Reflex、NTSync）
如何优化？编译期做指令集与跨函数优化；运行期用调度器把 CPU 优先给交互任务；系统层把电源 / IO / 内存回收调到低延迟；运行时层补齐兼容与画质升频
优化什么数值？可精确列举：BORE 10 个参数（含 penalty_offset=22、penalty_scale=1280、burst score 0–39、每 -1 约 1.25x 时间片）、tick 1000Hz、vm.swappiness=100（ZRAM 150）、NOFILE、IO 调度器按设备分配、NVIDIA NVreg_* 等
目的是什么？压掉延迟与抖动，优先保障尾部表现（1% low / 输入延迟），而非提高平均帧上限
效果证据多少？强：Phoronix 99 项 / 51 胜（但混杂变量）；中：CS2 1% low +20%、RX 5700 XT 平均 +6.4%；弱 / 存疑："10–15% FPS、ProtonDB 验证"（不成立）；反证：同机 AI 推理 Windows 胜、4K 优势消失
Phoronix 几篇？可确证 ≥3 篇：内核变体横评、BORE 内核专项、三系统 99 项横评（另有季度汇总提及）
评测公平全面吗？部分公平（同机同套件、公开数据、内核横评隔离了调度器）；不够全面（单机型、版本混杂、游戏项少、无帧时间、无 4K、单次运行、未做归因拆解）
最诚实的结论：CachyOS 的优化工程上是真实且可审计的（参数都在 GitHub），但"游戏帧率提升多少"目前缺乏高质量公开证据。宣传中的"20%""翻倍"等数字均来自单样本个人测试或未经证实的说法，应视为个案而非普遍结论。
