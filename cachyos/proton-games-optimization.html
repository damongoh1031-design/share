Proton 运行的游戏：CachyOS 哪一项优化收益最大？

赛博朋克 2077 · 幻兽帕鲁 Palworld · 灵魂面甲 Soulmask  |  2026-10-16  |  承接第九轮（原生单线程模拟游戏）

一句话结论：冠军换层了。原生游戏里"编译层无效"，是因为游戏二进制由厂商预编译；Proton 游戏多了一整层"发行版自己维护并重编译"的代码——Wine / DXVK / vkd3d-proton / Mesa，正好在 CPU 关键路径上。所以 CachyOS 的招牌（v3/v4 + LTO/PGO/BOLT）第一次真正生效，收益最大的单项变成翻译层 + 运行时栈，其次是 NTSync（收益主要在帧时间一致性，不在平均帧）。

一、与原生游戏的结构性差异（全部结论的来源）

原生游戏：  游戏二进制（厂商预编译） ──▶ 内核 / glibc
Proton 游戏：游戏二进制（厂商预编译） ──▶ Wine → DXVK / vkd3d-proton → Mesa RADV ──▶ 内核
                                        └── 这一整层是发行版的包，CachyOS 会重编译它
维度原生 Linux 游戏Proton 运行的游戏
游戏本体原生 ELF，厂商预编译Windows PE，仍是厂商预编译
关键路径上还有什么几乎只有游戏自己的代码多了一整层：Wine → DXVK(D3D9/10/11) → vkd3d-proton(D3D12) → Mesa/驱动
这层由谁构建—发行版自己（proton-cachyos / dxvk / vkd3d-proton / mesa 都是包）
招牌优化是否触达❌ 碰不到✅ 碰得到，且在关键路径上
额外固定成本无翻译开销：每个 draw call 过 DXVK/vkd3d，每个同步调用过 Wine

三、冠军项：翻译层 + 运行时栈

为什么它是冠军

  • DXVK / vkd3d-proton 要把每一次 DirectX 调用翻译成 Vulkan；Wine 要把每一次 Windows syscall / 同步调用翻译成 Linux 语义。这些代码每一帧都在跑，且由发行版编译。
  • CachyOS 把它们按 x86-64-v3/v4/znver4 重编译并叠加 LTO / PGO / BOLT——这正是 DXVK 这类"分支密集、指令密集"代码最吃优化的场景。
  • 侧证：DXVK 官方 release notes 自己就以 "CPU-bound performance" 作为发布标准（描述符绑定模型改动时写"expected to achieve roughly the same level of CPU-bound performance"）。

但它补不回原生

CachyOS 的优化是把 Proton 的翻译开销往回补一点，不是"让 Proton 超过原生"。对 CPU 密集的游戏，有原生 Linux 版就上原生版。2077 / Palworld / Soulmask 都没有原生版，Proton 是唯一路径——这时"减少翻译开销"才有意义。

四、亚军项：NTSync —— 必须打破媒体的夸大

Windows 游戏用 NT 同步原语（mutex / semaphore / event）协调线程，每秒可达百万次等待。Wine 历史上靠 wineserver 进程 RPC 往返模拟，对多线程游戏是真实瓶颈。NTSync（Elizabeth Figura / CodeWeavers）在内核里直接实现，暴露 /dev/ntsync，消除用户态往返。2025-01 进 Linux 6.14 主线；Wine 11.0（2026-01）默认启用；CachyOS 2025-03 就把 Wine 补丁默认切到 NTSync。

三条必须标注的限定

  • 对比基准是 vanilla Wine。而 Steam 玩家很多年没用过原版 Wine 了。
  • 对比 esync / fsync，NTSync 基本没有平均帧收益——社区原话："don't expect 100 more fps, or even 10"。
  • 它的核心价值是"正确性"与一致性：开发者表述"NTSync isn't faster, it's more correct. It fixes subtle edge cases like hitches and deadlocks." 收益主要体现在 1% / 0.1% low、alt-tab 不冻结、不锁死。

对 2077 / Palworld / Soulmask：三者都是现代多线程引擎（REDengine 4 / UE5 / UE4-5），理论上是 NTSync 的目标场景，但不是同步密集型的极端案例。合理预期：一致性小幅改善，平均帧接近 0。不要为了 NTSync 换发行版——内核 ≥ 6.14 的任何发行版都有。

五、决定性的前置问题：CPU 受限还是 GPU 受限

场景瓶颈有效项
2077 @ 4K 路径追踪GPU 受限只剩驱动版本、DLSS / FSR4、帧生成。翻译层优化几乎无效
2077 夜之城人群密集区 / 1080pCPU 受限翻译层 + NTSync + 调度
Palworld 大基地（大量帕鲁 / 掉落物）CPU 受限翻译层 + 调度；内存也可能吃紧
Soulmask 大基地（大量建造物 / NPC）CPU 受限同上
三者 @ 4K 高画质GPU 受限驱动 + 升频

60 秒实操判据

用 MANGOHUD=1 %command% 看 GPU 占用率：

  • GPU 占用 < 90% → CPU 受限 → 上面这些值得做。
  • GPU 占用 ≈ 100% → GPU 受限 → 别折腾，去调画质与升频。

六、可复用操作

# 1) 确认 NTSync 可用（内核 >= 6.14）
uname -r
lsmod | grep ntsync || sudo modprobe ntsync
ls -l /dev/ntsync

# 2) Proton 侧启用（Proton 11+ 默认开；老版本手动）
PROTON_USE_NTSYNC=1 %command%

# 3) 优先用发行版重编译过的 DXVK / vkd3d-proton
#    Arch/CachyOS: pacman -S proton-cachyos dxvk-mingw vkd3d-proton-mingw
#    然后在 Steam → 兼容性 → 强制指定 Proton 版本

# 4) 低延迟 / 升频（Proton-CachyOS 已集成）
PROTON_FSR4_UPGRADE=1 %command%   # 自动升级 FSR4 DLL

七、坑与反直觉

  • "NTSync 提升 678%" —— 对比的是原版上游 Wine；对比 esync/fsync 基本没有平均帧收益。
  • "CachyOS 编译优化让游戏更快" —— 对原生游戏无效；对 Proton 游戏有效但仅限翻译层，量级个位数%。
  • "Proton 能超过原生" —— ❌。CachyOS 是补回翻译开销，不是消除它。
  • "4K 下优势消失" —— 这条在 Proton 场景同样成立（与原生模拟游戏不同）。2077 4K 路径追踪是纯 GPU 瓶颈。
  • "换了发行版就快了" —— 对 Proton 游戏，GPU 驱动版本（Mesa RADV / NVIDIA 专有驱动）的版本差异通常大于发行版优化差异。
  • 2077 的 Proton 版本选择 —— 社区反馈 2077 在 Proton 8.0 上帧率更稳、崩溃更少，并非越新越好 → 按游戏查 ProtonDB。
  • 反例存在 —— 有测试显示启用 FSR 3 的《第一后裔》Windows 11 以 63 FPS 领先 Linux 端 54 FPS。

八、未核实 / 存疑

  • 没有 CachyOS 针对 2077 / Palworld / Soulmask 的公开对照基准 → 本报告量级为结构性推断。
  • "翻译层重编译带来十余 %" 的上界未经实测标定；DXVK 官方只给相对表述。
  • NTSync 对这三款游戏的具体收益：无公开数据；现有基准表全部是对 vanilla Wine 的对比。
  • smzdm 转述的 CachyOS vs Win11 数字（2077 平均 98 vs 91 FPS；星际战士2 1% low 72 vs 58，5600X + RX 6700XT）：二手转述，未披露方法 → 方向性参考。

九、两次提问的结论对照

游戏类型冠军项为什么
原生（RimWorld / 群星 / CK3）内核内存管理 + 调度延迟层编译层碰不到游戏二进制，只能靠系统层
Proton（2077 / Palworld / Soulmask）翻译层 + 运行时栈翻译层是发行版重编译的代码，且在 CPU 关键路径上

共同点：两者收益量级都在个位数百分比（除非内存吃紧或功耗受限，才可能出现量级差异）。换发行版永远不是最大杠杆——硬件（X3D / 内存容量 / GPU 驱动版本）才是。
