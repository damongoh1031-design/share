CPU 密集型模拟游戏：CachyOS 哪一项优化收益最大？

RimWorld · 群星 Stellaris · CK3  |  调研日期 2026-10-16  |  承接前八轮 CachyOS 系列

一句话结论：对这三款游戏，CachyOS 的头牌优化（全仓库 x86-64-v3/v4 + LTO/PGO/BOLT 重编译）几乎零收益——游戏本体是厂商预编译的二进制，发行版重编译碰不到它。收益最大的那一项是内核的内存管理 + 调度延迟层（MGLRU / THP / swappiness+ZRAM / BORE-EEVDF 调参 / 1000Hz / PREEMPT_DYNAMIC），量级为个位数百分比；唯一能产生"量级差异"的场景是内存吃紧时避免磁盘 swap。

二、先定瓶颈：这三款游戏吃什么

游戏引擎主瓶颈后期内存足迹缓存敏感度
RimWorldUnity (Mono)单线程 TPS，主线程单核 100%轻度 4–8 GB；重度 mod 8–30 GB极高
群星Clausewitz单核为主 + 少量并行1000 星后期 8–16 GB高
CK3Clausewitz主核 CPU0 长期高占用 + 内存带宽压力后期 6–10 GB高

四个共同点（全部分析的地基）

  • "后期慢" = 单线程吞吐不足——推进速度由一条主线程的 IPC × 频率决定。
  • 指针追逐 + 大工作集 → 对 L3 容量与内存延迟高度敏感（这正是 X3D 在这类游戏上收益大的原因）。
  • 内存足迹随时间单调增长 → 内存压力是常态（RimWorld 重度 mod 尤其）。
  • 显卡几乎不参与——1080p 和 4K 下都是 CPU 瓶颈。

推论：能真正加速它们的只有四件事——单核 IPC × 频率、内存延迟/带宽、L3 容量、RAM 容量。发行版只能碰到其中两项的一半。

把「作用于游戏执行路径」这一列筛出来，只剩内核内存管理、内核调度、系统层内存/电源三类——这就是全部候选池。

四、为什么头牌优化失效（最反直觉的一点）

宣传口径 ≠ 机制

CachyOS 的说法是"编译优化减少 CPU 空转 → 收益落在吃 CPU 的地方"，因此推不出"CPU 密集型游戏收益最大"。

  • 包仓库重编译的对象是发行版自己的包（内核、glibc、Mesa、Proton、库）。游戏二进制来自 Steam / 厂商，CachyOS 不参与其构建。
  • 这三款都有原生 Linux 版。走原生版时连 Proton 都不在链路上，编译层覆盖面进一步缩小到"内核 + glibc + Mesa"。
  • 模拟循环写在游戏自己的代码里，而那段代码由厂商用厂商的编译选项构建，v3/v4/LTO/PGO 一个都吃不到。
  • 唯一剩下的间接路径：glibc 的 malloc/memcpy（早已 IFUNC 运行时分派，增量很小）与内核自身的页回收/调度路径（亚百分比级）。

一句话：招牌对"发行版自己的软件"有效（编译器、渲染、AI 推理——这正是 Phoronix 99 项里它赢 51 项的地方），对"厂商预编译的游戏本体"基本无效。宣传里的"CPU 密集"指负载类型，不指游戏。

五、唯一能"量级"改变的一项

✅ 成立条件

物理内存 < 存档工作集（RimWorld 重度 mod 常见，群星 1000 星后期亦可能）。此时 swappiness=100 + ZRAM 把匿名页留在压缩内存里，避免磁盘 swap 造成的微秒→毫秒级跃迁。

⚠️ 反直觉的代价

ZRAM 的压缩/解压消耗 CPU。对 CPU 密集型游戏这是真实负项——内存充足时依赖 ZRAM 反而可能变慢。

正确排序：加内存 > ZRAM > 磁盘 swap。

六、可复用操作（任意发行版）

# 1) THP：减少大堆内存的 TLB miss
echo 'defer+madvise' | sudo tee /sys/kernel/mm/transparent_hugepage/defrag

# 2) ZRAM 兜底（仅内存 < 存档工作集时才值得开）
sudo pacman -S zram-generator
printf '[zram0]\nzram-size = ram / 2\ncompression-algorithm = zstd\nswap-priority = 100\n' \
  | sudo tee /etc/systemd/zram-generator.conf
echo 'vm.swappiness = 100' | sudo tee /etc/sysctl.d/99-swap.conf

# 3) 电源档：避免单核睿频被省电策略压住
powerprofilesctl set performance      # Fedora 用 tuned

# 4) 调度延迟：sched-ext 可运行时切换，无需换内核
scxctl start --scheduler scx_lavd     # Arch: scx-scheds / openSUSE: scx

# 5) 跑原生 Linux 版，不要走 Proton（这三款都有原生版）

BORE / BMQ 不在主线，必须换 linux-cachyos 内核或自编译补丁——这是 CachyOS 唯一无法在其他发行版"纯官方仓库"里复现的内核项。

七、坑与反直觉

  • "CPU 密集型游戏吃编译优化"是营销口径，不是机制。编译器层碰不到游戏二进制。
  • "收益在 1% low"作为卖点对这三款游戏错位。它们的痛点是吞吐（TPS / 回合推进），不是帧时间抖动。
  • "4K 下优势消失"这条边界条件不适用——这三款在任何分辨率都是 CPU 瓶颈。
  • 换发行版的收益 < 升级硬件。加速手段排序：X3D CPU（L3 容量） > 内存容量 > 内核/调度调优 > 换发行版。但即使上 X3D，群星后期 1000 星仍会卡——游戏架构问题，发行版救不了。
  • ZRAM 有 CPU 开销，内存充足时是净负项。

八、未核实 / 存疑

  • 没有任何 CachyOS 针对这三款游戏的公开对照基准 → 本报告量级为结构性推断。
  • BORE 对模拟类游戏吞吐的影响：无公开数据。
  • RimWorld 5800X3D +30%：贴吧/B站个人实测，单样本 → 社区实证。
  • CK3"主核占用高 + 内存带宽压力"：百度文库二手分析 → 推断。
  • THP/MGLRU 与 ZRAM 在该场景的增益/开销百分比：机制成立，量级未标定。

九、一手证据：开发者自己怎么说（最硬的校准）

这一节把上面的推断钉在第一方数据上——因为它给出了所有发行版优化的参照系。

群星 4.3「Cetus」开发日志（2026-02-06，官方）

同一台机器（i9-14900K / 32GB / RTX 3060）、巨型星系、士官难度、同存档同随机种子，用 -gamestatetimer 记录"每年秒数"：

版本开局速度后期速度
3.1430.52 秒/年2269 年退化到 44.63 秒/年
4.311.54 秒/年直到 2269 年才退化到 3.14 的开局速度

≈ 2.6× 提升，且全部来自游戏自身代码层：依赖跟踪减少 CPU 等待时间与"月度卡顿"、减小线程批处理粒度以更好分布到多核、重用内存并减少更新中的分配/释放、把触发器计算移到合适的脉冲（微刻/日刻/周刻/月刻/年刻）、优化字符串函数与舰队图标逻辑。

三条直接推论

  • 游戏版本 > 一切发行版优化。3.14 → 4.3 是 2.6 倍；CachyOS 相对通用发行版在这类负载上是个位数百分比。
  • 群星不是纯单线程，瓶颈含"CPU 等待"与"内存分配抖动" → 印证内核调度/内存层是唯一有效的发行版抓手，但天花板由游戏代码决定。
  • CK3 开发日志 #187（2025-10-15）同样把性能作为专门主题，基调是"新增功能的模拟负载需要专项优化" → 后期慢的主因在游戏代码与存档规模。

⚠️ 方法学提醒：官方测试用 Windows 机器、且是版本间对比，不是发行版间对比。它证明的是"游戏自身优化量级"，不是"Linux 比 Windows 快多少"。

十、与前序 KB 结论的对齐

仓库中已有前序会话产出的 KB 文档 cachyos/kb/cachyos-cpu-bound-strategy-games.md（v1.0，结论："若必须挑一项先测，选 game-performance 性能电源档"）。本报告与它不矛盾，而是给出分叉条件：

机器条件冠军项量级
功耗受限（笔记本 / 掌机 / 小机箱 / 温度墙）game-performance 电源档 / 单核睿频维持可显著
内存吃紧（重度 mod 存档 / RAM < 工作集）vm.swappiness=100 + ZRAM + THP/MGLRU0 或 量级
两者都不成立（台式 + 内存充足）只剩调度延迟层个位数百分比

前序文档的"电源档"结论在功耗受限机器上成立；本报告补充了内存吃紧分支，并给出"两者都不成立时收益退化为个位数"的上界。两版合并后写入 KB v2.0。
