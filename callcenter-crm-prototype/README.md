# 外呼 CRM · 交互原型（v0.9）

单文件可交互原型，用于在写 Go 后端之前验证产品形态、权限模型与操作流程。
数据存浏览器 `localStorage`，刷新不丢，重置按钮可回到初始状态。

- 入口：`prototype/crm-prototype.html`（双击即开，无需服务端）
- 技术：单文件 HTML + 原生 JS，无外部依赖、无 CDN、无网络请求
- 规模：约 2,600 行，26 位客户 / 30 条记事 / 28 条回访任务 / 8 个账号

---

## 1. 5 分钟体验路径

| 步骤 | 操作 | 要观察什么 |
|---|---|---|
| 1 | 以「王小明（员工）」进入 | 左侧只有 4 个菜单，看不到主管看板与用户管理 |
| 2 | 工作台 → 点「写跟进」 | 记事 + 更新状态 + 安排下次回访，一次提交三件事 |
| 3 | 客户 → 点任意客户 | 时间线按联系时间倒序，右侧显示下次回访 |
| 4 | 回访日历 → 点今天 | 当天安排抽屉，可写跟进 / 改期 / 取消 |
| 5 | 右上角切「赵敏（主管）」 | 客户数从 7 变 19，多出主管看板 |
| 6 | 主管看板 → 点员工姓名 | 右侧预览该员工今日待办与最近记事 |
| 7 | 切「系统管理员」→ 用户管理 | 账号、直属关系、禁用、重置密码 |
| 8 | 客户 → 导入 XLSX | 预览校验结果（5 成功 / 2 重复 / 1 失败）再确认 |

## 2. 已实现的可交互逻辑（不是静态截图）

**客户**
- 搜索（姓名/手机/公司，防抖 260ms）、按状态与负责人筛选、分页
- 新增 / 编辑，手机号唯一性校验（重复直接拦截并提示已有客户）
- 转移客户：可勾选「同时转移未完成回访」，历史记事保留原记录人
- 标记 / 解除「禁止联系」，解除必须填原因；标记后自动取消该客户待办回访

**呼叫记事**
- 联系时间、结果、内容、可选更新客户状态、可选同时安排下次回访
- 结果与客户状态分离（已接通 ≠ 有意向）
- 保存后自动回填客户「最近联系时间」并写入审计

**回访任务**
- 状态机：待处理 / 已完成 / 已取消
- 逾期是**动态计算**（待处理且计划时间已过），不落库
- 改期保留 `originalScheduledAt`、累加改期次数、必填原因
- 完成必须走记事表单，不能空完成
- 取消必填原因，且不计入完成率分母

**日历**
- 月视图（周一开头）+ 列表视图，日格显示任务数与时间/客户
- 红=逾期、绿=已完成、灰划线=已取消
- 点日期开抽屉，可直接处理任务

**主管看板**
- 团队 KPI、下属统计表（客户数/今日登记/联系客户/已接通/今日完成/逾期/按时率）
- 近 7 日登记外呼柱状图、最近团队动态
- 点员工姓名开预览抽屉

**权限（重点验证项）**
- 员工：仅本人客户；主管：本人 + 直属下属；管理员：全部
- 侧边栏按角色渲染，且数据层同样过滤 —— 用员工身份直接改 URL/调用渲染函数访问他人客户会显示「没有访问权限」
- 导出按当前筛选与权限范围计数

**其它**
- 站内提醒：铃铛未读数、单条已读、全部已读、点提醒跳任务
- 审计日志：新增/编辑/转移/改期/取消/导入导出/禁用账号都留痕
- 演示数据每日自动重置（`seedDay` 变化时重建），保证「今天」永远有内容

## 3. 明确模拟、不要当成已实现

| 能力 | 原型状态 | 真实系统要做的事 |
|---|---|---|
| 登录 | 点身份即进入，无密码 | bcrypt + Session Token 摘要 + HttpOnly/SameSite/CSRF |
| 数据存储 | 浏览器 localStorage | SQLite（WAL、foreign_keys、busy_timeout）+ 迁移 |
| XLSX 导入 | 固定 8 行预览，确认后插入 5 条 | Excelize 解析、体积/行数/解压限制、分批短事务 |
| XLSX 导出 | 只提示条数 | 服务端生成文件 + 公式注入防护 + 导出审计 |
| 电话外呼 | 只登记结果，不拨号 | 云呼叫中心或 FreeSWITCH 对接（本期不做） |
| 站内提醒 | 预置 5 条提醒 | Go 定时器 30s 扫描 + notifications 表 + 去重键 |
| 乐观锁 | 字段有 version，无冲突 UI | 更新带 version 条件，冲突返回 409 并提示刷新 |
| 备份 | 按钮 + 提示 | `VACUUM INTO` + 保留 14 份 + 恢复验证 |
| 通话时长/真实接通率 | 不采集 | 需电话平台回传，不在本期范围 |

## 4. 拿这个原型去问的问题（评审清单）

1. 「写跟进」里同时更新状态 + 安排下次回访，是不是坐席真实的操作顺序？会不会太重？
2. 客户列表默认按「下次回访时间」还是「最近联系」排序更符合使用习惯？
3. 逾期是否要显示在员工工作台顶部，还是只在主管看板暴露？
4. 一个客户同时存在多条待处理回访，是否合理？要不要限制为 1 条？
5. 主管是否需要「批量把客户从 A 转给 B」？原型只做了单个转移。
6. 导入时「重复号码默认跳过」是否符合预期？还是希望覆盖空字段？
7. 手机号全系统唯一，是否会挡住真实场景（同号不同联系人）？
8. 员工能不能看到同事的客户姓名（只读）？当前是完全隔离。
9. 日历要不要支持拖拽改期？当前只做点击改期。
10. 统计「按时率」用原始计划时间还是最新计划时间？原型用原始。

## 5. 与最终 Go 实现的映射

| 原型模块 | 对应后端 |
|---|---|
| 客户列表 / 详情 | `internal/customers` + `customers` 表 |
| 呼叫记事 | `internal/notes` + `call_notes` 表 |
| 回访任务 / 日历 | `internal/callbacks` + `callback_tasks` 表 |
| 提醒铃铛 | `internal/notifications` + 定时扫描 |
| 主管看板 | `internal/reports`（口径见页面底部说明） |
| 导入导出 | `internal/excel` + `import_batches` 表 |
| 权限过滤 | `internal/access`（页面、API、导出同一套判定） |
| 审计 | `internal/audit` + `audit_logs` 表 |

原型里的判定函数（`canSeeCustomer` / `visibleUserIds`）就是后端数据权限组件的雏形，
落地时把它移到服务端并对每个查询强制加范围条件，前端只做展示裁剪。

## 6. 已知限制

- 单浏览器单会话，没有并发与冲突演示
- 不做分页服务端化，客户量大时需要改
- 提醒为预置数据，不会真的到点弹出
- 移动端仅保证不横向溢出，未做专门布局
- 中文字体依赖系统（微软雅黑 / 苹方），无内置字体
