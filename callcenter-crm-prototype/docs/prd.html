1. 项目概述

1.1 背景

业务方需要一套内部使用的客户名单管理与外呼作业系统，替代当前「Excel 名单 + 手工记录」的方式。核心诉求有三条：

  1. 客户名单是公司资产，不能随便被带走（防导出、防截屏式复制、操作留痕）。
  2. 名单要能流动：主管分下去之后，没人跟进的客户要能自动回到池子里重新分配。
  3. 坐席每天打开系统就该知道「今天打给谁、打几个」，而不是自己去翻表格。

1.2 目标与成功标准

目标衡量方式目标值
名单不再沉淀客户沉淀率（超保护期未跟进 / 在跟客户）< 10%
作业有节奏坐席每日待回访清零率> 90%
数据可信记事登记完整率（有结果 + 有内容）> 95%
资产可控明文导出次数每周 ≤ 2 次，且全部有审计
打扰可控客户投诉「打太多次」的条数每月 ≤ 3 条

1.3 明确不做

不做原因
软电话 / CDR / 录音 / 通话质检本轮不接通信能力，坐席在系统外拨号，系统只做登记与流转
预测式外呼 / AI 首轮外呼依赖通话链路；且名单质量不足时只会更快制造投诉
中国式号码备案 / 主叫鉴权 / AXB 号码保护本地不适用
复杂商机 / 报价 / 订单 / 合同业务是「名单 + 外呼 + 意向筛选」，不是长周期销售
多级组织架构一层「主管 → 坐席」够用，层级一多数据范围规则会爆炸
原生移动 App坐席在工位用电脑；移动端只做响应式，不做 App

2. 用户与角色

2.1 角色定义

角色代号人数级职责
管理员admin1–2系统配置、账号与权限、全部客户、审计
主管 / 组长supervisor2–4带 5–10 名坐席；分配客户、审批流转、看团队 KPI
坐席 / 员工agent10–30领取与跟进自己名下客户，完成每日回访

一个员工只属于一个小组（users.manager_id 指向唯一主管）。小组由 teams 表定义，组长即该组主管。

2.2 典型一天

坐席（员工）

  1. 登录 → 落在「我的日程」：今天 8 条待回访、2 条逾期。
  2. 点第一条 → 呼叫台 → 看到客户资料 + 历史记事 → 拨号 → 回来登记结果。
  3. 登记完自动跳下一位，队列走完 → 去公海领 5 个新客户。
  4. 下班前日程清零。

主管

  1. 登录 → 落在「KPI 看板」：今日待回访、逾期、今日登记、团队客户。
  2. 看「客户池」三格：公海 3 / 待回收 1 / 待审批 0 → 有待回收就点进去处理。
  3. 看下属统计：谁今天 0 登记、谁逾期最多。
  4. 收到跨组流转申请 → 审批。

3. 业务流程

3.1 名单进入

XLSX 上传 → 解析预览（成功 / 重复 / 失败）→ 选择分配方式 → 确认导入
                                      ↓
                        公海（pool=public, ownerId=null）

三种分配方式：统一分配给某人、平均分配给下属、暂不分配（全部进公海）。

3.2 客户池状态机

                 ┌──────────── 领取（受持有上限约束） ────────────┐
                 ↓                                              │
   ┌──────────┐      ┌───────────────────────┐                  │
   │  public  │ ───▶ │  private (ownerId=我)  │ ─────────────────┘
   │  公海     │      │  claimedAt=领取时间     │
   └──────────┘      └───────────────────────┘
        ▲                       │
        │                       │ 保护期到期 且 无待办回访
        └──── 自动回收 / 手动退回 ┘

   private ──申请跨组──▶ 待审批 ──同意──▶ 目标组长名下（保护期重算）
                            └──驳回──▶ 原样

关键规则

规则定义可调
持有上限一个人名下私海客户数 ≤ claimLimit是，默认 200
保护期从 max(claimedAt, 最后一次记事时间) 起算 protectDays 天是，默认 15
有效跟进保护期内至少一条未作废记事否
回收条件超保护期 且 无待办回访 且 未禁呼 且 未合并自动回收可开关
回收动作pool=public、ownerId=null、claimedAt=null、取消待办回访、写审计否
有待办回访的客户不回收，是为了避免把正在推进的客户抽走。这一条不能做成可配置项。

3.3 回访作业闭环

排回访（任务）→ 到期进入日程/呼叫队列 → 登记结果（记事）→
  ├─ 已接通 → 完成回访，客户状态可更新
  ├─ 无人接听 / 占线 → 未接次数+1，未到上限则自动排下一次（周期重呼）
  ├─ 号码无效 → 标记无效，取消全部待办，停呼
  └─ 拒绝联系 → 可标记禁呼（需填原因）

周期重呼：间隔 cycleDays 天，最多 cycleMax 次。达到上限后进「待回收」，由主管决定继续还是判死。

3.4 跨组流转审批

触发：客户详情 →「申请转组」→ 选目标组 + 填原因。

  • crossApprove = 开：生成审批单（requests），目标组主管在「审批」页同意/驳回；同意后客户归到目标组长名下，未完成回访一并转。
  • crossApprove = 关：直接生效，不留审批单。

3.5 联系频次闸门

在记事登记、呼叫台保存、呼叫队列生成三处校验：

  1. 当前小时不在 [gateStart, gateEnd) → 拦。
  2. 近 gateDays 天内该客户记事数 ≥ gateMax → 拦。

被拦时给出具体原因（「该号码 7 天内已联系 2 次，达到上限 2 次」）。

这是打扰强度控制，不是法规要求。马来西亚没有营销外呼禁令；客户数据受 PDPA 2010 约束（告知目的、可要求更正与删除），属数据侧义务。

指标目标

7.2 安全

项要求
密码bcrypt（cost 10+），不存明文，不记日志
会话HttpOnly + SameSite=Lax + 服务端 session，30 分钟无操作过期
权限每个接口在服务端校验权限点 + 数据范围，前端隐藏只是体验
越权访问他人客户返回 403 并写审计
传输局域网内也建议 HTTPS（自签或内部 CA）
审计append-only 表，只插入不更新；关键操作含 IP
导出明文导出需二次确认，记录操作人、条数、范围
备份每日 VACUUM INTO + 保留 14 份 + 异地副本

7.3 可用性

项要求
部署单二进制 + SQLite，一条命令启动；systemd 守护
依赖无外部服务；不需要 Redis / 消息队列
故障恢复进程崩溃重启后数据一致（WAL）
备份恢复提供 restore 命令与演练脚本
日志结构化日志（JSON），按天切割，保留 30 天

7.4 兼容性

项要求
浏览器Chrome / Edge 最新两个大版本
分辨率1366×768 起；1600×900 为设计基准
移动端仅保证不横向溢出（「我的日程」「客户详情」两页后续做响应式）

8. 技术方案

8.1 架构

浏览器（单页，无构建）
   │  HTTPS / JSON
   ▼
Go HTTP 服务（单二进制）
   ├── internal/auth      登录、会话、强制改密
   ├── internal/access    权限点 + 数据范围（中间件）
   ├── internal/customers 客户 CRUD、分配、客户池
   ├── internal/notes     记事
   ├── internal/callbacks 回访任务、周期重呼
   ├── internal/excel     导入导出
   ├── internal/audit     审计、登录日志
   ├── internal/jobs      定时任务（回收、提醒、备份）
   └── internal/store     SQLite 访问层（sqlc 或手写）
   ▼
SQLite（WAL，单写队列）

8.2 选型

层选型理由
语言Go 1.22+单二进制、部署简单、团队已定
HTTPnet/http + chi轻量，不需要框架
数据库SQLite（WAL）单机局域网够用；写少读多
迁移golang-migrate 或自写 SQL 文件版本化
会话服务端 session 表 + HttpOnly Cookie可强制下线
密码golang.org/x/crypto/bcrypt
Excelexcelize读写 xlsx，注意解压炸弹防护
前端原生 JS 单页（沿用原型结构）无构建链，局域网加载快
部署systemd + 反向代理（可选 Caddy）
如果坐席数超过 50 或需要多机部署，把 SQLite 换成 PostgreSQL，其余不变。

10. 风险与开放问题

10.1 风险

风险影响应对
名单质量差（空号多）接通率低，坐席流失上线前先跑一轮号码体检；导入时做运营商前缀校验
坐席抵触登记数据不可信呼叫台把登记成本压到 3 次点击；主管用「登记完整率」考核
保护期/上限参数设错客户被大量回收或大量囤积上线首月每周复盘一次参数，之后每月
SQLite 并发写高峰期写锁等待单写队列 + busy_timeout=5000；超过 50 坐席换 PG
明文导出被滥用名单外流只给管理员 + 二次确认 + 每周审计导出记录

#问题影响

2「有效跟进」是否要区分「接通」与「未接通」？影响保护期计算口径
3一个员工是否可能属于多个小组？影响 manager_id 是否唯一
