一次点击的完整链路（以「呼叫台保存并下一位」为例）

click [data-act=call-save]→ A['call-save']→ saveCall()→ callQueue()[0]→ DB.notes.push→ task.status=completed→ 未接 → 建周期任务→ audit()→ saveDB()→ render()→ callView() 取下一位→ applyLang()
全站只有一条数据流：事件 → 改 state/DB → saveDB → render 全量重建 → applyLang。 没有虚拟 DOM、没有 diff、没有局部 patch（唯一例外是表格勾选，为避免闪烁做了局部更新）。 这带来两个好处：任何页面都能从 DB 直接复现；也带来一个代价：每次操作都重建 DOM，输入框需要靠 state 回填保持光标。

设计取舍（读代码时值得注意的三点）

1. 视图函数返回字符串，不持有状态。每个 xxxView() 都是 DB + state → HTML 字符串 的纯函数， 所以任何页面都能单独复现、单独测试；代价是没有局部更新能力，输入框靠 value="…" 回填。

2. 权限判断发生在渲染之前，而不是按钮上。can() 与 scopeIds() 同时作用于列表取数、详情取数、日历、记事、统计、导出、日志， 所以「隐藏按钮」只是副产品。员工把 state.custId 改成别人的客户，页面直接显示「没有访问权限」。

3. 动作层统一收尾：audit() → saveDB() → render()。没有这行收尾的动作一定是漏了东西。 这条约定让「审计完整」变成默认行为，而不是每个功能各自记得写日志。
