三个最容易被误解的点

① 绝大多数「向量库 MCP」只做召回，不做重排

官方 Qdrant MCP（1,548★，这个领域星数最高）只有 2 个工具：qdrant-store 和 qdrant-find。没有重排、没有混合检索，embedding 只支持 fastembed。它自述定位是「acts as a semantic memory layer」——不是 RAG 引擎。高星 ≠ 功能全。

② 想要「召回 + 重排」一体，只有很少几个 MCP 做到了

真正内置 cross-encoder 重排的 MCP，本轮只找到 3 个：haiku.rag、knowledge-rag、以及云端的 Bedrock KB Retrieval。

③ MCP 是「接缝」，不是「引擎」

RAG 的四个环节里，MCP 负责的是把已有能力接到 Agent 上，而不是替你实现能力。所以选型第一问不是「哪个 MCP 最强」，而是「我的检索后端是什么」。

关键结论

③ 召回 是 MCP 生态最成熟的环节（向量库厂商都在做官方 MCP）；④ 重排 是最稀缺的环节；② 切分 几乎没有独立 MCP。

1.2 MCP 是「接缝」，不是「引擎」

一个常见误解是「装个 MCP 就有 RAG 了」。实际上：

  • 向量库 MCP（Qdrant/Milvus/Weaviate）做的是「把你的查询转成对已有向量库的调用」
  • 它不负责：文档解析、切分策略、embedding 质量、重排、答案生成

所以选型顺序应该是：先定检索后端 → 再选 MCP，而不是反过来。

1.3 三类 MCP 的分工

类型代表你得到什么你需要自己做什么
存储型qdrant / milvus / weaviate / redis MCP一个「语义记忆」接口解析、切分、重排、答案
检索型haiku.rag / knowledge-rag完整的 RAG 能力几乎不用，装完即用
平台型Dify / RAGFlow / WeKnora完整平台 + 自带 MCP Server部署平台

二能同时做「召回 + 重排」的 MCP（最稀缺）

本轮全量检索后，真正内置 cross-encoder 重排的 MCP 只有 3 个（外加 1 个云端方案）。这一章是全文最有价值的部分。

2.3 awslabs/mcp — Bedrock KB Retrieval（云端首选）

项值
星数9,777★（整个 AWS MCP 集合）
LicenseApache-2.0
最后推送2026-10-14（活跃）

README 原文能力（已核实），其中三项非常关键：

Agentic retrieval on managed knowledge bases
  - Plan a multi-step retrieval strategy and synthesise a cited answer
  - Search several knowledge bases in one call
  - Optional condensed trace of the agent's planning and retrieval steps

Reach ACL-protected content
  - Pass user_id to retrieve content from ACL-aware data sources
    (SharePoint, OneDrive, Confluence with per-document ACLs)
  - Results are filtered to what that user is authorised to see

Rerank results
  - Improve relevance of retrieval results
  - Use Amazon Bedrock reranking capabilities

三个别处没有的能力：

  1. Agentic retrieval：不是单次检索，而是「规划多步检索策略 → 综合出带引用的答案」，且一次调用可跨多个知识库
  2. ACL 感知：传 user_id 就能拿到 SharePoint/OneDrive/Confluence 的权限内内容，结果按该用户权限过滤——企业场景的刚需，开源方案普遍缺失
  3. Bedrock 原生重排

同时支持 VECTOR 和 MANAGED 两种知识库类型，自动识别。

2.4 Azure AI Search 的 MCP 端点

Azure AI Search 每个知识库暴露原生 MCP 端点，检索请求里设 "resultsProcessing": "rerank" 即启用重排序管道。这是平台内建 MCP（不需要单独装服务器）。

⚠️ 注意

Azure/azure-mcp（1,225★）已归档（最后推送 2026-02-06）。Azure 的 MCP 能力现在走 AI Search 原生端点，不要去找那个归档仓库。

3.1 三个必须知道的发现

① Qdrant 官方 MCP 比想象的弱得多

已抓 README 核实，它的全部工具只有两个：

qdrant-store  → 存信息
qdrant-find   → 检索信息

配置项只有 QDRANT_URL / QDRANT_LOCAL_PATH / COLLECTION_NAME / EMBEDDING_PROVIDER（目前只支持 fastembed）/ EMBEDDING_MODEL（默认 all-MiniLM-L6-v2）/ QDRANT_SEARCH_LIMIT（默认 10）/ QDRANT_READ_ONLY。

高星 ≠ 功能全

它自述定位是「acts as a semantic memory layer」（语义记忆层）——不是 RAG 引擎。但它有 1,548★，是这个领域星数最高的。

② Elastic 官方 MCP 已废弃

[!CAUTION]
This MCP server is deprecated and will only receive critical security
updates going forward. It has been superseded by the Elastic Agent
Builder MCP endpoint, which is available in Elastic 9.2.0+ and
Elasticsearch Serverless projects.

另外它提示 SSE 传输已废弃，改用 streamable-HTTP。用 ES 做知识库的人要改路线。

③ Neo4j 有两套，别装错

neo4j-contrib/mcp-neo4j（988★）是 Neo4j Labs 项目，README 明确说「we don't provide any SLAs or guarantees around backwards compatibility」，并指向 github.com/neo4j/mcp 为官方产品版。它包含 4 个子服务：

  • mcp-neo4j-cypher — 自然语言转 Cypher
  • mcp-neo4j-memory — 知识图谱记忆（跨会话/客户端持久化实体与关系）
  • mcp-neo4j-cloud-aura-api — Aura 云实例管理
  • mcp-neo4j-data-modeling — 图数据建模与可视化

六记忆层（与知识库的边界）

「记忆」和「知识库」不是一回事
  • 知识库：你主动放进去的文档，可检索、可引用
  • 记忆：Agent 在对话中自动沉淀的事实/偏好，用于跨会话连续性

两者可以共用一个向量库，但用途和写入策略完全不同。选型时别把它们混成一个需求。

上一轮发现子代理的 star 数普遍不准。本轮进一步发现：光核验星数还不够，必须核实「它到底能做什么」。

  • 确认 Elastic 官方 MCP 已 deprecated（README 顶部 CAUTION 块）
  • 确认 knowledge-rag 的能力口径自相矛盾（13 tools/20 parsers vs 35 formats）

11.3 明确未核实 / 存疑项
