# 无人值守采集脚本的运维化设计

## 何时使用

- 用户说「为了长期维护」「避免 LLM 锁定」「不想经过 LLM 运行脚本」
- 用户问「出错了怎么纠错」「怎么挂计划任务 / cron」「中断了怎么办」
- 用户要求审查/改造一个已有的爬虫脚本，让它能无人值守跑
- 你自己写完一个采集脚本，交付前应主动按本清单补齐

## 核心判据

**「跑一次就完」的脚本不合格。** 合格的采集脚本必须能被**计划任务/cron**调用，
并且**不看 stdout 也能判断成败**。

## 九项必备件（缺一不可）

| # | 必备件 | 解决什么 | 关键实现 |
|---|---|---|---|
| 1 | **语义化退出码** | 无人值守唯一可靠信号 | 见下方码表；不要成功/失败都是 1 |
| 2 | **文件日志** | stdout 丢失后仍能排错 | `logs/run-<ts>.log`，含每次重试原因；日志目录不可写时降级不崩 |
| 3 | **自检模式** | 运行前发现问题，而非运行中 | `--doctor`：环境 + 网络 + robots + **选择器自检** |
| 4 | **离线自检** ⭐ | **拦住语义 bug**（`--doctor`/`--verify` 都看不见） | `--self-test`：纯函数断言，零网络。见下方专节 |
| 5 | **产出校验** | 确认结果质量没退化 | `--verify <out>`：行数/唯一性/格式/空字段/可疑字符 + **值域分布 + 集中度** |
| 6 | **顺序下载 + 完整性校验** | 避免「找不到资料」 | `--order sequential` + `manifest.json` 账本 + `--coverage` 报缺口 |
| 7 | **输出保护** | 防一次手滑毁掉数据 | 默认拒绝覆盖；`--force` 才覆盖且自动 `.bak`；`--append` 增量去重 + **读不到旧数据即中止**；**缩水守卫**；追加后用 `--verify --against` **自证旧数据没丢** |
| 8 | **断点续跑** | 长任务中断不丢工作 | 每页落 `state.json`；达标后自动清除；`SIGTERM` 也要先存断点 |
| 9 | **无-LLM 启动器** | 双击/计划任务可用 | `run.cmd` / `run.sh`，自动定位解释器，透传退出码 |

**另外三项强烈建议**：

| 项 | 解决什么 | 关键实现 |
|---|---|---|
| **互斥锁** | 计划任务重叠 → 双倍限流/互相踩踏 | OS 级文件锁（`msvcrt.locking` / `fcntl.flock`）。**进程死自动释放，不留死锁文件**，别用「写 pid 文件」那种土办法 |
| **脚本指纹** | 追溯「哪一版脚本」产出的数据 | 版本号 + 源码 sha256 写进输出 meta |
| **内置手册** | 用户不翻外部文档也能用 | `--manual` / `--examples` / `--print-api`（接口速查表） |

## 顺序下载 + 完整性校验（容易被忽略但很关键）

**问题**：随机抽样跑完，你不知道哪些页抓过、哪些没抓，无法判断资料是否齐全。

**解法三件套**：
1. `--order sequential`：按「分类顺序 → 页码升序」遍历，确定性、可复现（对比 `--order random` 抽样）
2. `manifest.json` 账本：每次成功抓取记 `{url, 分类, 页码, 字节数, 解析条数, sha1, 时间}`
3. `--coverage`：按分类算「已下载页集合 → 区间缺口 + 覆盖率%」，**有缺口就返回非 0 退出码**

```
  分类                    总页   已下载   覆盖   缺口
  hotels                   110       3  2.73%   4-110(未抓)
  office                   361       1  0.28%   2-361(未抓)
```

**补齐缺口**：再跑一次 `--order sequential`，已抓页会被去重跳过，只补没抓的。
**注意**：无下载记录时要报「尚无下载记录」，别误报「无缺口」（这是易犯的措辞 bug）。

## 派生产物必须「脚本重生成」，不能手贴

**问题**：采集脚本旁边常有一份看板/报告（HTML、Markdown、周报）引用产出数字。
如果这些数字是**手工粘贴**的，数据一更新就与源数据脱节 ——
**看板开始撒谎，而且没人会察觉**。这是比脚本 bug 更隐蔽的一类错误。

**解法**：把「源数据 → 派生产物」也做成**幂等脚本**（如 `inject_samples.py`）：

| 设计点 | 做法 |
|---|---|
| **标记式注入** | 在目标文件里放成对标记 `INJECT:XXX:START` / `END`，只替换标记之间。**不猜、不全文件重写** |
| **标记数量断言** | 每个标记必须各出现**恰好 1 次**，否则拒绝执行并返回独立退出码（如 5） |
| **注入后自检** | 校验：标记数量 / 生成的结构能否被解析（如 `json.loads`）/ 行数是否等于源数据 / 关键数字是否出现。**任一不过就不落盘** |
| **幂等** | 连跑两次 sha256 不变；第二次直接报「已是最新」。并提供 `--check` 只做一致性检查（给 CI / 计划任务用） |
| **缩水守卫** | 源数据行数 < 目标现有行数 × 50% 时**拒绝**（防「`--csv` 指错文件把看板改小」），确认无误加 `--force` |
| **先备份 + 原子写** | `.bak` + `.tmp` → `os.replace` |
| **`--dry-run`** | 先看会改什么、变更多少字节 |

**踩坑（真实）**：
- 标记若位于 `<script>` 内部，**不能用 HTML 注释 `<!-- -->`** —— 在 `<script>` 里那是裸文本，
  虽然靠 Annex B 的 HTML-like comment 侥幸能跑，但语义脆弱。**必须用 `/* */`**。
- 映射表（如分类 slug → 中文标签）要**显式列出**，遇到未收录项**打印警告并原样输出**，
  不要静默丢弃 —— 否则新分类会悄悄变成空标签。
- 引言文案里**不要虚报「一次跑出多少页/多少条」**：数据集往往是多次运行累积的，
  写死单次数字就是撒谎。只讲方法与总量，页数去 meta 里查。
- 生成器**自己的版本号若写进产物**（注释头等），改了版本号就要**重跑一次生成**，
  否则一致性检查会误报。要么别把版本写进产物，要么把这条写进维护清单。
- **自检要跑反例**：标记缺失 / 标记重复 / 源数据缩水 / 源文件不存在 ——
  四种都必须返回非 0。只测正常路径等于没测（本项目实测这四类都能正确拦住）。

## 输出保护（防误写/误覆盖）

| 场景 | 行为 |
|---|---|
| 目标不存在 | 正常写 |
| 目标已存在，未给 `--force` | **拒绝，独立退出码（如 7），不写任何文件** |
| 已存在 + `--force` | 先备份 `<名>.<时间戳>.bak` 再覆盖 |
| **新结果 < 已有行数 × 50%** | **缩水守卫：拒绝**（防一次失败运行覆盖好数据） |
| `--append` | 读旧 + 合并新，**按业务主键去重**，不丢旧数据；**合并前也自动备份** |
| 目标被 Excel 占用 | 降级写 `*_new.csv`，不抛异常 |

### `--append` 的三条铁律（血泪教训，必须堵死）

`--append` 的本质是**整文件重写**（读旧 + 合并 + 原子写）。所以：

1. **读不到旧数据 → 中止，绝不能当成「没有旧数据」。**
   读旧文件的函数必须支持 `strict=True`：读失败（Excel 独占 / 编码坏 / 列名变）直接抛错 → 退出码 7。
   否则 `old=[]` → 合并只剩新行 → 整文件重写 → **「追加」静默变成「覆盖」，旧数据全丢**。
   这是本类脚本**最危险的失败模式**：用户以为在做加法，实际在做替换，而日志一切正常。
2. **列名与 schema 不符 → 中止。** 旧文件是别的 schema 时盲目合并会写出「看着正常、字段全空」的行。
3. **本次新增 0 条 → 不写文件。** 全是重复数据时不做无意义重写（重写有被占用/中断风险）。

**另外**：追加模式的「是否达标」必须看「**本次新增**」而不是「合并后总数」——
否则 `--n 200` 永远「达标」（旧 100 + 新 1 = 101 也能糊弄过去），告警形同虚设。

### 追加后自证：`--verify --against <基线>`

上面三条防的是「**写入时**」丢数据。但真正要回答的是：
**跑完之后，怎么用机器证明那批老数据还在？**

做法：加一个 `--verify <新CSV> --against <追加前的.bak>`，**逐业务主键做集合包含判断**：

| 检查 | 通过条件 | 失败 |
|---|---|---|
| 基线主键保留 | 基线里**每一个**主键都仍存在于新文件（**超集**） | 退出码 6 |
| 总行数 | 新文件行数 ≥ 基线行数 | 退出码 6 |
| 基线可读 | 基线存在且能解析 | 退出码 6 |

- **为什么不比行数**：行数相同也可能是「丢 50 条 + 多 50 条」。只有逐主键做集合包含才能证明没覆盖。
- 这是**唯一可脱离 LLM 复现的证据**：计划任务里追加完接一句 `--verify --against`，非 0 就告警。
- 自检里要给**反例**写断言：造一个真丢了旧主键的 CSV，断言它必须报错（否则这个功能自己会退化成永远通过）。

## 退出码设计（直接抄）

```
0   成功且达标
2   参数错误
3   环境错误（目录不可写 / 网络不通 / robots 不允许）
4   被站点封禁或出现验证页
5   目标结构变更（解析持续为空）—— 唯一必须人工介入的
6   成功但结果不足目标（产出已写出，需人工判断）；覆盖率有缺口也用它
7   输出文件已存在且未授权覆盖（防误覆盖）
8   已有另一个实例在运行（互斥锁）
130 被中断（断点已存，可 --resume）
```

**要点**：
- 「成功但不足量」必须是**独立的码**（6），不能混进 0 —— 否则监控永远发现不了数据缩水。
- 「防误覆盖」也应是独立码（7），这样监控能区分「忘了加 --force」和真正的抓取失败。
- 「被中断」用 130（POSIX 惯例）。
- 把码表写进 `--help` 的 `epilog`、`--manual` 和排错手册。

## 数量控制

- `--n`：目标条数
- `--preset tiny/small/medium/large`：常用规模组合（展开为 n + per-cat + max-pages），比让人记三个数字友好
- `--max-minutes`：时间预算，超时停止并保存断点（无人值守必需，防无限跑）

## 自检模式（--doctor）该查什么

按性价比排序，前 3 项必查：

1. **选择器自检** ← 最有价值。抓一页跑解析正则，报「解析出 N 条」。
   **站点改版会在这里立刻暴露**，而不是等跑完 30 页才发现全空。
2. **robots.txt 实时判定**（不要硬编码在 banner 里，站点会改规则）
3. **目录可写 / 磁盘空间 / 网络连通**
4. 解释器版本、缓存目录完整性

## 离线自检模式（--self-test）—— 必备件，不是装饰

`--doctor` 查**环境**，`--verify` 查**数据格式**，**都不查语义**。
调度逻辑、正则边界、配额计算这类错误，两者都报「一切正常」，但数据是错的。

> **真实教训（2026-10-08，malaysiayp 采集器）**
> - bug 1：`--per-cat` 被写成「每页上限」而非「每分类上限」→ 顺序模式 14 页全花在 1 个分类，
>   产出 109 条只覆盖 1 类。退出码 0、`--doctor` 全绿、`--verify` 说数据格式完美。
> - bug 2：号码正则 `01\d{7,8}` 只认 9~10 位 → 马来西亚 11 位的 `011-XXXXXXXX` 号段
>   **全部被静默丢弃**（实测缓存里 12 条 11 位一条没进 CSV）。同样退出码 0。
> - bug 3：`--manual` 崩溃 —— 手册正文里的正则 `{7,8}` 被 `str.format()` 当占位符吃掉
>   （**修 bug 2 时引入的**：改一处炸另一处）。教训：文档渲染路径也要有断言。
> - bug 4：`--append` 在旧文件读不出来时静默退化成「覆盖」（见「输出保护」一节）。
>
> 结论：**对语义本身写断言**，是唯一能拦住这类 bug 的办法。

**设计要点**：
- **零网络、零副作用**，30 秒内跑完，纯函数级断言（不依赖真实站点）
- 覆盖：文本清洗 / 号码正则边界（**正例与反例都要**）/ 解析捕获组顺序 /
  **调度配额语义**（用假索引断言「配额吃满后必须跨分类」）/ 输出保护 / 增量合并 /
  覆盖率缺口计算 / 退出码表完整性 / **文档能否渲染** / **文件头版本号 == `__version__`**
- **生成器类函数的测试技巧**：传一个调用方持有的计数 dict，边迭代边改它，
  断言「生成器是否读到最新值」—— 这正是惰性生成器的语义盲区所在
- **必须写反例**：只测「正常输入通过」等于没测。要造「旧数据被覆盖」「坏编码」
  「schema 不符」这类**必须失败**的输入，断言它真的失败了
- 断言里调用会打日志的函数时，用 `logging.disable(logging.CRITICAL)` 临时静音，
  只看退出码，避免自检输出被淹没
- 返回码复用「结构错误」码（如 5），便于监控区分「自检失败」与「环境失败」
- **写进维护清单：改过解析正则或调度逻辑 → 先 `--self-test` → 通过再联网**
- 版本号只留**一个真源**（`__version__`），并写一条断言检查文件头 banner 与它一致，
  防止两处版本漂移

**顺带把诊断信息加进 `--verify`**（能发现「整段数据缺失」这类静默问题）：
- **值域分布**（如号码前缀分布、位数分布）→ 某段整段缺失立刻可见
- **集中度**（如「最大分类占比」）→ ≥90% 说明配额/抽样没生效
- 不要只看「格式合法」，要看「分布是否合理」

## 六个自愈机制（避免「一次异常就崩」）

1. **索引/配置损坏** → 改名保留 `.corrupt` 后**自动重建**，不崩
2. **缓存文件损坏**（上次被杀留下的半截文件）→ 按大小阈值判定并**丢弃重抓**
3. **输出文件被占用**（Excel 开着）→ **降级写 `*_new.csv`**，不抛异常
4. **所有写入原子化** → 一律「写 `.tmp` → `os.replace`」，进程被杀不留半截文件
5. **互斥锁** → 防计划任务重叠；OS 级文件锁，进程死自动释放
6. **信号优雅退出** → `SIGINT`/`SIGTERM` 都先保存断点再退出（返回 130），可无损 `--resume`

## 无-LLM 运行方式（三种都要给）

```
A. Windows 双击 / 计划任务 :  run.cmd --n 100
B. Linux / macOS          :  ./run.sh --n 100
C. 直接调解释器            :  python scrape_x.py --n 100 --seed 42
```

**启动器要点**：
- 解释器查找顺序：`环境变量` → `已知托管路径` → `PATH`，找不到报错返回 3
- `chcp 65001`（Windows）确保 UTF-8 输出不乱码
- **透传退出码**，不要吞掉
- **只在「无参数（双击）」时 pause** —— 否则计划任务会永久挂住 ⚠️ 最易踩的坑
- **`.cmd` / `.bat` 内容用纯 ASCII**，中文说明放 `.md`（批处理编码极易损坏）

**计划任务配置**：
- 程序 = `run.cmd`；**参数必须非空**（留空会触发 pause 挂住）；起始目录 = 脚本目录
- 勾选「不管用户是否登录都要运行」+「失败后重启」
- cron 里加 `PYTHONUNBUFFERED=1`，否则日志不及时落盘

## 无人值守的八个硬坑（2026-10-08 全部实测踩过）

> 坑 1–4 属于 **Windows 计划任务**专项；坑 5 是**通用的缺陷页鉴别与处置**，
> 任何长跑采集都会遇到。

这四个坑的共同点：**任务看起来注册成功了、也会触发，但实际每片都白跑**。
只查 `Get-ScheduledTask` 的 `State=Ready` 完全发现不了。

### 坑 1：`pythonw.exe` 下 `sys.stdout` 是 `None`，`print()` 直接崩

为了「Interactive 身份不弹控制台窗口」，几乎所有人都会把动作从 `run.cmd`
改成 `pythonw.exe script.py`。但 `pythonw.exe` 会把 `sys.stdout` / `sys.stderr`
**显式设为 `None`**，任何 `print()` 立刻抛 `AttributeError`。

如果脚本的 `log()` 是「写文件 + print 到屏幕」，那么它**在第一条日志就会崩**，
每个切片都在启动瞬间死掉。`LastTaskResult` 会是异常码而不是你的业务退出码。

```python
def _ensure_stdio() -> None:
    """pythonw.exe（无控制台）下 sys.stdout/stderr 为 None，任何 print() 都会抛
    AttributeError。把输出改接到文件，既保留现场又不产生控制台窗口。"""
    if sys.stdout is not None and sys.stderr is not None:
        return
    os.makedirs(LOGDIR, exist_ok=True)
    try:
        fh = open(os.path.join(LOGDIR, "slice-stdio.log"), "a",
                  encoding="utf-8", buffering=1)
    except OSError:
        fh = open(os.devnull, "w", encoding="utf-8")
    if sys.stdout is None:
        sys.stdout = fh
    if sys.stderr is None:
        sys.stderr = fh


def main(argv=None) -> int:
    _ensure_stdio()          # ← 必须是第一行
    ...
```

**验证判据**：跑一次之后 `logs/slice-stdio.log` **必须有内容**。
如果它一直不存在，说明任务实际走的是 `.cmd`/`python.exe`（有控制台），而不是 `pythonw.exe`。

**配套**：脚本内部 `subprocess.Popen` 要加 `creationflags=CREATE_NO_WINDOW`，
否则它 fork 出来的 `python.exe` 会自己新建一个控制台窗口弹出来。

### 坑 2：`MultipleInstances=IgnoreNew` + 切片长于触发间隔 → 触发被静默拒掉

`IgnoreNew` 的语义是「上一个实例没结束，就拒掉新触发」，返回
`LastTaskResult = 2147946720`（`0x800710E0`，「操作员或管理员拒绝了请求」）。

所以**切片的时间预算必须严格小于触发间隔**：

| 触发间隔 | `--budget-minutes` | `ExecutionTimeLimit` |
|---|---|---|
| 20 分钟 | 15 | 25 分钟 |
| 60 分钟 | 45 | 75 分钟 |

另外 `ExecutionTimeLimit` 必须大于切片预算，否则任务计划程序会在切片跑完前强杀它。
（`New-ScheduledTaskSettingsSet` 默认是 1 小时，容易忘记改。）

**`LastTaskResult` 速查**：

| 值 | 十六进制 | 含义 |
|---|---|---|
| `0` | — | 正常结束 |
| `267009` | `0x41301` | 正在运行 |
| `267011` | `0x41303` | 从未运行 |
| `267014` | `0x41306` | 被终止 |
| `2147942401` | `0x80070001` | 程序未找到（路径失效） |
| `2147946720` | `0x800710E0` | **被 IgnoreNew 拒掉：上一实例还在跑** |

### 坑 3：编辑正在运行的 `.cmd` → cmd.exe 跳到错误偏移并重复执行

`cmd.exe` 执行批处理时**不把文件读进内存**，而是记住一个**字节偏移**，
每执行完一条命令就从该偏移读下一行。**运行期间编辑这个 `.cmd`，文件长度一变，
偏移就落到错误位置，cmd.exe 会跳回去重复执行某些行。**

实测经过：`task_slice.cmd` 13:58:33 被拉起，13:58:35 执行到 python 行；
14:05 给它加了一个参数（文件变长），那个**还活着的 cmd.exe 在 14:05:47
跳回去把 python 行又执行了一遍**，凭空多出一个实例。
更糟的是旧实例因此**永远不结束**，于是坑 2 把所有后续触发全拒了。

**规避（按推荐度排序）**：
1. 计划任务的动作**不要指向 `.cmd`**，直接指向 `pythonw.exe <脚本> <参数>`。
2. 必须改 `.cmd` 时，先 `Stop-ScheduledTask`，改完再让它触发。
3. 改完立刻 `Get-CimInstance Win32_Process -Filter "Name='cmd.exe'"` 查有没有
   还挂着该批处理的进程，有就 `Stop-ScheduledTask` 清掉。

### 坑 4：注册「静默成功」的三种原因

| 原因 | 现象 | 修法 |
|---|---|---|
| `-RepetitionDuration ([TimeSpan]::MaxValue)` 序列化成 `P99999999DT23H59M59S` | 报「任务 XML 包含格式不正确或超出范围的值」 | 改用 `New-TimeSpan -Days 3650` |
| 上面这个错是**非终止错误**，被 `\| Out-Null` 吞掉 | 注册返回了对象，但 `Get-ScheduledTask` 查不到 | 注册语句必须加 `-ErrorAction Stop` |
| WorkBuddy 等沙箱把对受保护位置的写入**虚拟化后丢弃** | 同一条命令内 `Test-Path` 返回 True，换条命令查不到 | 用 `dangerouslyDisableSandbox` 注册，并**从另一条命令复核** |

### 坑 5：缺陷页的鉴别与「可逆剔除」（2026-10-08 实战）

长时间采集必然遇到「某些页永远抓不到」。**先鉴别性质，再决定处置** ——
三种性质的处理方式完全不同，判错了要么白等，要么误删。

#### 鉴别流程（按顺序，每步都便宜）

**第 1 步：看响应头，不要只看 body。** 这一步信息量最大，很多人跳过。

```python
conn = http.client.HTTPSConnection(host, timeout=25)
conn.request("GET", path, headers={"User-Agent": UA})
r = conn.getresponse()
print(r.status, r.getheader("Content-Length"), r.getheader("Transfer-Encoding"))
print(dict(r.headers))          # ← 关键：Via / Vary / Cache-Control / Server
```

实测案例的响应头直接暴露了技术栈：
`Via: 1.1 Caddy` + `Vary: rsc, next-router-state-tree, next-router-prefetch`
⇒ 站点是 **Next.js App Router + Caddy 反代**，缺陷必然在应用层。

同时能看出缺陷形态：

| 形态 | 响应头特征 | 含义 |
|---|---|---|
| 完全空 | `Transfer-Encoding: chunked` + 无 `Content-Length` | 渲染管线无输出 |
| 硬截断 | `Content-Length: 32768`（= 2¹⁵，精确缓冲边界） | 输出被切断 |
| 正常 | `Content-Length: 36510~37369` | — |

**第 2 步：多变量对照，逐一证伪。** 每个假设一次请求，别省。

| 假设 | 怎么测 |
|---|---|
| 限流 | 把 `--delay` **降下来**（提速）看错误率是否变化。**若提速无影响 ⇒ 不是限流** |
| 封禁 | 查 403 / 429 / 验证页 / 挑战指纹是否出现 |
| CDN 缓存坏响应 | 加**随机** query：`?cb=<random>`，连测两次不同随机值 |
| 需要强制回源 | 请求头 `Cache-Control: no-cache, no-store` + `Pragma: no-cache` |
| 代理 / 传输层 | 绕过代理直连；`Accept-Encoding: identity` |
| 压缩问题 | 要 gzip，看**解压后**长度是否仍等于那个可疑边界 |
| 负载均衡随机 | **并发 3 个相同请求**，看结果是否一致 |
| 前端路由差异 | 若站点是 Next.js，试 `RSC: 1` / `?_rsc=<rand>` / `Next-Router-Prefetch: 1` |

**第 3 步：验证「页面到底有没有内容」。** 抓一个**截断页**，检查：

```python
txt = body.decode("utf-8", "replace")
print("</html> 结尾?", txt.rstrip().endswith("</html>"))   # False ⇒ 被截断
print("列表项出现次数:", txt.count('class="row-item"'))     # >0 ⇒ 有内容
print("最后 120 字符:", repr(txt[-120:]))                   # 停在半截 URL ⇒ 切断
```

如果列表项渲染出来了、分页导航也在，只是末尾被切断 ⇒ **页面有内容，是输出被切断**，
**不是「页面不存在」**。

**第 4 步：验证站点的页数声明是否自洽。** 用「总条数」反算：

```
末页 rows = 13
总条数 5493 = 274 × 20 + 13   ✅ 分毫不差 ⇒ 站点确实有 275 页，我们的预期没错
```

**第 5 步：抽样复核自己的账本。** 从断点库随机抽 20 个「失败页」+ 15 个「成功页」实测：

- 失败记录一致率 100% ⇒ 账本可信，可以直接作为处置依据
- **重点看成功页有没有「由好变坏」的** —— 有，就说明缺陷**不是永久的**

> ⚠️ **这一条改变了处置策略**。实测遇到 `page/213` 由「成功(rows=20)」变为「0 字节」，
> 证明状态会随时间变化、**存在自愈可能** ⇒ **不能永久删除**。

#### 处置：延期，不是删除

```sql
-- 只改 not_before 一个字段，不动 status / attempts / error / rows
UPDATE pages SET not_before = :now_plus_6h
WHERE status='pending' AND error<>'' AND not_before <= :now
--                                       ^^^^^^^^^^^^^^^^^^^
-- 【最关键的一行】只延期「已经到期」的页。
-- 少了这个条件，定时执行会把已延期的页反复推后，让它们永远回不来。
-- 自检方法：第二次执行必须输出「已延期 0 页」。
```

**为什么只改 `not_before` 是安全的**（要逐个校验函数确认，别凭感觉）：

| 校验 | 是否受影响 |
|---|---|
| 完成判定函数 | ❌ 通常不看 `not_before` |
| 数据完整性校验 | ❌ 通常只校验 `status='done'` 的页 |
| 选页条件 `not_before<=?` | ✅ 自然跳过，正是想要的效果 |

**延期时长怎么定**：取「站点缓存期」与「你自己的复检周期」的较小值。
实测案例：站点 `s-maxage=86400`（24h），复检周期 6h ⇒ 取 **6h**。
效果是无效请求比脚本默认退避（上限 1h）**减少约 6 倍**，同时保留一天 4 次自愈捕捉。

**必须配套的两件事**：

1. **备份 + 回滚**：写库前把原始 `not_before` 存 JSON（保留最近 N 个），
   提供 `--rollback`。**说得出就要做得到** —— 输出里承诺了回滚命令就必须真的实现。
2. **报告里区分「真没抓」和「已延期」**：
   ```python
   effective_expected = expected - deferred_count
   effective_pct = done / effective_expected
   ```
   否则进度条会被一批永远抓不到的页**永久压住**，看不出真实推进。

**硬剔除（`status='failed'`）只在延期方案被证明无效后才用** ——
它能让任务立刻收敛，代价是**永久放弃这些页**。

### 坑 6：用「已经坏掉的页」做实验 —— 否则证伪全是无效的（血泪）

**症状**：站点大面积返回 `200 + 0 字节`。做了 5 组对照实验（随机 `?cb=`、
`Cache-Control: no-cache`、`Accept-Encoding: identity`、`--noproxy` 直连、
并发一致性），结论「全部无效」⇒ 判定「与缓存/代理无关，是源站确定性缺陷」。

**错在哪**：那 5 组实验用的是**当时还正常**的页。它只证明了
「**好页**加参数还是好页」，对**坏页**的行为一无所知。

**纠正做法**：拿**已经确认坏掉**的 URL 重做同一组实验。重做后：
`?cb=123456789` → 仍 0 B；`no-cache`/`no-store`/`Pragma` → 仍 0 B；
`identity`/`gzip`/`br` → 仍 0 B；`RSC: 1` → 307。
**结论没变，但现在才有证据支撑。**

**更要命的是**：重做时发现站点其实有**两类**坏响应，恢复时间差两个数量级：

| | A 型 · 短时限流 | B 型 · 坏缓存 |
|---|---|---|
| 表现 | `200` + 0 字节 | `Content-Length: 32768`(2¹⁵) 截断，或持续 0 字节 |
| 恢复 | **分钟级**（实测 < 4 min） | ≥ 24 h（`s-maxage=86400`） |
| 判据 | 静默后重测**会恢复** | 静默后重测**仍坏**，`Etag` 恒定 |
| 分布 | 分类首页为主 | 深层分页为主 |
| 处置 | **降速重试**（别延期） | **延期 25 h** 后复检 |

**必备鉴别脚本**：`probe_recover.py --n 30 --gap 10`
→ 抽样 30 个已报错页，以静默间隔逐个重测，输出**恢复率**。
恢复率高 ⇒ A 型为主（降速重试）；恢复率低 ⇒ B 型为主（延期是对的）。
本项目实测：**深层页恢复率 0.0%** ⇒ B 型为主。

**分层延期**（一个固定时长覆盖不了两类，必须按 attempts 阶梯）：
```
attempts 1   → +30 分钟     # 等 A 型限流窗口过去
attempts 2   → +6 小时
attempts ≥3  → +25 小时     # 跨过 s-maxage=86400
```

**顺带纠正一个错误判据**：「页面短 = 页面坏」是**错的**。
本项目曾把「< 34000 字节」当截断阈值，结果 `art-schools`（19533 B，
含 `</html>`，**只有 1 条记录**）被误判。正确判据只有两条：
**`< 3000 字节` 或 缺 `</html>`**。页面长度随记录数变化，**不能当阈值**。

**方法论一句话**：证伪实验的**输入**必须是「已经复现问题的样本」，
否则你验证的只是「问题不存在时一切正常」。

### 坑 7：多调度器并存 —— 一个空转的旧任务能瞒你很久

**症状**：日志里每 15 分钟出现一次 `rc=7`（output_protected），
但你的计划任务是每 20 分钟、参数正确的。按任务名过滤（`*Malaysia*`）只看到一个任务。

**真相**：还有一个**名字毫无关联**的旧任务（本例叫 `WBProbe3`），
每 15 分钟调用一个**参数过时**的兜底 `.cmd`；该 `.cmd` 的 `ARGS` 里
**缺 `--page-attempts 30`**，与 DB 的 `job_meta.config` 不符 ⇒ 每次都在
**配置检查阶段**就 `rc=7` 退出，**一个请求都没发**。

**为什么难发现**：
1. 任务名不含项目关键词 ⇒ 按名字过滤查不到
2. `rc=7` 在**抓取前**退出 ⇒ 不占锁、不发请求、只写 wrapper 日志
3. 主任务进度在涨，容易忽略日志噪声

**正确做法 —— 按「动作」而不是「任务名」搜索**：
```powershell
Get-ScheduledTask | Where-Object {
  ($_.Actions | ForEach-Object { "$($_.Execute) $($_.Arguments)" }) -match '项目目录关键词'
} | Select-Object TaskName, State
```

**并且**：兜底 `.cmd` 里的 `ARGS` **必须与 DB 的 config 逐字段一致** ——
少一个 `--page-attempts` 就是 `rc=7`。写死参数时把它**抄全**。

**推论**：任何「多入口」设计（计划任务 + 守护 + VBS + 外部自动化）都要
**统一到一个入口**，或让所有入口**共用同一份参数定义**。
否则早晚出现「一个在跑、一个在空转」。

### 坑 8（补充）：队列优先级决定成败 —— 字母序会把你送进坑里

**症状**：采集速率看着还行，但成功率长期 0–33%，进度几乎不涨。

**根因**：选页 SQL 是 `ORDER BY not_before, category, number`。
当所有页 `not_before` 都是默认值 0 时，**实际按分类字母序**推进 ——
于是任务一头扎进 `agricultural` / `apparel-*` 这类**巨型且深层页大量损坏**的分类，
在 600+ 个坏页里空转。

**解法（不动脚本，只改数据）**：用 SQL 调 `not_before` 做优先级，可回滚：
- **未索引分类的首页** → `not_before = -1000`（负数抢占队首）
- **已确认缺陷页** → `not_before = now + 延期`

**注意幂等**：UPDATE 条件必须带 `AND not_before <= now`，
否则定时执行会把页**反复往后推**，永远回不来。

**效果实测**（同一任务、同一站点）：

| | 0 字节率 | 成功率 |
|---|---:|---:|
| 重排前 | 67–100% | 0–33% |
| **重排后** | **0%** | **92%** |

**为什么首页价值最高**：每个未索引分类的首页同时产出
① ~20 条新记录 ② 该分类的**真实页数**（把总量估计从猜测变成事实）。

### 收工后的「终点」要提前设计好

无人值守任务最容易被忽略的是**它到底什么时候算结束**。
如果完成判定要求「零缺口」（例如 `done == expected`），
而站点存在**确定性缺陷页**（同一 URL 恒返回 200+0 字节，重试永远失败），
那么「完成」**永远不可达**，任务会无限空转。

**做法**：
1. 承认这个事实，把脚本的终止信号设计成**专门的退出码**（如 `6 = 重试预算耗尽`），
   而不是靠 `0`。
2. 该退出码下**落盘一份缺口报告**（逐页：分类 / 页码 / 尝试次数 / 错误），
   人类可读 `.md` + 机器可读 `.json` 各一份。
3. 写一个**耗尽标记文件**（含 `next_recheck`），守护与切片在标记未过期时
   **直接返回、不发起任何请求**——否则计划任务每 20 分钟刷一个空日志。
4. 复检周期取 **6 小时**：覆盖站点 CDN 的 `s-maxage=86400`（坏响应最多缓存 24h），
   一天 4 次足以在站点恢复后接上，又不刷垃圾日志。
5. **不要靠加大重试次数解决**：退避封顶 3600s 时，30 次已覆盖约 26 小时窗口，
   继续加只是拉长空转时间。

**正确验收口径**：全量 CSV 分片（逐片 SHA256 账本）+ 断点库 + 缺口清单，
而不是「退出码 0」。

## 故障处置表模板（写进 TROUBLESHOOTING.md）

| 现象 | 根因 | 处置 |
|---|---|---|
| 空响应 / 0 字节 | 软限流（不是 429！） | 退避重试 6s→12s→24s；频繁则调大 `--delay` |
| HTTP 403 / 挑战页 | 被封 | **立即停手**，等数小时，调大 `--delay`；不要绕验证码 |
| 解析持续为 0 条 | 站点改版 | 抓一页存本地 → 对照正则捕获组顺序 → 改完跑 `--doctor` 验证 |
| 结果不足目标 | 限流/越界跳过 | 调大 `--max-pages` 或调小 `--n` |
| 输出文件 PermissionError | 被 Excel 占用 | 已自动降级；关掉占用程序 |
| 中文乱码 | 控制台编码 | 强制 UTF-8 输出 + `chcp 65001` |
| 数据里有 `�` | **源站本身脏** | 入库前清洗（`html.unescape` + 去 U+FFFD/控制字符） |

## 关键工程细节（容易漏）

- **限流形态不止 429**：很多站返回 **200 + 0 字节**。必须把「空响应/页面过短」当**可重试**，
  否则会误判成封禁而中止整个任务。这是最常踩的坑。
- **别猜 `--delay`，让脚本自己去撞一次墙**（内置 `--stress-test` 探针）。实测数据常与直觉相反：
  - **形态是「概率性随机丢弃」，不是「跑满 N 次就封」**：30 次连发 @0.3s → 10 次 0 字节（33%），
    但**交错出现**、**最长连续只有 2 次**，且**硬封禁 0 次**。所以「第一次出现 0B」这个指标毫无意义。
  - **成功率对间隔几乎不敏感**：1s=70% / 2s=70% / 3s=80% → 瓶颈是**配额回补速度**，不是请求速率。
    结论：**把 `--delay` 从 2s 拉到 10s 不会减少限流，只会让总耗时变 5 倍**。
    正确策略是**保持 2s + 靠退避吸收**。
  - **恢复时间要用「连续 N 次成功」判定**：单次成功只是运气。实测 5s 时成功 0 次，
    15s 才第 1 次成功，**稳定恢复 ≈41s**。只测一次会把恢复时间严重低估。
  - **退避方案要量「吸收率」**：6s→12s→24s 实测吸收 **4/4 = 100%**（平均 1.75 次尝试）
    → 证明**不需要并发/代理/换 IP**。
  - 各间隔测试之间要**插入冷却**，否则「先测的占便宜」，结论有顺序偏差。
- **区分异常语义**：`Fatal`（被封，立即中止）vs `Unavailable`（404 页码越界，只跳过该页）。
  不要一律中止。
- **页码越界返回 404 是正常的**，不该中止。
- **清洗源站脏数据**：`html.unescape` + 去 `U+FFFD` + 去控制字符 + 折叠空白。
  注意**显示文本**常有乱码，而结构化字段（`href` 里的值）通常干净 —— 优先取结构化字段。
- **Windows 编码**：`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。
- **meta 侧车文件**：`out.meta.json` 记录本次参数/条数/覆盖范围/退出码/索引时间，供长期追溯。

## 环境备注（本机 Windows 沙箱，实测）

- Bash 工具里调 `cmd` / `powershell.exe` 被沙箱拦；
  **PowerShell 工具里调 `cmd /c` 也被拦**（"cmd.exe cannot be used from the PowerShell tool"）。
  ✅ 可行：PowerShell 工具里用 `& ".\run.cmd" args` 直接调用 `.cmd`。
- **PowerShell 工具 stdout 常被吞掉** → 用**副作用验证**：查 `logs/` 是否新增文件、
  查 `netstat` 端口等，不要依赖 stdout。
