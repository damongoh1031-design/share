# DB3 CallApp（s.callapp.com）—— 限流、污染与失效全过程

> 一手实测，2026-10-06。**结论：DB3 已不可用于批量取名字，且它的失效方式是「静默返回随机假名」，
> 比直接封禁危险得多。** 这份文档记录完整的测验方法与判据，供以后复核该源是否恢复。

---

## 1. 端点与参数（先纠一个长期错误）

```
https://s.callapp.com/callapp-server/csrch
    ?cpn=%2B<国际号，如 60162281297>
    &myp=gp.106898501948939491020     ← 必需，App 包名
    &ibs=0&cid=0
    [&tk=0011243853]                   ← ⚠️ 已失效，带上会 513
    [&cvc=2206]                        ← ⚠️ 已失效，带上会 512
```

### ★ 参数逐项还原实验（2026-10-06 10:24）

| 参数组合 | HTTP | `X_C_CODE` | 结果 |
|---|---|---|---|
| 全参数（含 `tk`+`cvc`） | **513** | **-4** | 空体 |
| 去掉 `Host` 头 | 513 | -4 | 空体（**与 Host 头无关**） |
| 只留 `tk`+`cvc` | 512 | -3 | 空体 |
| **只留 `myp`** | **200** | **1** | **`{"name":"Jacky Sidhu"}`** ✅ |
| 只留 `cvc` | 525 | 0 | 空体 |
| 全裸（只有 `cpn`） | 525 | 0 | 空体 |

**结论**：`tk=0011243853` / `cvc=2206` 这两个硬编码值**已失效**（返回 `X_C_CODE:-4/-3`），
带上它们必然 `513`。**去掉 `tk`+`cvc`、只保留 `myp`+`ibs`+`cid` 才能拿到 200。**

`X_C_CODE` 语义（实测归纳）：

| 值 | HTTP | 含义 |
|---|---|---|
| `1` | 200 | 正常返回 |
| `0` | 525 | 缺必需参数（`myp` 没给） |
| `-3` | 512 | 参数组合非法 |
| `-4` | 513 | `tk` 无效 |

⚠️ 仓库 `phone-number-lookup` 里的 `CallApp.send_request()` **写死了 `tk` 和 `cvc`** ——
所以**直接跑原版脚本永远拿到 513**，必须先改 URL。

## 2. 污染现象：同一号码每次返回不同名字

修好参数后（去掉 `tk`/`cvc`）短时间内确实拿到了**高质量真实数据**：

```
60127680101 -> '福来'                60127680303 -> '李翠英'
60127680120 -> 'cheng siew'          60127680328 -> 'ktp thk group'
60127680168 -> 'antie js'            60127680026 -> 'faisal affini'
60127680042 -> 'siew fui ling'       60127680151 -> 'izah amk'
```

**全是马来西亚/华人姓名形态**（有中文、有大小写混排、有商家名），覆盖率 **80%**（300 样本 241 命中）。

约 15 分钟后（期间被打过一轮 300 次压力测试），同一号码变成：

```
60127680101: ['Rayford Moyle', 'Billy Goggin', 'Kevyn Leeds']         ← 3 次 3 个名字
60127680303: ['Eulogio Hannah', 'Nefi Caplinger', 'Chez Bergen']     ← 3 次 3 个名字
60162281297: 10 次查询 -> 8 个不同名字，零重复
```

**形态变成了美式英文姓名组合（First Last，全首字母大写），每次查询都不同。**

## 3. 关键判据：幂等性（这是唯一可靠的检测手段）

### ❌ 不能用的判据

| 判据 | 为什么失效 |
|---|---|
| HTTP 状态码 | 污染后**仍是 200**，而且 `512`/`525` 混在里面，看起来像"偶发网络抖动" |
| 名字形态 | 假名 `Maryam Thrush` 完全符合"人名"形态，肉眼分辨不出 |
| 覆盖率 | 污染后覆盖率**反而升到 90%**（比真实时还高），极具欺骗性 |
| 请求速率 | 见下节，与速率**无关** |

### ✅ 唯一可靠判据

> **同一号码连查 N 次（N≥3），返回的名字必须完全一致。**

不一致 ⇒ 该源当前输出**随机垃圾**，必须立刻停止一切批量写入。

已固化为脚本：`scripts/check_idempotent.py`
```bash
"$PY" scripts/check_idempotent.py --source db3 --phone 60162281297 --repeat 5 --gate
# 稳定 → exit 0 ；不稳定 → exit 9（--gate 模式供驱动器当门禁）
```

## 4. 污染与速率无关（三组对照实验）

固定同一号码连续查询，统计"不同名字数"（=1 才算真实）：

| 实验 | 请求间隔 | 次数 | HTTP 分布 | 不同名字数 | 判定 |
|---|---|---|---|---|---|
| A 极慢速 | **10 秒** | 12 | 200×11, 512×1 | **11/11** | ❌ 污染 |
| B 中速 | 1.0 秒 | 60 | 200×55, 512×5 | **55/55** | ❌ 污染 |
| C 快速 | 0.1 秒 | 60 | 200×54, 512×6 | **54/54** | ❌ 污染 |
| D 慢速长跑 | 3 秒 | 80+ | 200×71, 512×9 | **71/71** | ❌ 污染 |

**每 10 秒才查 1 次也照样 100% 随机** ⇒ 不是限流触发，是**该源对这批号码整体已降级为假数据**。

⚠️ 注意 `512`/`525` 的占比在各速率下都稳定在 8–10% 左右 —— 这**不是**限流信号，
而是这个源固有的抖动率，不要去"优化"它。

## 5. 时序还原

| 时间（2026-10-06） | 事件 |
|---|---|
| 10:00 | 修好参数（去掉 `tk`/`cvc`），覆盖 80%，名字真实且稳定 |
| 10:05–10:10 | 一轮 300 次连续压力测试（成功 246 次） |
| 10:20 | 全线 `513`（`tk` 问题暴露） |
| 10:24 | 去掉 `tk` 恢复 200，但**内容已变成随机假名** |
| 10:33–10:50 | 系统性测验：确认 100% 随机、与速率无关、不可自动辨别 |

**推断**：那 300 次压力请求触发了服务端对该 key 的**降级**（而非封禁）。
DB1 的做法是明确返回 `status: -10` 拒绝；DB3 的做法是**继续返回 200 + 假数据** ——
后者危险得多，因为任何只看"有没有名字"的流程都会被静默污染。

## 6. 操作结论

1. **不要用 DB3 批量取名字。** 当前它对马来西亚号码 100% 返回随机假名。
2. **任何批量写名字列之前，必须先跑 `check_idempotent.py --gate`。** 这一条是硬门禁。
3. 想复核 DB3 是否恢复：跑幂等性抽检（同一号码 3 次同名 = 恢复），
   **不要**看覆盖率（污染时覆盖率更高）。
4. `phone-number-lookup` 仓库里的 `CallApp` 类**默认就是坏的**（写死失效的 `tk`），
   即便将来 DB3 恢复，也要先改 URL 才能用。
5. 假的典型特征（可供人工复核）：**全首字母大写的 `First Last` 美式姓名**，
   与马来西亚号码的族群构成（马来/华人/印度）明显不符。

## 7. 对 DB1 的启示（横向对比）

| | DB1 aunumber | DB3 CallApp |
|---|---|---|
| 失效表现 | HTTP 200 + `{"status": -10}` | HTTP 200 + **随机假名** |
| 是否可自动识别 | ✅ 判 `status < 0` | ❌ **必须做幂等性抽检** |
| 污染风险 | 无（明确拒绝） | **极高**（静默污染） |
| 2 次失败模式 | 一致（都是负数 status） | 参数失效（513）→ 数据污染（假名），两段式 |

⇒ **一个愿意明确报错的源，比一个"永远返回 200"的源更值得信任。**
评估新数据源时，幂等性优先级高于覆盖率。

## 8. 2026-10-07 复测：仍未恢复 + ★ 用已知真名做 ground truth 的验证法

### 方法（可复用，比单纯幂等性更强）

表 `SHOPEE LIST 01` 的 A 列已有 **1683 个由 DB1 查出的名字**。
把「A 列非空」的行当**黄金标准**，拿同一号码去问 DB3：

- **判据一（幂等）**：同一号码连查 3 次必须同名
- **判据二（一致性）**：DB3 的名字应与 A 列已知名**相同**

两条都过才算「DB3 返回真实资料」。只做幂等性还不够 ——
万一 DB3 稳定地返回**另一个源的合法数据**（同名率高但都与 DB1 不同），
幂等性会通过、一致性会失败，这时需人工判断而非直接采信。

脚本：`Temp/db3_verify.py`（分层抽样覆盖全表，`--n` 抽样数 / `--repeat` 次数）

## 9. 附：运行环境的坑（2026-10-07 踩到）

`C:/Users/Admin/AppData/Local/Temp/` 下存在一个 **`inspect.py`**
（Steam Workshop 查询脚本，名字起错），会**抢占标准库 `inspect` 模块**：

```
File "C:\Users\Admin\AppData\Local\Temp\inspect.py", line 7
    ids=[int(x) for x in sys.argv[1:]]
ValueError: invalid literal for int() with base 10: '--n'
```

任何 **cwd 在 Temp 下**运行的 Python 脚本都会中招（`requests` → `urllib3` → `importlib.metadata` → `inspect`）。

**规避**：把脚本放进子目录再运行，例如 `Temp/db3verify/`。
（`db1_batch.py` 没中招只是因为它的依赖链没触到 `inspect`，不代表安全。）
**教训**：不要往 `Temp` 根目录放与标准库同名的 .py 文件。

> ✅ **2026-10-08 已根治**：该文件已改名为 `Temp/steam_workshop_inspect.py`（功能保留）。
> 但注意：**只换 cwd 不够** —— Python 会把*脚本所在目录*也加进 `sys.path[0]`，
> 所以把脚本放在 `Temp` 下同样中招（2026-10-08 又踩一次）。根治办法只有改名或移走。

> **DB3 对任何号码都返回名字** ⇒ 它连「这个号有没有记录」都不含信息。
