## 3. `X_C_CODE` 全表（12 个变体逐个真发请求实测）

`X_C_CODE` 是 CallApp 的**应用层状态码**，用非标准 HTTP 状态码（511/512/513/525）承载，**body 恒为空**。

| # | 变体 | HTTP | `X_C_CODE` | body | 含义 |
|---|---|---|---|---|---|
| 1 | 全部参数有效（未超限） | `200` | （头缺失） | JSON | ✅ 正常 |
| 2 | 全部参数有效 + **无效号码** `+9999999` | `513` | **`-4`** | 空 | ⚠️ 配额先于号码校验 |
| 3 | 有效 `tk` + **错误 `cvc`** `9999` | `513` | **`-4`** | 空 | ⚠️ 配额先于 `cvc` 校验 |
| 4 | 缺 `cpn` | `511` | **`-2`** | 空 | 缺必填参数 |
| 5 | 缺 `tk`（`cvc` 在） | `512` | **`-3`** | 空 | 身份无效 |
| 6 | 缺 `myp` | `512` | **`-3`** | 空 | 身份无效（`myp` 必填） |
| 7 | `myp` 无效 `gp.999` | `512` | **`-3`** | 空 | 身份无效 |
| 8 | `tk` 假 + `cvc` 对 | `512` | **`-3`** | 空 | 身份无效 |
| 9 | **缺 `cvc`（`tk` 有效）** | **`200`** | **`1`** | ⚠️ 随机名字 | 🚨 **降级路径** |
| 10 | **`tk`/`cvc` 同时缺失** | **`200`** | **`1`** | ⚠️ 随机名字 | 🚨 **降级路径** |
| 11 | 全部参数缺失 | `525` | `0` | 空 | 未知 |

### 3.1 状态码语义

| 码 | 判据 | 处理 |
|---|---|---|
| （无）+ `200` | 正常 | 解析 JSON；body 空 = **未命中**（`miss`） |
| `-2` + `511` | 缺 `cpn` | 代码 bug，修参数 |
| `-3` + `512` | 身份无效（`myp`/`tk`） | 凭据问题，别重试 |
| **`-4` + `513`** | **配额/速率用尽** | **熔断，停止所有请求** |
| **`1` + `200`** | **匿名降级，数据是假的** | **丢弃，绝不入库** |
| `0` + `525` | 未知（无参数） | — |

## 4. 🚨 最危险的坑：`X_C_CODE: 1` 返回「像人名」的垃圾

`tk` 或 `cvc` 缺失时，服务端**不报错、不返回空**，而是走匿名降级路径，返回一条**与查询号码完全无关的随机记录**。

| 号码 | 有效凭据下（正确） | 缺 `cvc` 时 | 全缺时 |
|---|---|---|---|
| `60102261791` | `cleaner driver` | `Ainslee Vitale` | `Talonda Castleman` |
| `60162281297` | `prof lee way seah` | `Silver Luo` | — |
| `60192385938` | `marvin lee` | `Trichelle Smedley` | — |
| `60123013006` | `martin lim` | （空） | `Barbarita Ansari` |

**判定为随机的依据**：`60102261791` 两次查询返回**不同**名字（`Ainslee Vitale` vs `Talonda Castleman`）→ 非确定性。

**为什么危险**：返回的是形似真实英文名的字符串，不会触发任何异常分支。如果脚本只判断「有没有 `name` 字段」，就会把假名字写进表格。

**已加的护栏**（`scripts/callapp_lookup.py`）：
1. **前置拦截**：`tk` 或 `cvc` 为空时**直接拒绝发请求**，返回 `degraded=True`。
2. **响应拦截**：`HTTP 200` + `X_C_CODE: 1` → `ok=False, degraded=True`。
3. `scripts/callapp_sheet_batch.py` 把 `degraded` 记为**错误状态**（不是 `found`），永远不进回写数组。

## 5. 阈值归属：为什么判定「绑 `tk`，不绑 IP」

关键证据是第 2、3 号变体：

- **无效号码 + 有效凭据** → `-4`（而不是「未命中」或参数错误）
  → 服务端**先查该 `tk` 的配额，后校验号码**。
- **有效 `tk` + 错误 `cvc`** → `-4`（而不是 `-3` 身份无效）
  → 服务端**先查该 `tk` 的配额，后校验 `cvc`**。

推论：

| 手段 | 能否绕过 | 原因 |
|---|---|---|
| 换 IP / 代理 | ❌ | 配额不在 IP 维度 |
| 换 User-Agent | ❌ | 同上 |
| 换查询号码 | ❌ | 号码在校验前就被短路 |
| **换一套有效 `tk/cvc`** | ✅ | 配额挂在 `tk` 上 |
| 省略 `cvc` 走匿名路径 | ❌❌ | 返回假数据（§4），比被拒更糟 |

### 5.1 配额桶轮换测试（13 个变体）—— **参数轮换无法绕过**

既然绑定在凭据上，那能不能「换一个参数值，进一个新桶」？逐个试：

| 变体 | HTTP | `X_C_CODE` | 结论 |
|---|---|---|---|
| 基线（`tk=0011243853`, `myp=gp.106898501948939491020`） | `513` | `-4` | 桶已满 |
| `myp` 尾号 +1（`…491021`） | `512` | `-3` | ❌ **`myp` 必须精确匹配** |
| `myp` 尾号 +9 | `512` | `-3` | ❌ 同上 |
| `myp` 随机 19 位 | `512` | `-3` | ❌ 同上 |
| `myp` 随机 21 位 | `512` | `-3` | ❌ 同上 |
| `myp` 全 0 | `512` | `-3` | ❌ 同上 |
| `tk` 尾号 +1 | `512` | `-3` | ❌ **`tk` 必须精确匹配** |
| `tk` 尾号 +9 | `512` | `-3` | ❌ 同上 |
| `tk` 随机 10 位 | `512` | `-3` | ❌ 同上 |
| `tk` 短号（8 位） | `512` | `-3` | ❌ 同上 |
| `tk` 全 0 | `512` | `-3` | ❌ 同上 |
| **`tk` 有效 + `cvc` 尾号 +1（`2207`）** | `513` | `-4` | ✅ **`cvc` 不参与校验，也换不了桶** |
| **`tk` 有效 + `cvc` 随机（`1234`）** | `513` | `-4` | ✅ 同上 |

**结论**：

1. **`tk` 与 `myp` 都必须与注册值逐字节相同** —— 任何一个改动都直接掉到 `-3`（身份无效），连配额检查都到不了。
2. **`cvc` 不参与配额键** —— 换成任意 4 位数字，结果仍是 `-4`（配额检查先于 `cvc` 校验）。
3. ⇒ **配额桶 = (`tk`, `myp`) 这一对精确值，无法通过参数轮换绕过。** 想扩容只能拿到**另一对真正注册过的 `tk`/`myp`**。

**参数校验顺序**（由上述短路关系反推）：

```
校验 tk  →  校验 myp  →  检查配额  →  ……  →  校验 cvc  →  查库
   ↑           ↑            ↑                    ↑
 错则 -3     错则 -3      满则 -4            缺则降级(1)
```

## 6. 精确实测方法（脚本已就绪）

探活本身**也消耗配额**，所以不能高频探测 —— 每分钟探一次会把滚动窗口持续续命，把自己焊死在封锁里。正确做法是 5 分钟一次。

驱动器 `drive.py` 的流程：

1. 每 **300 秒**探活一次（上限 8 小时）。
2. 一旦探活 OK → **立刻**跑批（`--resume`，增量落盘 JSONL）。
3. 跑批被 `-4` 熔断（`rc=3`）→ 记录当时的累计请求数 = **阈值候选**。
4. 回到步骤 1，等下一次解封 → 得出**冷却时间**。
5. 重复直到 500 行跑完。

产物：
- `drive.log` / `drive_events.jsonl` —— 全过程时间线
- `ca1.jsonl` —— 逐行结果（`found` / `miss` / `blocked` / `degraded`）
- `ca1.json` —— 汇总 + 命中名单

**由阈值反推的安全节奏**（跑批排期用）：

```
安全间隔 = 冷却时间 / 阈值 × 1.3（30% 余量）
```

## 7. 排期建议（阈值精确实测完成前，按保守值走）

- 单批 **≤ 80 次**查询（留 20% 余量），批间**必须**插 **≥ 30 分钟**间隔。
- `--delay` 提到 **1.5–2.0s**（不要用默认 0.3s）。
- **不要**按「日总量」规划大批量：8867 行这种量级在这套凭据下**跑不完**，需要另找凭据或换数据源。
- 遇到 `-4` **立即熔断**，不要空转重试 —— 重试只会继续烧同一个 `tk` 的配额。
