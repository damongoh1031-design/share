# CLI 全命令实测 → 可信文档 / 运维手册

## 何时用

- 用户给了一个 CLI 工具（新发布的、或版本刚升级），要求「把教程写准」「每条命令都测一遍」。
- 已有教程/文档与真实行为不符，需要找出偏差。
- 用户问「怎么长期运维」，需要拿实测数据（内存基线、回收时机、磁盘占用）而不是文档推断。

**不适用**：只是查某个命令怎么用（直接读 `--help` 即可）。

## 核心原则

1. **一手数据优先于文档**。官方文档常滞后于实际行为，尤其是新 GA 的工具。所有结论必须能在本机复现。
2. **只跑不碰生产**。用独立的测试对象（临时容器 / 临时目录 / 测试分支），全程不碰用户正在跑的东西。
3. **有始有终**。测完必须清理，并在结尾验证生产对象仍健康。
4. **诚实标注未核实项**。没测过的不要写成结论；厂商数据要标明是厂商数据。

## 执行步骤

### 第 1 步：建立命令清单

```bash
# 顶层命令树
<tool> --help
# 逐条导出子命令帮助（关键：先拿到全部命令名，别漏）
for c in "container cp" "image save" "network create" ...; do
  echo "########## $c ##########"
  <tool> $c --help
done > /tmp/help_all.txt 2>&1
```

- 帮助文本通常很长 → **落盘到文件再读**，不要指望一次性塞进上下文。
- 注意命令是否有**顶层别名**（如 `run` 能省略 `container` 前缀）。别名缺失是最常见的坑之一。
- 记录哪些命令**不存在**（用户会照着文档写错）。

### 第 2 步：设计测试分组，跑「只读 → 变更 → 边界 → 清理」

| 组 | 内容 |
|---|---|
| A 只读 | `list` / `inspect` / `info` / `version` / `stats` |
| B 变更-基础 | `create` / `start` / `exec` / `logs` / `stop` / `restart` / `kill` |
| C 变更-进阶 | `cp` / `export` / `save` / `load` / `import` / `tag` / `build` |
| D 资源 | `network *` / `volume *` / `registry *` |
| E 运维向 | `events` / `info` / `settings` / 会话类 |
| F 边界与负例 | 故意传错参数、故意让目标不存在、故意让对象被引用 |
| G 清理 | 删掉所有测试对象 + 验证生产对象健康 |

**写测试脚本，不要一条条手敲**：

```bash
#!/bin/bash
export MSYS_NO_PATHCONV=1          # Git Bash 下必须，否则容器内路径被转成 Windows 路径
W="/path/to/tool.exe"
OUT="/tmp/test_b.txt"
: > "$OUT"
run() {
  echo "" >> "$OUT"
  echo "=== \$ tool $* ===" >> "$OUT"
  "$W" "$@" >> "$OUT" 2>&1
  echo "--- exit=$? ---" >> "$OUT"     # 退出码必须记！很多坑体现在 exit code 上
}
run container create --name t1 -e FOO=bar alpine sleep 300
```

**每一条都记三样：命令、stdout+stderr、exit code。**

### 第 3 步：必须覆盖的「高危行为」（这些最容易出 bug）

- **文件复制/传输**：目标不存在会怎样？目标是文件而非目录会怎样？符号链接怎么处理？
- **`prune` 类命令**：有没有 `-f`？没 `-f` 会不会交互式等确认？（脚本里必挂）
- **格式化输出**：`--format` 支持哪些值？`-f` 是 `--format` 的别名还是别的选项（如 `--filter`）？支持模板语法吗？
- **流式命令**（`logs -f` / `events`）：会不会自己退出？脚本里要不要 `timeout`？
- **导出/归档**：对运行中对象是否有限制？
- **删除**：被引用时行为如何？要不要 `--force`？

### 第 4 步：探测交互式命令的默认配置

很多 CLI 的配置文件**首次运行才生成**，且生成后会打开编辑器阻塞。

```bash
# 用 timeout 让它先落盘配置文件、再杀掉编辑器，然后直接读文件
timeout 8 <tool> settings >/dev/null 2>&1
cat "<config-path>"     # 拿到全部字段与默认值，比查文档准
```

配置路径通常能从 `<tool> info` 或 `--help` 里找到。

### 第 5 步：写文档时用「三态标记」

| 标记 | 含义 |
|---|---|
| ✅ | 实测通过 |
| ⚠️ | 可用但有陷阱 |
| ❌ | 实测失败或不存在 |

配一张**坑速查表**（现象 → 原因/正解），按「会不会让你卡住」排序。这比按字母序排列命令表有用得多。

### 第 6 步：运维章节（对标用户已知的工具）

用户说「类似 X 目前的运维模式」时，做一张**维度对比表**，逐项给出对应方案：

管理界面 / 空闲回收 / 开机自启 / 崩溃自愈 / 快照回滚 / 磁盘回收 / 更新 / 监控 / 企业管控

再补：
- **运维节律**：日 / 周 / 月 / 事件驱动，每格写具体命令
- **备份方案**：分层（镜像 / 数据 / 整体），每层给命令
- **容量规划**：用实测数字（空载内存基线、单对象开销、闲置后占用）给出公式
- **自愈脚本**：如果工具本身没有 restart policy，写出巡检+拉起的脚本
- **「什么时候该换方案」**：明确列出本工具的短板，别只讲优点

### 第 7 步：清理与验证（不能省）

```bash
tool remove -f <test-object>
tool prune -f
tool list -a        # 确认只剩生产对象
tool image list
# 生产对象健康检查
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:PORT/health
```

## 扩展：验证「机制类宣称」（不止命令行为）

用户常拿一句官方简化说法来问，比如「X 让网络更方便」「Y 让读写更快」。这类宣称**必须拆成可观测的量**再验，否则只能复述厂商话术。

### 拆解套路

| 宣称类型 | 拆成什么 | 怎么测 |
|---|---|---|
| 「流量以 X 身份发出」 | 边界两侧的连接表 | **在边界两侧同时**取连接表，比对远端是否一致，再查宿主的 `OwningProcess` 进程名 |
| 「性能更快」 | 分区间的绝对数值 | 大文件顺序 I/O + 小文件元数据，**分开测**（结论往往相反） |
| 「兼容 / 继承某配置」 | 实际配置文件内容 | 进容器 `cat /etc/resolv.conf`、`cat /proc/mounts`，别信文档描述 |
| 「支持某语义」 | 边界用例矩阵 | 直接构造：大小写、符号链接、FIFO、稀疏文件、文件锁，再去宿主侧用原生工具复核 |
| 「相比旧方案快 N 倍」 | 能否复现对照环境 | **如果不能，就明确写「无法验证」，不要背书** |

### 性能测试的硬性要求

- **必须用不可压缩数据**：`/dev/urandom`，不要 `/dev/zero`（会被优化掉）。
- **写必须 `conv=fsync`**，否则测的是页缓存。
- **读必须 `iflag=direct`**（O_DIRECT）：容器内通常**没有权限** `drop_caches`，O_DIRECT 是唯一可靠的冷读手段。
- **小文件用 `tar` 解包/打包做单进程测量**，**绝不用 shell 循环 + `cp`**——后者的 fork 开销会完全淹没文件系统差异。
- **每个维度单独报告**，不要合成一个「综合分」。

### 元数据瓶颈的定位技巧

如果小文件慢、大文件不慢，做这一组对照就能定位：

```
ls -f  <dir>   # 只枚举目录项，不 stat  → 如果这步很快
ls -l  <dir>   # 枚举 + 每个文件 stat    → 如果这步很慢
```

→ 说明瓶颈是 **per-file 元数据往返**，不是目录枚举。这个区分直接决定优化方向（合并文件 vs 换文件系统）。

### 边界两侧取证的通用模式

```bash
# 1. 在被测对象内制造一个可识别的长连接/长操作
<tool> exec <obj> sh -c "<长操作> &"
# 2. 立刻在宿主侧抓快照，按归属进程过滤
#    Windows: Get-NetTCPConnection -State Established | % { $p=Get-Process -Id $_.OwningProcess; ... }
#    Linux:   ss -tnp | grep <pid>
# 3. 回到被测对象内抓对照快照
<tool> exec <obj> netstat -tn
# 4. 两边比对：远端地址相同、本地地址/端口不同 → 说明中间有转换层
```

**用 `timeout` 包住所有可能挂起的采集命令**，用 `&` 制造并行的长操作。

### 判定「两个工具是否共享同一后端」（做生态/兼容性调研时必用）

用户常问「A 和 B 能不能互相管理 / 能不能共存」。**别靠文档推断，按下面 5 步实测**：

```bash
# 1. 先各自找后端：进程 + socket/管道。这决定它们是同一个引擎还是两个。
ps -eo pid,comm,args | grep -E '<daemon>'        # 后端进程与启动参数
ls -la /run/ /var/run/ | grep -i sock            # unix socket
#   Windows: 枚举 \\.\pipe\ ；看 registry 里 Uninstall 项判断某产品是否还在

# 2. 造一个「用 A 创建的对象」，再问 B 能不能看见
A create ... && B list

# 3. 造一个「用 B 创建的对象」，再问 A 能不能看见   ← 必须双向做
#    不对称是常态：往往是 B ⊃ A（一方是另一方的超集）
B run ... && A list

# 4. 可见性之后测「可控性」：读(inspect/logs) + 写(exec/stop/rm) 各来一次
#    报错信息本身是证据（如 E_UNEXPECTED / not found / 权限拒绝）

# 5. 若怀疑有「私有记账」，做反证实验
#    把 A 对象身上的所有特殊标记（标签/注解/元数据）原样复制到 B 对象上，看 A 是否认领
#    若仍不认领 → 说明存在独立注册表，不是纯标记过滤
```

**推论要点**：
- 两个工具「共享同一引擎」**不等于**「互相可见」——中间可能有私有注册表/记账层。
- 反过来，**可见不等于可达**：Windows 宿主上的端口可达性要单独测（见下条）。
- 测「宿主侧端口是否真的通」**绝对不要用 curl**：很多沙箱/代理环境对 HTTP 做了拦截，**未监听的端口也返回 502**（先用一个确定没监听的端口做对照，立刻能识别）。
  ✅ 用原始 TCP：PowerShell `New-Object System.Net.Sockets.TcpClient` + `BeginConnect`；Linux `bash -c 'exec 3<>/dev/tcp/host/port'`。
- 判断某产品是否还在系统上，**别只看 PATH**：查注册表 Uninstall 项 + 安装日志（`%LOCALAPPDATA%\<vendor>\install*.txt` 常留完整安装/卸载记录）。

### 「容器/VM 运行时能力边界」实测清单（对比选型时按这张表跑一遍）

文档只会写「支持容器」，不会写「哪些容器跑不起来」。**下面每一条都能在 5 分钟内实测**，且每一条都真实拦过人：

```bash
# 1. 特权与命名空间（直接看 CLI 是否接受这些 flag）
<cli> run --privileged / --cap-add / --pid host / --device   # 报「选项名未被识别」= 硬缺失

# 2. systemd 容器（最能暴露问题的一条，且失败时常常没有日志）
<cli> run --name sdtest -d <systemd镜像>     # 别加 --rm，否则失败后被自动清掉看不到证据
<cli> inspect sdtest | grep -E 'ExitCode|StartedAt|FinishedAt'   # 9ms 内 Exited(255) = 跑不起来

# 3. cgroup 可写性（systemd 失败的直接根因）
<cli> run --rm <镜像> sh -c "mkdir /sys/fs/cgroup/probe"     # Read-only file system = 不可用

# 4. guest 内路径 bind mount（容器工具常把源解析成宿主路径）
<cli> run --rm -v /唯一探针名:/x <镜像> sh -c "ls -la /x"    # /x 空 + 宿主多出对应目录 = 被误解析
#    ⚠️ 用独一无二的名字，跑完记得删宿主侧被创建的那个目录

# 5. VM 级能力：systemd / 内核模块 / 嵌套虚拟化
ps -p 1 -o comm=                        # init ≠ systemd
modprobe <常见模块>                      # 能否加载
modprobe kvm_intel; ls -la /dev/kvm      # Operation not supported / 无设备 = 无嵌套虚拟化

# 6. 宿主侧真实占用（别信配额，信 commit 与工作集）
#    Windows: Get-Process | ? {$_.ProcessName -match 'vmmem|<产品名>'} |
#             select ProcessName,@{n='WS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}},
#                    @{n='Commit_MB';e={[math]::Round($_.PagedMemorySize64/1MB,1)}}
```

**判读要点**：
- 「配额」和「实际占用」可能差 6 倍（动态内存 + page reporting）→ **两个数都要报**，并说明回收机制。
- 容器类 CLI 常有**每次调用固定延迟**（跨中继通信）→ 用 `date +%s%N` 前后差测 3 次取中位，别只测一次。
- 结论要落到「这台机器的硬约束是什么」（内存？磁盘？CPU 世代？Windows 版本？）——**脱离硬件的选型建议没有价值**。

### 多层级服务的「哪一层坏了」排查法（代理/隧道/容器链路必用）

当服务经过 N 层转发（隧道 → 宿主服务 → 反代 → 端口映射 → 容器）时，**不要整体测试**，先把它拆成可独立验证的 N 跳：

```
逐跳验证模板
  跳 1  隧道可达？     从对端 <tunnel-cli> ping <目标>
  跳 2  宿主服务在跑？  Get-Service / systemctl is-active
  跳 3  反代配置在？    <proxy-cli> status  （看有没有预期的 target）
  跳 4  端口真的在听？  原始 TCP 连接（不要用 curl，见下方陷阱）
  跳 5  容器健康？      <container-cli> inspect → HealthStatus
```

**监控也要分层，否则会假健康**：
- L1 进程/容器在跑 → 只能发现「死了」
- L2 本地 `/health` 200 → 只能证明到**第一跳**通
- L3 走**公网/外部入口**再探一次 → 才能发现「反代配置丢了 / 隧道断了 / 证书过期」

⚠️ **只做 L1+L2 是最常见的监控设计缺陷**：本地 200 而外部完全进不来时，监控全绿。

**逐跳定位的实战价值**：一次真实排障中，L2 一直 200，但 L3 不通；按跳查下来发现是「隧道服务本身没启」——如果只有 L1/L2，这个故障永远不会被自动发现。

## 常见陷阱

- **帮助文本里的用法可能是错的**：`--help` 写 `SOURCE DEST`，实测可能目标必须已存在。以实跑为准。
- **退出码 0 不等于成功**：有的命令失败也返回 0，要看 stderr。
- **交互式确认命令在脚本里会挂死**：一律加 `-f`，或 `echo y |`。
- **Windows 路径/编码**：Git Bash 下跑容器类工具必须 `export MSYS_NO_PATHCONV=1`；写 `.ps1` 必须 UTF-8 with BOM（否则 PS 5.1 按 GBK 解析中文注释会报假语法错误）。
- **工具输出被吞**：某些环境下 PowerShell 工具返回 exit 0 但无 stdout → 让命令 `Out-File` 到临时文件再用 Read 读。
- **别把「文档没写」当成「不支持」**，也别把「文档写了」当成「能用」——两种都要实跑。
- **搜索排第一 ≠ 可信**：做这类调研时，搜索引擎常把 **SEO 内容农场**排到很前面（实测：搜 `wslc compose` 时排名很高的 `wslcontainers.com` 返回的是赌博站注册教程，与主题毫无关系）。判定法：先看返回内容与问题是否相关；不相关就整个域名丢弃。**可信源只留：厂商官方文档 + 官方仓库的 issue/PR 原始数据（用 REST API 直读，不要二手转述）+ 自己实跑。**
- **GitHub issue 里的一手数据比 README 可靠**：查「某功能是否在路线图上」，直接拉 issue/PR 的 JSON（`api.github.com/repos/<o>/<r>/issues/<n>`），看 `state` / `labels` / 评论里 `author_association=MEMBER` 的回复，以及分支是否真实存在（`/branches/<name>`）。**不要只看标题就下结论。**
